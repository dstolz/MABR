# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

MABR (Matlab Auditory Brainstem Response) is a **proprietary, Windows-only** MATLAB toolbox for presenting acoustic stimuli and acquiring/analyzing ABR electrophysiology data. Copyright Daniel Stolzberg, PhD — see `Copyright.txt`. There is no build system or package manager; it runs inside MATLAB.

One **git submodule**: [`stimgen`](https://github.com/dstolz/stimgen) at `external/stimgen`, the suggested source of calibrated stimuli and the calibration front end. Clone with `--recurse-submodules`, or run `git submodule update --init` after the fact. It is **optional at runtime** — MABR launches and acquires without it, and everything that needs it is gated on `mabr.stim.stimgenAvailable`. Note stimgen is GPL-3.0 while MABR is proprietary; the submodule stores only a commit pointer, so no GPL source enters this tree, but distribution is a decision worth making deliberately (both repos are the same author's).

The acquisition app was **rewritten ground-up** into a single `+mabr` namespace (see `MABR Complete Refactor — Ground-Up Rewrite.md`). The legacy `+abr` package was retired at cutover and is recoverable from git history / the `master` branch.

## Running & developing

- **Launch the app:** run `MABR` from the MATLAB command window. `MABR.m` genpath-adds every subfolder (except `.git`) and opens `mabr.ui.App`.
- **Requires** (see `mabr.Config.RequiredToolboxes`): MATLAB ≥ 9.11 (R2021b — `uitoolbar` on a `uifigure`), Signal Processing ≥ 8.1, Audio Toolbox ≥ 1.5, DSP System Toolbox ≥ 9.1, **Parallel Computing Toolbox** (new — the acquisition engine runs on a parpool worker). Audio I/O expects an **ASIO** device via `audioPlayerRecorder`.
- **Verification (no hardware):** `tests/run_all_verifications.m` runs the suite — engine loopback, `.abr` round-trip through the offline pipeline, legacy import, and the online-advance early-stop. Individual scripts: `verify_engine_loopback`, `verify_data_roundtrip`, `verify_legacy_import`, `verify_online_advance`, `verify_artifact_rejection`, `verify_filters`, `verify_trace_organizer`, `verify_trace_inspector`, `verify_audio_settings`, `verify_stimgen_import`, `verify_stimulation_only`, `verify_timing_selftest`, `verify_timing_loopback`, `verify_test_runner`. All run in TESTING loopback mode with no audio device. `verify_stimgen_import` **skips and passes** when the `external/stimgen` submodule is absent — a suite must not fail over an optional dependency nobody fetched. The same suite runs from the GUI — **Help ▸ Verification Tests…** (`mabr.ui.TestRunner`), which discovers the scripts rather than listing them. `verify_timing_loopback` is also the rig **diagnostic**: run it with `'Testing',false` to characterise the real loop-back (pulse recovery, latency, jitter, clock drift, amplitude margin against the hard-coded 0.1 detection threshold), sweep `'PulseRate'` to find where a device starts dropping pulses, and use its `'Corrupt'` option to confirm those measurements actually respond to a known defect.
- **Verbosity/logging:** code logs through `mabr.log.vprintf(level, [red], fmt, ...)` gated on global `GVerbosity` (-1…3). `mabr.log.vprintf(0,1,...)` prints a critical message in red. Logs also go to `.error_logs/`.

## MATLAB conventions used here

- `+mabr/` is the **package namespace** — everything is `mabr.Thing` / `mabr.subpkg.Thing`. Subpackages: `+acq` (acquisition engine), `+data` (data model + IO), `+stim` (stimulus adapter + advance criteria), `+metrics` (small tested functions), `+ui` (GUI), `+log` (logger).
- `mabr.Config` is a plain **value** object (NOT a superclass) holding constants (`DACSampleRate=192000`, `ADCSampleRate=12000`, `frameLength=1024`, `maxInputBufferLength=2^26`) and the runtime/error-log paths. Nothing inherits from it.
- `mabr.ArtifactPolicy` is the other top-level value object: the artifact criterion (`none`/`voltage`/`rms`), its thresholds **in volts** (defaults ±100 mV peak, 30 mV RMS), and `Repeat`. `loadPrefs`/`savePrefs` persist the user's choice in MATLAB prefs (group `MABR`), so a rig keeps whatever suits its electrode chain; `toStruct`/`fromStruct` are the same fields as a plain struct, forgiving of a missing/invalid field the same way `loadPrefs` is, and back `mabr.ui.App`'s save/load **configuration** file (see GUI section) rather than the "last used" pref. `mabr.ui.App` edits one and hands it to the controller at Start **and on every later change** — the artifact controls are deliberately left live while a schedule runs (see `App.applyArtifacts`), since the criterion is only decided at finalization.
- `mabr.FilterPolicy` is the third top-level value object: the **display** filter chain, as three independent switches — high pass (10 Hz), low pass (3000 Hz), notch (60 Hz, 4 Hz wide) — plus a shared Butterworth order clamped to `[2 8]`. `design(Fs)` caches the `digitalFilter` chain in the object and `apply(x)` runs it zero-phase (`filtfilt`, column-wise) — so the realized response is |H|², corners at −6 dB, which is what `response(Fs)` reports and the dialog draws. `apply` on an undesigned policy returns its input, the same opt-in rule `Recording` follows, and a signal too short to `filtfilt` passes through rather than throwing (a truncated sweep must not kill the live view). `loadPrefs`/`savePrefs` persist it in the same `MABR` pref group; `toStruct`/`fromStruct` (deliberately excluding the cached `Designs`, same as `sameSettings`) are the configuration-file counterpart. It is called *display* filtering advisedly: it decides what a plot or a metric is computed from and never touches `Recording.Data`, which is what `io` writes — so no setting here can reach a `.abr` file, and there is no wrong moment to change one.
- `mabr.AudioSettings` is the fourth top-level value object: the ASIO `Device` name, the `PlayerChannels`/`RecorderChannels` mapping that `mabr.stim.Schedule.renderSpec` and `mabr.acq.worker_loop`'s `prepare_device` have always accepted but the GUI never exposed a way to set, `MicChannel` — the input the calibration microphone is patched to, deliberately **separate** from `RecorderChannels(1)` because acquisition records an electrode where calibration records a mic, two patchings of one device and therefore two settings (only `mabr.stim.CalibrationAdapter` reads it; nothing about it can reach a `.abr`) — `Testing` — the loopback (no hardware) switch, moved here from the main window because it is meaningless without an opinion about which device it is overriding — and `StimulationOnly` (see below). `loadPrefs`/`savePrefs` persist all five in the same `MABR` pref group, so a rig keeps whatever mode, device, and wiring suit it across restarts; `toStruct`/`fromStruct` do the same for the configuration file. Unlike `ArtifactPolicy`/`FilterPolicy` it is a **config** control, not a live one — `mabr.ui.App` locks its Settings menu item for the duration of a schedule (see `configControls`), because the worker's `audioPlayerRecorder` is already open on whatever device (or lack of one) `Start` handed it, and `AcqController.start` re-verifies the timing loop-back (`verifyTimingLoop`) whenever `Schedule.Device`/`PlayerChannels`/`RecorderChannels` change between runs; `mabr.ui.App.ensureController` rebuilds the worker whenever `Audio.Testing` differs from the running controller's, the same way it always compared the old checkbox. The DAC/ADC sample rates stay fixed by `mabr.Config` — every stimulus must already be rendered at `Config.DACSampleRate` — so nothing here sets a rate; `probeSampleRate` instead briefly opens a real device on the selected `Device` and reports the rate it was actually granted, a *determination* rather than a setting — and it opens the *same class* the worker would (an `audioDeviceWriter` under `StimulationOnly`), since probing full-duplex would fail on exactly the input-less hardware that mode exists for. `availableDevices` wraps `getAudioDevices(audioPlayerRecorder)` and never throws, since it feeds a settings dialog, not a start-up check.

  **`StimulationOnly`** is the fifth setting and the one that changes what MABR *is* for a run: playback and the timing pulse go out, and **nothing is recorded**. It exists for rigs where another system does the recording, or none does. `worker_loop`'s `prepare_device` opens an output-only **`audioDeviceWriter`** rather than an `audioPlayerRecorder` whose input is discarded — that is what lets the mode also run on hardware with **no input channels at all** — and `stream_block` skips `rb.writeFrame` while the device clock still paces the loop. Both play columns are still emitted: a timing pulse is as much an output as the signal, and something downstream may well be reading it. It is mutually exclusive with `Testing`, which opens no device at all and therefore wins everywhere; `AudioSettingsDialog` greys the `stimCheck` under `Testing` and `readControls` reconciles the pair, and under stimulation only it greys just the *input* half — the recorder channels and the mic — while device, player channels, and Test Device stay live. Unlike `Testing` (baked into the worker at `parfeval` time, so changing it forces an `ensureController` rebuild) this flag rides **per block in the render spec** (`Schedule.StimulationOnly` → `renderSpec`), which costs nothing because `prepare_device` rebuilds the device on every `Prep`. Client-side, `AcqController` drops the whole recording half: `start` skips `verifyTimingLoop` (there is no input to loop back to, so requiring one would make the mode unusable), `on_engine_state` never starts the live timer, and `on_block_completed` skips `finalize_run` entirely — **no `Block`, no `BlockReady`, no `.abr`**.

  What it does *not* drop is the record of what was played. `AcqController.log_stim_run` is the stimulation-only counterpart of `finalize_run`: one **`.stimlog`** per run (`mabr.data.io.writeStimLog`, same MAT-file-with-a-distinctive-extension convention as `.abr`/`.torg`/`.mabrcfg`, holding one `MABR_StimLog` struct), carrying every presentation in play order — stimulus index and ID, polarity, onset sample and time — plus the bank's parameters flattened exactly as a `.abr`'s `SIG` is, and the schedule settings behind them. Nothing is recorded, but *what was presented* is still the experimental record, and on a rig where another system does the recording it is the only thing that can align the two: the onsets are the rendered ones, and the same play matrix puts a timing pulse at each of them. The onsets come from `renderSpec`'s `ExpectedOnsets` (there is no input to recover them from) and are honest about early stops — `worker_loop` now reports how many play-matrix samples actually went out (a `'streamed'` message, sent *before* the `Completed` state so a `BlockCompleted` listener already has it; `Engine.LastStream`), so a run cut short by Advance/Abort writes the whole plan with the unreached presentations flagged `Presented = false` rather than a truncated one or a lie. `BlockSaved` fires for the file (the event means "a file was written"; the extension says which kind), and `Schedule.recordRun` is fed the presented counts so the plan's bookkeeping is as true here as for a recorded run. The schedule-advance tail runs as always, so the plan drives itself to `SchedComplete` exactly as it would with a recording attached. Covered by `tests/verify_stimulation_only.m`.

  The mode also **re-labels the worker**. `mabr.acq.Engine.Role` (`'acquisition'` / `'stimulus'`, → `WorkerName`) names it in every startup message and log line, because a worker that records nothing is not an acquisition worker and the log saying otherwise is misleading in exactly the mode where the user most needs to be sure. `AcqController.workerRole(stimOnly)` is the one place the mapping lives; `App.ensureController` passes it at construction and `AcqController.start` calls `Engine.setRole` for each run, since one worker is reused across runs that may switch modes between them (`setRole` logs the change — "the worker" in a log must not silently be two different things). `worker_loop` says which device class it opened and tags a stimulation-only block as it streams.

## Architecture: parpool-worker acquisition engine (`+mabr/+acq/`)

The load-bearing subsystem. Acquisition runs on a **1-process parallel pool worker** launched once per session with `parfeval`, keeping the pool and `audioPlayerRecorder` warm. Control/state flow over **parallel queues**; recorded samples flow through **one** memory-mapped ring buffer. This replaces the legacy two-`matlab.exe` design (spawned via `system(...)`, Wmic PID checks, `info.mat`, `dac.wav` handoff, `mabr_com.dat` command/state memmap).

- `mabr.acq.Engine` (client, GUI process) — starts/keeps the pool warm, launches the worker, owns the read-only ring buffer, and turns worker messages into **events** (`StateChanged`/`BlockCompleted`/`WorkerError`) via a `DataQueue` `afterEach` callback. **No busy-waits.**
- `mabr.acq.worker_loop` (runs ON the worker) — owns the `audioPlayerRecorder`, streams the pre-rendered stimulus frame-by-frame (analogue of the legacy `acquire_block`), writes recorded ch1/ch2 into the ring buffer, and polls a `PollableDataQueue` every frame for `Prep`/`Run`/`Pause`/`Stop`/`Kill`. A **TESTING loopback** mode (`Engine(cfg,true)`) runs the whole engine with no hardware.
- `mabr.acq.RingBuffer` — thin wrapper over the retained memmap surface: `ring_signal.dat` + `ring_timing.dat` (single, `maxInputBufferLength`) plus a small `ring_header.dat` write-head header. Worker writable, client read-only.
- Enums `mabr.acq.Cmd` (client→worker commands) and `mabr.acq.State` (worker→client state) travel as messages, not shared memory. `Cmd.Release` (+ `Engine.releaseDevice`) closes the audio device while keeping the worker and warm pool alive. It exists because the worker opens its `audioPlayerRecorder` on the first `Prep` and holds it until `Kill` — that is what keeps block-to-block latency down, but an ASIO device has exactly one owner, so **"controller idle" does not mean "device free"**. Without it, the first calibration after any acquisition could not open the device and the only remedy would be restarting MABR. The next `Prep` reopens it.
- Because commands are polled every frame, the engine can honor an **online advance criterion** — stopping a block early when a correlation threshold is met (the capability the legacy code documented it could not provide).

Sweep extraction moved to `+metrics`: `mabr.metrics.find_timing_onsets` (pure function on a timing vector) and `mabr.metrics.extract_sweeps` (explicit cursor state, reads the ring buffer) — direct analogues of the legacy `abr.Runtime` methods.

## Core data model (`+mabr/+data/`)

- `mabr.data.Recording` (value type) — one channel's `SampleRate` + `Data` + `SweepOnsets`/`SweepLength`, with `SweepData`/`SweepMean`/`noisePower`/`SNR` ported from the old `abr.Buffer` but **cycle-free** (no `ABRobj` back-reference; decimation passed explicitly). Filtering is **explicit** and lives in a `mabr.FilterPolicy` held in `Filters` — the same object the GUI edits and the live view applies, so what the operator watches and what a `Block` reports come off one set of corners. `designFilters()` designs it at the Recording's own `SampleRate`, after which it is applied consistently in segmentation (the legacy designed but never applied it); before that call `ProcessedData` returns raw `Data`. `Data` is never filtered in place and `io` saves `Data`, so a `.abr` file is always the raw trace. `IsArtifact` flags rejected sweeps (aligned with `SweepOnsets`, **not** with `SweepData` — map through the `ValidSweeps` mask, since a truncated run's last window is dropped from `SweepData`); flagged sweeps are excluded from everything descriptive — `CleanSweepData` is the basis of `SweepMean`, `noisePower`/`SNR`/`RMS` and `Block.computeMetrics`, while `SweepData` still returns every sweep — but never removed from `Data`. With *every* sweep flagged, `SweepMean` is all-NaN (there is no mean to report) and viewers skip it.
- `mabr.data.Block` (value) — one condition's result: stimulus metadata + the recorded `Recording` + computed metrics + start time + `SweepPolarity` (+1/-1 per sweep, aligned with `ADC.SweepOnsets`).
- `mabr.data.Session` (handle) — subject/device/rate config + block queue + array of `Block` results.
- `mabr.data.io` — save/load. `writeABR` emits an offline-compatible `ABR_Data` struct and matching filename; `importLegacy` reads old `ABR_Data` structs (incl. sigProp-style SIG) into the new model. `writeStimLog`/`buildStimLog` emit the `.stimlog` a stimulation-only run produces in place of a `.abr` (see `AudioSettings.StimulationOnly`); both filename builders share one `subjectToken`, so a session's files sort together whatever it wrote.

## Stimulus adapter (`+mabr/+stim/`)

MABR **does not** generate signals or calibrate — an external package supplies precomputed, calibrated waveforms as a plain struct array where **each entry is one presentation**: `signal` (required), `ID` (required), optional `SampleRate`/`Repetitions`/`Timing`/`alternatePolarity`/`informativeParams`, and any number of passthrough fields. `mabr.stim.StimulusSet` wraps and validates it; `mabr.stim.demoStimuli` is a built-in tone-pip bank for testing only.

`informativeParams` is the one addition the stimgen work forced. Left absent, MABR infers the list — every numeric scalar extra — which is right for a hand-built bank whose only extras *are* its parameters. A generator emits far more than that (a stimgen `Tone` variant carries `Duration`, `WindowDuration`, `OnsetPhase`), and every name on that list becomes a **grouping dimension** in the offline pipeline, so a source that knows which of its parameters actually vary now says so instead of letting MABR guess from types. `StimulusSet` also carries a `Source` struct (`Kind`/`File`/`Calibration`/`Generated`) and an `isCalibrated()` — provenance, not contract: nothing in acquisition reads them, but a calibrated bank and the demo bank are otherwise indistinguishable once they are struct arrays, and that is exactly the confusion worth being unable to have.

**stimgen is the suggested source** (`external/stimgen`, optional — see `mabr.stim.stimgenAvailable`). `mabr.stim.fromStimgen` converts a `.spl` bank file, a live `stimgen.StimPlayer`, a `StimPlay`, or a bare `StimType` into a `StimulusSet`. Three things about it are load-bearing:

- **One stimgen *variant* is one MABR entry.** A vectorized property expands into variant combinations — a `Tone` with `Frequency=[8000 16000]`, `SoundLevel=[30 60]` is four variants — which is already MABR's unit. The conversion flattens `StimPlayer.StimPlayObjs` → `StimPlay.StimObj` → variants and reinterprets nothing.
- **Regenerated, not resampled.** `StimType.Fs` defaults to 97656.25 (a TDT rate); MABR sets `Fs = Config.DACSampleRate` on a `copy()` and calls `update_signal()`, so each variant is synthesized natively at 192 kHz. This is why the importer takes *parameters* and never a bank's cached `Signal`.
- **`VariantReselectOnUpdate` must be forced false first.** With it at its default, every `selected_value()` call *outside* an update cycle silently re-runs the selector and advances the active index — so metadata read back after `set_variant_index` describes a *different* variant than the `Signal` just generated under it, and an 8 kHz waveform gets saved labelled 16 kHz. The signal is always right; it is the description that drifts. `verify_stimgen_import` FFTs each waveform against its own label to catch exactly this.

Deliberately dropped on import: `StimPlay.ISI`, `StimPlayer.ISI`, `SelectionType`, `StimOrder`. MABR owns presentation and `mabr.stim.Schedule` decides it. `Schedule` does now have a `[min max]` jitter range of its own (`ISIMode`/`ISIRange`), so stimgen's ISI *could* be carried across — it still is not, because the timing is the operator's setting for this session and adopting a bank must not silently retime a schedule already configured around it. `Reps` survives as the starting repetition count **unless the host hid the field**: `fromStimgen`'s `repsHidden` reads a live player's `ControlVisibility.Reps`, and a hidden control means the number is `StimPlay`'s default (20) rather than anyone's choice — 20 sweeps is not an ABR — so it imports as *no opinion* and `Schedule.startingRepetitions` supplies 512. A `.spl` read from disk carries no such tell and is taken at its word. Two unit reconciliations happen in one place (`buildEntry`): stimgen's `SoundLevel` → `Level`, and `Frequency` Hz → kHz, because `mabr.data.io.buildFilename` reads both by name and unit to match the offline regex.

**An uncalibrated stimgen bank is the sharp edge.** `apply_calibration` is a no-op with no calibration loaded, so `SoundLevel` never reaches the amplitude and a 30/60/90 dB series would be three *identical* stimuli. Absolute SPL is unknowable without a measurement, but the spacing is not — dB is a ratio — so `fromStimgen`'s `relativeLevels` pass rescales an **entirely** uncalibrated bank relative to its own loudest entry (`10^(ΔdB/20)`, recorded per entry as `LevelScale`, which passes through to the `.abr`). The reference is the top of the bank, never a fixed dB, so the loudest waveform is left exactly as stimgen normalized it and this can only ever *attenuate* — no bank acquires a clipping risk it did not already have. A **partly** calibrated bank is left untouched: half its volts are real and there is no common reference to be relative to. Either way `Calibrated` stays false and `App` warns rather than refuses — an amber bank label, and a `uialert` on adopt naming which of the two cases it is (`warnUncalibratedLevels` branches on the presence of `LevelScale`). Covered by `verify_stimgen_import`, which asserts a 30 and a 60 dB entry come back exactly 30 dB apart.

Also: `stimgen.StimCalibration.loadobj` currently throws (it assigns the read-only `Engine.MicSensitivity`), and `StimType.fromStruct` calls it unconditionally — so `fromStimgen`'s `readBank` restores the stimulus *without* its calibration and reattaches separately in a `try`. One stimgen bug must not make every saved bank unloadable; a bank whose calibration cannot be revived imports and reports itself uncalibrated. `StimType.fromStruct` also does not restore `SoundLevel`/`Duration`/`WindowDuration`/`WindowFcn` (stimgen's own `load_bank` assigns those itself), so `readBank` does too — without it a bank comes back silently at class defaults, 60 dB and 100 ms.

**MABR owns presentation, the stimulus package does not.** `mabr.stim.Schedule` turns a `StimulusSet` plus three GUI-chosen settings — `ISI` (s, onset-to-onset), `Repetitions` (per entry), and `Strategy` — into ordered *runs*, and renders each into the 2-channel play matrix. Strategies: `blocked`, `shuffled-blocks` (one run per stimulus) and `interleaved`, `shuffled-cycles`, `shuffled` (one run, **intermixed**). All five are permutations of a fixed multiset — each entry gets exactly its repetition count — hence "shuffled", not "random". An entry flagged `alternatePolarity` has its successive presentations multiplied by `+1,-1,+1,…` — the repetition count is *split* between polarities, never doubled, and the polarity travels with the presentation through shuffling. `renderSpec` emits `StimulusIndex` — the stimulus behind each onset — plus `Polarity`, the sign applied there — and refuses runs exceeding `maxInputBufferLength` (`mabr:stim:Schedule:tooLong`, checked before allocating). It builds the timing-pulse channel it synthesizes (one pulse per onset) because sweep extraction depends on it.

The ISI is either of two settings, chosen by `ISIMode`: the scalar `ISI` (`'fixed'`, onsets on a strict grid) or a uniform draw per interval from `ISIRange` = `[min max]` s (`'random'`, so the presentation rate carries no periodicity of its own). Both are always held, and the mode picks between them, so turning randomization off and on cannot lose the range — the GUI's checkbox *is* `ISIMode`. `renderSpec` accumulates one interval per presentation rather than multiplying a period, drawing from the schedule's own `RandStream`, so rendering never perturbs the global `rng` and a `Seed` fixes a plan's timing along with its order. Two dependent properties say which number to reason with: **`MinISI`** (the shortest interval that can occur) is what `overlaps()` and the GUI's overlap warning judge against — one short draw is enough to collide — while **`MeanISI`** is what `summary().duration` estimates from, making a randomized plan's duration an expectation rather than a promise. Nothing downstream knows or cares: the timing channel still marks every onset, so sweep extraction and every metric are indifferent to the spacing, and the realized intervals survive in each file's `ADC.SweepOnsets`. Covered by `tests/verify_isi_jitter.m` (no hardware, no pool).

`mabr.stim.CalibrationAdapter` implements stimgen's `stimgen.calibration.HwAdapter` (`sample_rate()` + `play_and_record(signal)`) against MABR's own audio path, so `Settings ▸ Calibration…` measures **this** rig: `Audio.Device`, out on `PlayerChannels(1)`, in on `MicChannel`, at `Config.DACSampleRate`. The rate is not bookkeeping — `fromStimgen` regenerates every stimulus at the DAC rate and stimgen's `design_filter` produces a rate-specific FIR, so a calibration measured elsewhere would be applied to signals it does not describe. Note stimgen's contract is `(1,:) double` both ways, so `play_and_record` transposes on the way out. It refuses in `Testing` mode (loopback would measure the excitation fed back to itself) and while the controller is non-`Idle`, and calls `Engine.releaseDevice()` once per adapter to take the device off the idle-but-still-holding worker. MABR does **not** implement `stimgen.HardwareHost` — that is a TDT/RPvds buffer protocol, and MABR owns playback through its own worker.

Advance criteria are proper implementations in `+stim/+advance/`: `num_sweeps` and a real `corr_threshold` (the legacy `abr_adv_corr_thr.m` was an empty stub). They are evaluated **only for blocked strategies** — an intermixed run pools different conditions, so early-stopping it is both meaningless and unbalancing. The GUI greys the control out accordingly.

**Artifact rejection** is *decided* at finalization. `AcqController.finalize_run` judges each sweep with `mabr.metrics.detect_artifacts` (a pure function: `voltage` = any sample outside ±thr, `rms` = sweep RMS over thr) on the **filtered** sweeps, and records the verdict in `Recording.IsArtifact`. The live path *previews* the same policy (`AcqController.live_artifacts`, on the sweeps `filter_sweeps` has already run the same chain over; with the high pass switched off it falls back to removing each sweep's own mean, since nothing else would be taking out a baseline offset) so the live mean shows the average the block will actually hold and a noisy electrode is visible while it is happening — nothing there is recorded, and re-pointing `Artifacts` just changes what the next tick previews. Once flagged, a sweep is excluded from everything **descriptive**: `Recording.CleanSweepData` is what `SweepMean` (hence the trace organizer), `noisePower`/`SNR`/`RMS`, and `Block.computeMetrics` are built on, while `SweepData` still returns every sweep. Rejected sweeps are always **marked and saved, never dropped** — `io` writes `ADC.IsArtifact` alongside `ADC.SweepPolarity` so offline analysis can override the call or use `abr_analysis/rejectArtifacts` (which instead rejects by `isoutlier` over a whole session; a fixed threshold is what the live path needs because it is decidable for one sweep as it arrives). When `ArtifactPolicy.Repeat` is set, the controller calls `Schedule.appendMakeup(counts)` to re-present what was lost. Make-up runs are **appended to the end** of the plan (a run's play matrix is rendered before streaming and cannot grow mid-flight) and hold **one stimulus each**; `Schedule.MakeupLimit` (default 1 = at most double a condition) bounds the total so a permanently noisy electrode cannot make a session run forever, and `reset()` drops them so a re-started schedule begins from what `build()` produced. Clearing `Repeat` mid-schedule is the one policy change that cannot simply wait for the next run — `AcqController.set.Artifacts` calls `Schedule.dropPendingMakeup()`, withdrawing the make-up runs not yet reached (the one in progress is kept) and refunding their budget.

## GUI (`+mabr/+ui/`)

- `mabr.ui.App` — the programmatic uifigure view (replaces `abr.ControlPanel`); `createComponents` builds five titled panels (Session / Stimulus / Presentation / Acquisition / Run) from one `panelGrid` helper and a shared `LabelWidth`, so the fields align across panel borders; panels carry explicit pixel heights because `'fit'` does not see through a `uipanel` to its nested grid (so adding a row to a panel means bumping its height in `Grid.RowHeight`). The Acquisition panel's artifact controls share **one** threshold field between the voltage and RMS criteria — they are alternatives, and `syncArtifactFields` swaps the value and its display-format caption on a mode change so each criterion keeps its own number. Below them the **Filters** row is a one-line summary plus a button: three independent filters need eight controls and a response plot to state properly, which is a window (`mabr.ui.FilterDialog`) rather than a panel row, so the row carries the whole setting in text and the button is only pressed to change it. Both groups are in `liveControls` — they stay enabled while a schedule runs and are re-derived by `transport()` in both directions, since `setBusy` kills them on the way in. The Presentation panel's ISI row is followed by a **Random** checkbox and the `[min max]` ms bounds it governs (`Schedule.ISIMode`/`ISIRange`), sharing one row in the field columns the way the artifact-repeat checkbox does; the two settings are alternatives, so `syncISIFields` greys whichever is not in force and `transport()` re-derives it for the same reason it re-derives the advance enables — `configControls` switches all five ISI controls back on wholesale. `isiSeconds` is the single place the GUI answers "which interval", returning the minimum (for the overlap warning) and the mean (for duration estimates) so those two questions cannot be confused. The Stimulus panel's Bank row is three buttons — **Design…** / **Load bank…** / **Demo** — with stimgen leftmost because it is the suggested route. `Design…` opens `stimgen.StimPlayer` **non-modally** and the same button becomes **Adopt bank**: `StimPlayer` keeps its figure handle private so there is nothing to `uiwait` on, but non-modal is the better shape anyway — it lets the user tune, adopt, inspect in the stimulus viewer, and adjust again without reopening, matching how the viewers already behave. `hideDesignerSessionControls` then calls stimgen's own `set_control_visibility(All=false)`, collapsing the designer's Reps / ISI / Shuffle-Serial / Run / Pause widgets out of its layout — every one of them duplicates a Presentation-panel setting MABR owns, and the duplicates are inert (`fromStimgen` drops ISI and `SelectionType`, and the designer's Run streams through stimgen's speaker preview, not the rig the worker holds open). It is guarded on `ismethod` rather than assumed, since a rig may have the optional submodule checked out at an older commit; the per-stimulus **Play**/**Play All** preview buttons are not hideable and stay, which is right — auditioning a stimulus is the designer's job. `syncDesignButton` derives its label/tooltip/enable (and is re-called from `transport()`, since `configControls` switches it on wholesale but it must stay off without the submodule). `Load bank…` takes `.spl` or `.mat` — `StimulusSet.fromFile` dispatches on extension. The bank label now reads `12 stimuli · stimgen`, amber rather than green when uncalibrated.

A **Settings** menu (beside `HelpMenu`, built alongside it in `createComponents`) holds `Audio Device (ASIO)…`, which opens `mabr.ui.AudioSettingsDialog` over the `Audio` property (`mabr.AudioSettings`), and `Calibration…`, which opens stimgen's own `CalibrationGui` over a `mabr.stim.CalibrationAdapter` rather than reimplementing it — stimgen owns calibration, MABR owns the rig. Unlike the artifact/filter controls both are in `configControls`, not `liveControls` — they lock for the duration of a schedule, since `buildSchedule` hands `Schedule.Device`/`PlayerChannels`/`RecorderChannels` to the controller only at `Start` and `AcqController.start` verifies the timing loop-back against whatever it was handed. The **Help** menu adds `Verification Tests…` below the wiki link, opening `mabr.ui.TestRunner`; it is a `configControls` entry too, for a blunter reason — the suite builds its own engine, worker and pool, so it cannot share the rig with a schedule in flight. Owns the presentation settings (bank, per-stimulus repetitions, strategy, ISI); `buildSchedule` is the single place they (and the `Audio` settings) become a `Schedule`, shared by the plan-summary preview and `onStart` so they cannot drift. **Start and Preview are one code path** — `onStart(preview)`; Preview hands the controller a `Session` with an empty `OutputPath`, which is already `finalize_run`'s record-without-saving route, so blocks are still acquired, finalized, counted for artifacts, and pushed to the viewers through `BlockReady` while nothing reaches disk (and the output folder does not join the remembered history). Because a preview is otherwise indistinguishable from a real run, the Run panel's title carries `PREVIEW (nothing is saved)` for as long as one is in flight. A **stimulation-only** schedule (`Audio.StimulationOnly`) gets the same treatment one notch stronger and takes precedence over it — `STIMULATION ONLY (no recording)`, since a preview acquires everything and merely declines to write it while this never records at all. `setRunTitle` decides *which* banner (from the `StimOnlyRun` snapshot, captured at Start for the same reason as `Previewing`) and the caller only says whether one is in flight. In that mode the **entire Acquisition panel is disabled** — `syncAcquisitionEnables` is the one place that decides it, retitling the panel `Acquisition — n/a (STIMULATION ONLY)` (a greyed control says "not now"; only the panel can say why) and routing through the three `sync*` functions that own those enables, since `transport()` calls them and would otherwise put the controls straight back. Those three speak only for their own *fields*, though, which leaves every row label black and the header bold — a panel that reads as live with some dead controls in it, which is the opposite of what is true — so a final sweep disables the panel as a unit, labels and title included (`ForegroundColor` greyed against the `AcqPanelFG` captured at build time, since the theme's own title colour is not the same everywhere). It runs **last** for that reason: it is the one that has to win. Coming back *out* of the mode it re-derives only the labels, which carry no state of their own — every interactive control keeps whatever verdict the `sync*` calls just reached, so an artifact threshold stays dead under `none` and Advance under an intermixed strategy. The panel's own `Enable` is deliberately unused: `uipanel` only gained one after R2021b, which `mabr.Config` still supports. Every one of them judges, stops, or displays a *recording*: an advance criterion has no running average to watch, an artifact threshold no sweep to judge, a filter chain nothing to draw (`FilterLabel` reads `n/a — nothing is recorded`). The live-plot toolbar button goes with them, since the controller is handed no `LivePlot`; the trace organizer stays, because it can still load a `.torg`. `syncAcquisitionEnables` is called at construction, from `transport()`, on each **Commit** in the audio dialog (`applyAudioSettings`, which is why the panel greys while that dialog is still open), and at the end of `applyConfiguration` (a restored `Audio` can enter the mode after the artifact/filter blocks above it have just re-enabled their controls from the same file). Advance is re-derived only when nothing is running, because it is a `configControls` entry that `transport()` owns. In that mode `onStart` opens **no viewers** and hands the controller an empty `LivePlot` — there is nothing coming back to plot, and two windows that never fill are worse than none — so the Run panel's `Sweeps:`/`r =` readouts carry run progress (`Run k/N`, `no recording`) instead, written by `setRunReadout` from `onState`, since no live timer runs to fire `onMetrics`. `AudioMenuItem` is already a `configControls` entry, so the mode cannot be toggled mid-schedule. It opens **both acquisition viewers at Start/Preview** — `openViewers`, called from `onStart`, builds only the ones whose window is absent and never raises one already up — and lays them out beside itself on first run; nothing but the main window opens at launch, since there is nothing to watch until a schedule is in flight; a `uitoolbar` of pictogram glyphs (`live` = one trace on axes, `traces` = a stack of traces, `stim` = a loudspeaker, `help` = a question mark, all drawn through `mabr.ui.Icon` like `TraceOrganizer`'s) raises them (`live`, `traces`), opens the stimulus viewer (`stim`), and opens the wiki (`help`). Because an open organizer keeps itself current through `BlockReady`, `traces` is a pure raise once it exists — it backfills from the `Session` only when building the organizer from scratch, so it cannot discard a loaded `.torg` view. `stim` is on-demand (it inspects what is about to be played, not what is coming back); `adoptStimuli` pushes each newly loaded bank into an open viewer, and a plain raise deliberately does *not* re-push, so it keeps the user's selection.

A **File** menu (leftmost, built before `SettingsMenu` in `createComponents`) holds `Save Configuration…` / `Load Configuration…` — the direct analogue of the legacy `+abr` ConfigTab's "Save/Load a Config file", now covering everything the GUI owns: Subject/Output, the stimulus bank plus per-stimulus repetitions, Strategy/Advance/ISI, and the `Artifacts`/`Filters`/`Audio` policies, in one `.mabrcfg` file (a MAT-file under `save(file,'MABRConfig')`, matching the `.abr`/`.torg` convention of a distinctive extension over a plain MAT-file). This is a separate concept from each policy's `loadPrefs`/`savePrefs` "last used" persistence — a configuration is a deliberately named, reloadable point (switching between protocols on one rig) captured by `App.captureConfiguration` as **plain structs**, never classdef objects, so a file saved by one version keeps loading after a class gains or loses a property. `App.applyConfiguration` restores defensively field-by-field (the same rule `loadPrefs` already follows) and returns a warning string rather than calling `setStatus` itself, because `onLoadConfiguration`'s own final status would otherwise overwrite it the instant it returns; `applyConfigStimuli` is where that warning usually comes from, when `StimulusSource.File` — the bank's own provenance, from `StimulusSet.Source` — is empty (a bank built live in the stimgen designer and never saved to a `.spl`/`.mat`) or has moved, in which case the bank already loaded is left alone and the repetitions are not touched either. Where the bank *does* reload, saved per-stimulus repetition counts are matched back onto it **by ID, not position**, so a bank that has gained or dropped an entry since the configuration was saved still lines counts up correctly. Restoring a Strategy that turns out to intermix stimuli always wins over a saved 'Correlation Threshold' `Advance` value (`syncAdvanceEnables` runs first and its disabled state gates whether the saved value is even applied) — early-stop is meaningless for an intermixed run, configuration or not. `LoadConfigMenuItem` is a `configControls` entry, since loading one can replace the bank/ISI/audio mapping out from under a running schedule; `SaveConfigMenuItem` is not, since capturing a snapshot changes nothing and is safe at any time, including mid-run.

- `mabr.ui.WindowPos` — restore/remember a window's position in MATLAB prefs (`MABR`/`WindowPos_<name>`), clamped back onto the current display so an unplugged monitor cannot strand a window off-screen. `App` applies it to both viewer windows, saving on viewer close and on app close.
- `mabr.ui.Icon` — renders a 16×16 toolbar `CData` from ASCII art ('X' inked, '.' transparent). Shared by `App`'s and `TraceOrganizer`'s toolbars.
- `mabr.ui.FilterDialog` — modal editor over a `mabr.FilterPolicy`, returning the edited policy (or `[]` on cancel) **undesigned**, so the caller designs at whatever rate it needs and no stale design travels with the object. Three checkbox+field rows, a shared roll-off dropdown, and a log-frequency magnitude plot of the chain as applied. `validate(Fs)` *reports* an unrealizable chain (high pass above low pass, a corner past Nyquist) so OK can grey out rather than the dialog erroring at a user mid-edit.
- `mabr.ui.AudioSettingsDialog` — modal editor over a `mabr.AudioSettings`. A **Testing (loopback, no hardware)** checkbox sits at the top — moved here from the main window's Acquisition panel, since it decides whether anything below it matters: checking it greys out the device dropdown, the player/recorder `[signal timing]` channel fields, the **Microphone** input channel (calibration needs a real device as much as acquisition does), and the **Test Device** button (`probeSampleRate`, which reports the sample rate the selected device actually grants), because `worker_loop`'s `prepare_device` opens no device at all in that mode. Directly beneath it, **Stimulation only (no recording / no loop-back)** is the same kind of switch one step less drastic — a real output device *is* opened, so device, player channels, and Test Device stay live, and only the recorder channels and the mic grey out. `syncTestingEnable` derives both sets of enables in one place and `readControls` forces `StimulationOnly` false under `Testing`, so the two can never both be in force. The DAC/ADC rates are shown but fixed (`mabr.Config`) since every stimulus must already be rendered at `Config.DACSampleRate` — this dialog *determines* whether a device honours that rate rather than letting one be chosen. Its transport is **Commit / Cancel** rather than OK / Cancel because the two are no longer the same act: `onCommit` applies the settings through an optional `applyFcn` the owner passes as a third argument (`App.onAudioSettings` → `App.applyAudioSettings`, which adopts them, `savePrefs`, re-runs `syncAcquisitionEnables`, and sets the status line) and **leaves the dialog open**, so the consequence of a setting is visible while it can still be changed — above all `StimulationOnly`, which takes the entire Acquisition panel out of play, and which the user would otherwise only see after closing the window they would have to reopen to undo it. `applyAudioSettings` ends in a `drawnow` because the dialog is modal and nothing would flush the queue until it closed, and a failing `applyFcn` leaves the edit *uncommitted* rather than reporting a success the app never had. `syncCommitEnable` greys Commit whenever the controls match what was last committed — nothing pending — and re-labels Cancel to **Close** by the same test, since committed settings have already been applied and are not about to be undone; the dirty comparison is against a `readControls()` snapshot taken at open, so a `settings0` holding both mode flags is normalized before it can read as a pending change. The return value is the last *committed* settings (`[]` if none), which is what a caller passing no `applyFcn` uses. Like the acquisition viewers its position is remembered across sessions (`mabr.ui.WindowPos`).
- `mabr.ui.TestRunner` — the verification suite as a window (Help ▸ Verification Tests…, or standalone). The list is **discovered**, not declared: every `verify_*.m` in `tests/` becomes a row, ordered by parsing the `@verify_…` calls out of `run_all_verifications.m` so the two cannot disagree, with anything that file does not mention falling in after — a test that exists is a test the window offers, wired into the suite or not. A test passes by returning without throwing, the same contract `run_all_verifications` relies on. Output is captured per test with `evalc`, and the `try`/`catch` sits *inside* the captured region (`runOne` → `guarded`) so a failure keeps what the test printed before it threw. Everything runs hardware-free except one deliberate opt-in: **Use the rig for the timing loop-back** re-runs `verify_timing_loopback` with `'Testing',false` and the device/channels from `mabr.AudioSettings.loadPrefs`, which is the rig diagnostic that file documents. Stop is cooperative (MATLAB is inside the test; it takes effect between them), and closing mid-run defers the teardown rather than pulling the window out from under a running test. Covered by `tests/verify_test_runner.m`, which drives it the way a user does and is itself discovered by it — the nesting is bounded because the run it drives is `verify_filters`.
- `mabr.ui.RepetitionsDialog` — modal editor returning a repetition vector (or `[]` on cancel): one value for the whole bank, or one per stimulus, with a live total and duration estimate.
- `mabr.ui.AcqController` — owns the `Engine`/`Session`/`StimulusSet`/`Schedule`, translates UI actions → engine commands and engine events → UI updates, and runs **one ~20 Hz timer** for the live view only. A single explicit `mabr.ui.ProgState` (Idle/PrepBlock/Acquire/BlockComplete/AdvanceBlock/SchedComplete/Error) drives program flow — event-driven, no global, no busy-wait. `finalize_run` **de-interleaves** the run: it pairs recorded onsets with `Schedule.runSequence` and emits one `mabr.data.Block` + one `.abr` per stimulus present, so the on-disk unit stays one-file-per-condition however the run was ordered. A homogeneous run saves the continuous trace; an intermixed one saves each stimulus's sweep windows concatenated (`compact_sweeps`) rather than N copies of a shared trace. `finalize_run` is also where the `Artifacts` policy is applied, where the `Filters` policy is handed to each `Recording`, and where make-up runs are appended (see above). The live path filters too: `filter_sweeps` runs the chain over the pre- and post-onset windows **together**, since `extract_sweeps` takes the baseline as the samples immediately preceding the onset at the same stride — one unbroken segment — which doubles the length available to `filtfilt` and keeps the edge transient in the baseline rather than on the first milliseconds of the response. Everything downstream of it (traces, correlation, artifact preview) therefore sees the same chain finalization will use. `set.Filters` redesigns the cached `LiveFilter` at the ADC rate on assignment, because `designfilt` costs milliseconds and the tick runs 20 times a second. It raises **`BlockReady`** (`.Info.block`, the finalized `Block`) once per stimulus recovered — always, independent of saving — alongside `BlockSaved` (`.Info.file`), which only fires when the `Session` has an `OutputPath`. Viewers listen to `BlockReady`. `start()` also runs a one-time hardware self-test, `verifyTimingLoop`: it streams a synthetic timing-only block (no signal, a few unit pulses) through the real `Engine.prep`/`run` path and confirms at least one pulse comes back on the timing input channel before letting the first real block begin, so a broken or mis-mapped loop-back cable — "the most common rig problem" — fails immediately with `mabr:ui:AcqController:timingNotDetected` instead of after a whole block streams with zero onsets. A private `SelfTestActive` flag makes that synthetic block invisible to `on_engine_state`/`on_block_completed`. The result is cached as `VerifiedAudioConfig` against the current `Device`/`PlayerChannels`/`RecorderChannels` rather than for the controller's whole lifetime, because `App.ensureController` reuses one `AcqController` across `Start` clicks and those three are editable between runs — so the check re-runs whenever they change and is skipped otherwise. It runs unconditionally, including in `Testing` mode, since `worker_loop`'s loopback branch passes the timing column straight through and exercises the identical code path.
- `mabr.ui.LivePlot` — the live view, and the one place an intermixed run is legible while it runs. The most recent sweep keeps its **own axes at the top** (a single sweep is tens of times a mean; sharing an axis would flatten the averages) with the correlation bar beside it; below it sits **one running mean per stimulus the run presents**, either overlaid on one axes or one small axes each. Sweeps are attributed by the per-onset stimulus index `AcqController.live_info` passes through — the same pairing `finalize_run` de-interleaves by, so the live panels and the saved blocks agree. The controller hands it `[pre post]` as one contiguous segment so the time base can start **before** the onset; `TimeBase` (default `[-2 10]` ms), `Layout` (`overlay`/`separate`), and `AmpMode` (`each`/`common`/`manual` + `ManualLimit`) are public properties, and the control strip along the bottom of the window writes exactly those. Overlaid means share an axes and therefore a scale, so `each` collapses to `common` there; the latest-sweep axes always autoscales, including under `manual`. `setFilterText` captions the latest-sweep axes with the chain in force (a subtitle — the sweep count owns the title and the artifact readout owns the top-left corner), so a filtered view is never mistaken for the raw signal. Covered by `tests/verify_live_plot.m` (no hardware).
- `mabr.ui.StimulusViewer` — read-only inspector for the loaded `StimulusSet`: a multi-select list of entries beside time-domain and magnitude-spectrum axes, plus a details pane (duration, rate, peak/rms, `alternatePolarity`, passthrough params). An overlay's spectra share one 0 dB reference — the loudest entry selected — so level differences stay visible.
- `mabr.ui.TraceOrganizer` (+ `Trace`/`Marker`) — interactive stacked-waveform viewer with the broken legacy Group/Marker fixed and the user32.dll mouse hook replaced by standard figure callbacks. Each trace is labelled with its stimulus ID and carries a per-trace amplitude `Gain` on top of the shared normalization; amplitude, spacing, selection, ordering, and marking are driven from a menu bar, a right-click menu, and the keyboard, all built from one `menuSpec` so they cannot drift. `saveView`/`loadView` round-trip a `.torg` file holding the waveforms plus the complete display state, so a view reloads exactly as saved; markers are stored as sample indices so they survive rescaling. `listenTo(controller)` subscribes it to `AcqController.BlockReady` so an open view gains a trace as each block completes; it tracks one controller at a time, so re-opening the organizer (or rebuilding the controller) re-points the listener instead of duplicating traces. **Double-clicking a trace** (or `i`, or Peaks ▸ Inspect trace…) opens it in `mabr.ui.TraceInspector` — the stack normalizes every trace to one shared scale, which is what a level series needs and what a measurement cannot use, so latencies are picked over there and come back through `Trace.setMarkers`. `onTraceClick` branches on `SelectionType == 'open'` and **disarms the drag** the first click of the pair armed, or the trace follows the mouse while the inspector opens. One inspector at a time: re-opening on the same trace raises the window rather than discarding the peaks placed in it, and `pruneInspector` closes it when the trace it was editing is removed. Covered by `tests/verify_trace_organizer.m` (no hardware).
- `mabr.ui.TraceInspector` — the measurement window behind that double-click: one trace, full size, in volts scaled to µV (`DisplayScale`/`DisplayUnit`), with the organizer's normalization, gain, and offset all out of the way. Waves are rows in a table — a name, a search window in ms **re stimulus onset** (a `Recording`'s `TimeVector` starts at the onset, so the trace's own time base is already the right one), and Peak or Trough — and `autoDetect` fills each enabled row with the **most prominent** extremum inside its window, ranking `mabr.metrics.find_peaks` by prominence rather than taking the first. A window holding no turning point at all (a monotonic flank, a peak on the window edge) falls back to the segment extremum: the latency it then reports is what tells the user the window is wrong, which is more use than a silent blank. **Opening the inspector runs this automatically** on whatever the constructor's `seedFromTrace` leaves unplaced — `find([obj.Waves.Enabled] & isnan([obj.Waves.Loc]))` — so a trace with nothing marked yet shows peaks with no button press, but a pick already there (seeded from the trace, or left from an earlier pass) is never recomputed out from under the user; the manual Auto-detect button/`a` has no such restriction and recomputes every enabled wave, placed or not, which is how a wave gets re-found after its window is widened. A placed marker is then dragged freely, clicked into place (snapping to the nearest local extremum within `SnapWindow` ms), or nudged a sample at a time — and it may leave its window, because the window is a search hint, not a cage. `SmoothSpan` smooths the **view and the detection together** (picking off one signal while showing another is a disagreement nobody catches until the numbers are wrong) with the raw trace still drawn underneath; markers are stored as indices into the trace's own samples, so nothing smoothed is ever transferred. **Nothing reaches the trace until Apply & Close**, which calls `Trace.setMarkers` with the placed waves in temporal order plus their names and then fires the apply callback so the organizer redraws; Cancel writes nothing. Reopening on a marked trace **seeds the table from those markers**, matching by name, so a second pass edits the first. Search windows (never the picks) persist in the same `MABR` pref group on Apply, and `results()` returns them as a table (`copyTable` puts the same thing on the clipboard). Covered by `tests/verify_trace_inspector.m` (no hardware).

## Offline analysis pipeline (`abr_analysis/`) — UNCHANGED

A **separate, function-based** batch pipeline (authored `dstolz@umd.edu`, 2025) — not part of the app and untouched by the rewrite. It reprocesses saved `.abr` files. Flow (`batchABRAnalysis`):

`getABRSessions` → `parseABRFiles` (regex over filenames, e.g. `SUBJ_ID_<n>_Frequency_<f>kHz_Level_<L>dB_<yyMMdd'T'HHmmss>.abr`) → `extractABRResponses` (loads `-mat`, filters full trace, segments into sweeps grouped by stimulus) → `rejectArtifacts` → `filterABRData` → `plotABRGrid` → `abrPermutationThreshold` (permutation-test threshold via `permtest`, with `abrPermutationThresholdCuration`).

It reads exactly: `ABR_Data.ADC.SampleRate`/`Data`/`SweepOnsets`, `ABR_Data.StartTime`, `ABR_Data.SIG.informativeParams` + numeric named params + `Label`. `mabr.data.io.writeABR` emits precisely these, plus `ADC.SweepPolarity` (+1/-1 per sweep) and `SIG.alternatePolarity` (0/1) for polarity-aware analysis, and `ADC.IsArtifact` (logical per sweep) recording which sweeps acquisition rejected — all three always written, and kept out of `informativeParams` so they don't become grouping dimensions; `verify_data_roundtrip` confirms it. Note `batchABRAnalysis` has a **known stale-signature bug** (it calls `parseABRFiles`/`extractABRResponses` with positional args that no longer match) — **do not fix** it; call those functions with name-value syntax directly instead. `parfor_progress` is an external File Exchange dependency of this pipeline.

## Data file format

`.abr` files are **MATLAB v5 MAT-files** (despite the extension) containing a single `ABR_Data` struct. Load with `load(file,'-mat')`. `.mabrcfg` files are the same convention applied to `mabr.ui.App`'s save/load configuration feature (see GUI section): a MAT-file holding one variable, `MABRConfig`, a plain struct. `.stimlog` files are the same again, holding one `MABR_StimLog` struct — the stimulation sequence of one run, and the *only* output a stimulation-only session produces (see `mabr.data.io.buildStimLog` for the fields; `Sequence` is parallel arrays, one element per presentation, so `struct2table(S.Sequence)` reads as a log on the spot). Note `*.abr`, `*.stimlog`, `.runtime_data/`, and `*.asv` are gitignored.
