# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

MABR (Matlab Auditory Brainstem Response) is a **proprietary, Windows-only** MATLAB toolbox for presenting acoustic stimuli and acquiring/analyzing ABR electrophysiology data. Copyright Daniel Stolzberg, PhD — see `Copyright.txt`. There is no build system or package manager; it runs inside MATLAB.

Two **git submodules**, both under `external/` and both picked up by `MABR.m`'s `genpath`. Clone with `--recurse-submodules`, or run `git submodule update --init` after the fact.

- [`granary`](https://github.com/dstolz/granary) at `external/granary` — **the logger**. Every message MABR prints to the command window and every line in `.error_logs/` goes through it (see the Verbosity/logging bullet). It is **not** optional the way stimgen is: it is the toolbox's only logger, and a clone missing it loses the daily file that explains a failure. It is deliberately not fatal either — `mabr.log.vprintf` falls back to console-only printing and says so once, because a logger that threw would take down the app at startup and make the error about the missing logger itself unloggable. Gated on `mabr.log.granaryAvailable`, the same idiom as stimgen's.
- [`stimgen`](https://github.com/dstolz/stimgen) at `external/stimgen` — the suggested source of calibrated stimuli and the calibration front end. **Optional at runtime** — MABR launches and acquires without it, and everything that needs it is gated on `mabr.stim.stimgenAvailable`.

Note both are GPL-3.0 while MABR is proprietary; a submodule stores only a commit pointer, so no GPL source enters this tree, but distribution is a decision worth making deliberately (all three repos are the same author's) — and granary being a *required* dependency rather than an optional one is the sharper end of that: MABR does not run usefully without it, where it does run without stimgen.

The acquisition app was **rewritten ground-up** into a single `+mabr` namespace (see `MABR Complete Refactor — Ground-Up Rewrite.md`). The legacy `+abr` package was retired at cutover and is recoverable from git history / the `master` branch.

## Running & developing

- **Launch the app:** run `MABR` from the MATLAB command window. `MABR.m` genpath-adds every subfolder (except `.git`) and opens `mabr.ui.App`.
- **Requires** (see `mabr.Config.RequiredToolboxes`): MATLAB ≥ 9.11 (R2021b — `uitoolbar` on a `uifigure`), Signal Processing ≥ 8.1, Audio Toolbox ≥ 1.5, DSP System Toolbox ≥ 9.1, **Parallel Computing Toolbox** (new — the acquisition engine runs on a parpool worker). Audio I/O expects an **ASIO** device via `audioPlayerRecorder`.
- **Verification (no hardware):** `tests/run_all_verifications.m` runs the suite — engine loopback, `.abr` round-trip through the offline pipeline, legacy import, and the online-advance early-stop. Individual scripts: `verify_logging` (**first in the suite**, since everything after it logs: the granary wiring, every calling shape, caller attribution read back out of the file, the literal-text format policy, the two independent verbosity gates, one record per exception, and MABR still printing with the submodule off the path — it writes its probes to a temporary log and puts the user's log directory and verbosity globals back, and unlike `verify_stimgen_import` it does **not** skip when its submodule is absent, because granary is required where stimgen is optional), `verify_strategies` (the built-in strategies present the designs they are named for, conventional runs and interleaved cycles follow `OrderBy`/`OrderDirection`, and the retired names still load — `interleaved-ramp`/`-plateau` with the order they stood for), `verify_play_plan`, `verify_engine_loopback`, `verify_device_reuse` (the worker keeps its device open and clocked between runs and rebuilds it only on a changed setting — a real worker over `mabrtest.FakeAudioDevice`, since Test Mode opens no device), `verify_data_roundtrip`, `verify_legacy_import`, `verify_online_advance`, `verify_custom_strategy` (the custom presentation-strategy contract: the context, the accepted return shapes, the validator, the template, polarity parity with the built-ins, and a file-resolved user strategy driving the run order), `verify_artifact_rejection`, `verify_loop_mode` (Loop: `Schedule.loopRun` inserting a pass of a run directly behind it — the same presentations and signs, flagged `IsLoop`, dropped by `reset()`, a make-up run's pass a full run, an intermixed plan refused — then, in loopback, a run held for several passes until Loop is cleared, each pass its own block and `.abr`, Advance still moving on, Abort still halting, an intermixed plan played once whatever `Loop` says, stimulation only looping too; and no `.abr` overwritten by a same-second one), `verify_filters`, `verify_live_pipeline` (the live statistics are those of the sweeps, bit-identical however the run arrives — one call, random slices, a sweep at a time — and rebuilt exactly on a policy, gain or chain change, with no copy of the sweeps made by stepping; and a dropout inside a timing pulse is not an onset, live or at finalization; no pool), `verify_compute_worker` (the publish buffers, a worker-served run, bit-identical parity, priorities, the metrics worker, and a DSP worker lost mid-run — the worker parts **skip and pass** where the pool cannot hold three workers), `verify_stimulus_alignment`, `verify_test_mode`, `verify_progress_monitor`, `verify_presentation_order` (the order window's active condition follows the live count, and `Schedule.setEnabled` drops a disabled condition only from runs not yet started — no pool), `verify_metric_plot`, `verify_trace_organizer`, `verify_trace_inspector`, `verify_notes`, `verify_audio_settings`, `verify_view_prefs` (what a rig gets back next session beyond those settings: `mabr.ViewPolicy`, the window layout as one snapshot, and the live and analysis views' look — it takes the user's own prefs out of the way and puts them back, as every pref-touching script here does), `verify_recent_banks` (the recent stimulus banks list, `mabr.stim.BankHistory`: order, de-duplication, the cap, remove, distinct labels, and a pref that holds junk — no window, no pool), `verify_stimgen_import`, `verify_stimgen_launcher` (the stimgen tools launcher: settings and both persistence routes, Test Mode/Offline/adapter reuse, the designer opened at the rig's rate with capture routed through it, the main window's Design… designer put on that same rig, the shared calibration window, the inspector, a vanished calibration file — skips without the submodule), `verify_calibration_latency` (the calibration adapter takes the device round trip out of each record via the timing loop-back, so a conduction delay reads the air path; its stimgen part skips without the submodule), `verify_stimulation_only`, `verify_timing_selftest`, `verify_timing_loopback`, `verify_test_runner`, `verify_shutdown_pool` (last in the suite deliberately: it ends with no pool open, so anything after it would pay the relaunch). All run in TEST MODE (loopback) with no audio device. `verify_stimgen_import` **skips and passes** when the `external/stimgen` submodule is absent — a suite must not fail over an optional dependency nobody fetched. The same suite runs from the GUI — **Help ▸ Verification Tests…** (`mabr.ui.TestRunner`), which discovers the scripts rather than listing them. `verify_stimulus_alignment` is the one that tests the correspondence every other number rests on — that the samples recorded at the onset a timing pulse marks **are** the stimulus the schedule placed there. Its bank is built so each condition is identifiable from its own samples (one frequency per column of the design, one amplitude per row, both frequencies chosen to survive the decimation *and* the display low pass), which turns "is this attributed correctly?" into arithmetic: a mean sweep must peak at its own `Frequency`, and a 30 dB step must come back as a 31.62× amplitude ratio. In loopback the DAC frame *is* the ADC frame, so it asserts the strongest form available — recovered onsets sample-exact against `ExpectedOnsets`, and the recorded samples at each onset bit-identical to that stimulus's waveform times its polarity. It covers the plan, the recording, de-interleaving into `Block`s, the online metrics (through `evaluateJobs` *and* a real `MetricPlot`), the live per-condition statistics, alternating polarity, the snapshot an analysis window pulls mid-run (made only when pulled, and each of its conditions its own), and the same run again through the compute workers. It is **also a rig diagnostic**: `verify_stimulus_alignment('Testing',false)` streams through the real device, where it asserts a *constant* onset offset (reporting the loop-back latency) rather than zero and skips the bit-exact waveform comparison, since what returns through a converter is not what went out.

`verify_timing_loopback` is also the rig **diagnostic**: run it with `'Testing',false` to characterise the real loop-back (pulse recovery, latency, jitter, clock drift, amplitude margin against the hard-coded 0.1 detection threshold), sweep `'PulseRate'` to find where a device starts dropping pulses, and use its `'Corrupt'` option to confirm those measurements actually respond to a known defect. Its default 8-sample pulse is too short to hold a dropout. Pass `'PulseWidth',0.005` to test pulses of a presentation's length: it then reports every dropout inside a pulse (count and longest), and fails if one is longer than the re-arm (see `find_timing_onsets` below). The reference rig's Focusrite drops out for exactly 24 samples — one 125 µs USB microframe at 192 kHz — about once in 12,000 pulses, mostly early in a fresh stream. The test's own detector keeps a lockout of 40% of the pulse period, which hides such a dropout from its spurious count; that is why the dropout report reads the trace directly.
- **Verbosity/logging:** code logs through `mabr.log.vprintf(level, [red], msg, ...)`, which is a **facade over `granary.printf`** — granary (`external/granary`) is the logger; `+mabr/+log` is the seam. The calling convention is unchanged, so all ~130 call sites are untouched: `mabr.log.vprintf(0,1,...)` still prints a critical message in red, an `MException` in place of the message still logs the stack, and the daily file is still `<repo>/.error_logs/error_log_<ddmmmyyyy>.txt`. Three things about it *are* different and all three are granary's:
  - **Two gates, not one.** `GVerbosity` (default 1) decides the command window; **`GLogVerbosity`** (default `Inf`) decides the file. Turning the console quiet no longer throws away the record that explains a failure. The cost is that a level-3 or level-4 message in a per-frame loop now pays for formatting and a file write — lower `GLogVerbosity` on a rig where that matters. MABR has exactly one level-3 call site and none in a hot loop, which is why the default is left as granary ships it.
  - **A message given no values is LITERAL text.** The old logger read every message as a printf format, so a runtime-built string (`me.message`, a Windows path) was mangled by its own `\` and `%`. This is the disagreement `mabr.log.StimgenLogSink` used to work around by forcing text through `'%s'`; the contracts now agree and it forwards straight through.
  - **An exception is one record**, carrying identifier, message, stack and nested causes, attributed to the catch site. The old logger recursed through the front door once per stack frame, which both timestamped each frame separately and made `dbstack` report the logger as the caller.

  **`mabr.log.configure`** is the one place granary is wired to this installation, and it is called by every process that logs — `MABR.m` at startup, and lazily from `vprintf` itself, which matters because granary's settings are per-MATLAB-session and the acquisition and compute workers are separate processes (without it a worker's messages would go to `<tempdir>/.error_logs`). It sets `LogRoot` = `mabr.Config.root` and `LogDirName` = `.error_logs` (so the path is exactly what MABR always wrote), `PrefGroup` = `MABR` (so an operator's `granary.setLogDir` override sits with every other MABR pref rather than in a group named after a dependency), and **`FacadeFiles`** = `{'vprintf.m','StimgenLogSink.m'}` — the one that bites. granary credits each line to the frame that raised it, found by skipping its own package plus any front door the host names; unnamed, MABR's two front doors would appear as the origin of every message they carry, at one fixed line, and the caller column would say nothing. `'vprintf.m'` is matched by filename, which also covers stimgen's own `+stimgen/+util/vprintf.m` so attribution passes through to the stimgen code that logged. `mabr.log.logFile` names the current file (flushed first), which is what a bug report attaches.

  stimgen's messages land in the same place: `mabr.ui.App` installs a `mabr.log.StimgenLogSink` (stimgen's `LogSink` host seam, via `stimgen.util.logSink`) at startup when the submodule is present, so stimgen forwards through `mabr.log.vprintf` instead of writing its own daily file under tempdir — one log per session, one console verbosity setting (both packages gate on the same `GVerbosity` global).

  Two direct `fprintf` users in `+mabr` are deliberately *not* routed here, because a line logger cannot do what they do: `mabr.analysis.Progress` overwrites its counter in place with backspaces, and `mabr.analysis.Session`'s `disp` overload must print when a user types the object's name whatever the verbosity is. `mabr.ui.TestRunner.guarded`'s `fprintf` is inside an `evalc` capture and is the test's own output, not a log message. The legacy unqualified `helpers/vprintf.m` — a second logger writing its own file, called by nothing — was removed with this change.
- **The wiki is not in this repo.** The user/developer wiki lives *only* in the separate GitHub wiki repository (`git clone https://github.com/dstolz/MABR.wiki.git`), which is what the app's Help ▸ MABR Wiki opens. A `wiki/` source folder used to be mirrored here; it drifted out of step with the published pages and was removed — edit the wiki clone and push it, and do not recreate a copy in this tree. Repo-side prose stays in `docs/`. Note wiki links inside a Markdown table need the pipe escaped (`[[Title\|Page]]`) or the cell splits and the link never forms.

## MATLAB conventions used here

- `+mabr/` is the **package namespace** — everything is `mabr.Thing` / `mabr.subpkg.Thing`. Subpackages: `+acq` (acquisition engine), `+compute` (the signal processing between the ring buffer and everything that looks at it, and the two optional workers that run it — see the compute-workers section), `+data` (data model + IO), `+stim` (stimulus adapter + advance criteria + custom presentation strategies), `+metrics` (small tested functions, plus `+metrics/+online` — the per-condition metrics the online analysis window plots, and the one struct they are all called with), `+ui` (GUI), `+log` (logger). `mabr.pool` is a top-level package function: the parallel pool MABR's workers run on, made the right size *before* the first worker launches (a pool cannot be resized once the acquisition loop is on it), from the compute-worker preference. **`mabr.shutdownPool`** is its counterpart: it takes the pool away again when the GUI closes (see the Settings menu), and declines to delete a *busy* one by the same `FevalQueue` test `mabr.pool` uses before resizing — by then MABR's own workers have been killed and waited for, so anything still running belongs to somebody else.
- `mabr.Config` is a plain **value** object (NOT a superclass) holding the streaming constants (`frameLength=1024`, `maxInputBufferLength=2^26`) and the runtime/error-log paths. Nothing inherits from it. `DACSampleRate` is the one thing on it that is not a constant: `mabr.Config(fs)` builds one at a rate other than the 192 kHz `DefaultDACSampleRate`, and the property is **immutable** — a Config is a value object half the toolbox keeps a copy of, so changing a rig's rate means building a new one and handing it out (`mabr.ui.App.applySampleRate`), never mutating one copy while the rest go on believing another clock. The rate itself is a *setting* and lives in `mabr.AudioSettings.SampleRate`; `AudioSettings.config()` is the single place it becomes a Config. **`ADCSampleRate` is derived, not chosen**: `mabr.metrics.extract_sweeps` windows the ring buffer with a colon *stride* and `finalize_run` resamples `1:df`, so the analysis rate can only ever be the DAC rate over a whole number. `decimationFor` picks the integer landing closest to `ADCTargetRate` (12 kHz) — so 192/96/48 kHz all give exactly 12 kHz while the 44.1 kHz family gives 11.025 kHz, an honest rate a stride can reach rather than a round one it cannot. `SupportedSampleRates` is what the dialog's picker offers, deliberately not a restriction (`validateSampleRate` accepts any positive rate at or above the analysis rate, since a box may run at one nobody listed).
- `mabr.ArtifactPolicy` is the other top-level value object: the artifact criterion (`none`/`voltage`/`rms`), its thresholds **in volts** (defaults ±100 mV peak, 30 mV RMS), and `Repeat`. `loadPrefs`/`savePrefs` persist the user's choice in MATLAB prefs (group `MABR`), so a rig keeps whatever suits its electrode chain; `toStruct`/`fromStruct` are the same fields as a plain struct, forgiving of a missing/invalid field the same way `loadPrefs` is, and back `mabr.ui.App`'s save/load **configuration** file (see GUI section) rather than the "last used" pref. `mabr.ui.App` edits one and hands it to the controller at Start **and on every later change** — the artifact controls are deliberately left live while a schedule runs (see `App.applyArtifacts`), since the criterion is only decided at finalization.
- `mabr.FilterPolicy` is the third top-level value object: the **display** filter chain, as three independent switches — high pass (10 Hz), low pass (3000 Hz), notch (60 Hz, 4 Hz wide) — plus a shared Butterworth order clamped to `[2 8]`. `design(Fs)` caches the `digitalFilter` chain in the object and `apply(x)` runs it zero-phase (`filtfilt`, column-wise) — so the realized response is |H|², corners at −6 dB, which is what `response(Fs)` reports and the dialog draws. `design` is also **memoized per MATLAB process** (`designMemo`, keyed bit-exactly on the switches, corners, clamped order and rate; `designCacheStats`/`clearDesignCache` for tests), because `designfilt` costs ~280 ms for the default three sections and every finalized block asks for the same chain twice — on the DSP worker (`Pipeline.finalize` → `Recording.designFilters`) and on the GUI thread (`Recording.withProcessed`). Unmemoized, that was most of the dead time between blocked runs and ~20 s at the end of a 54-condition intermixed run. A memoized chain is the one `designfilt` would have built (`verify_filters` Part F), and nothing mutates a design, so sharing it is safe. `apply` on an undesigned policy returns its input, the same opt-in rule `Recording` follows, and a signal too short to `filtfilt` passes through rather than throwing (a truncated sweep must not kill the live view). `loadPrefs`/`savePrefs` persist it in the same `MABR` pref group; `toStruct`/`fromStruct` (deliberately excluding the cached `Designs`, same as `sameSettings`) are the configuration-file counterpart. It is called *display* filtering advisedly: it decides what a plot or a metric is computed from and never touches `Recording.Data`, which is what `io` writes — so no setting here can reach a `.abr` file, and there is no wrong moment to change one.
- `mabr.AudioSettings` is the fourth top-level value object: the ASIO `Device` name, the `PlayerChannels`/`RecorderChannels` mapping that `mabr.stim.Schedule.renderSpec` and `mabr.acq.worker_loop`'s `prepare_device` have always accepted but the GUI never exposed a way to set, `MicChannel` — the input the calibration microphone is patched to, deliberately **separate** from `RecorderChannels(1)` because acquisition records an electrode where calibration records a mic, two patchings of one device and therefore two settings (only `mabr.stim.CalibrationAdapter` reads it; nothing about it can reach a `.abr`) — `Testing` — **Test Mode**, as everything the user sees now names it (see the Test Mode section below), moved here from the main window because it is meaningless without an opinion about which device it is overriding — and `StimulationOnly` (see below) — plus **`AmplifierGain`** (issue #6), the linear V/V gain of an external amplifier ahead of the recorder's signal input (default 1). `mabr.compute.Pipeline` divides the recorded signal by it in both the live step and finalization (`AcqController.AmplifierGain` → `Pipeline.configure`'s fifth argument, and `Cmd.Configure`'s `AmplifierGain` for the compute workers), so the live view, the artifact thresholds, the metrics, and `ADC.Data` in every `.abr` are volts **at the electrodes** — which means `ArtifactPolicy` thresholds are input-referred too once a gain is set. The ring buffer is deliberately left in converter units, so the timing channel, the loop-back self-test and `alignmentCheck` are unaffected. `recordingGain()` returns 1 in Test Mode (no amplifier in the path; `App.onStart` asks it that way), the dialog greys the field with the recorder mapping, and the gain applied is recorded as `Block.AmplifierGain` → `ABR_Data.ADC.AmplifierGain` (always written; `importLegacy` reads it back). `loadPrefs`/`savePrefs` persist all six in the same `MABR` pref group, so a rig keeps whatever mode, device, and wiring suit it across restarts; `toStruct`/`fromStruct` do the same for the configuration file. Unlike `ArtifactPolicy`/`FilterPolicy` it is a **config** control, not a live one — `mabr.ui.App` locks its Settings menu item for the duration of a schedule (see `configControls`), because the worker's `audioPlayerRecorder` is already open on whatever device (or lack of one) `Start` handed it, and `AcqController.start` re-verifies the timing loop-back (`verifyTimingLoop`) whenever `Schedule.Device`/`PlayerChannels`/`RecorderChannels` change between runs; `mabr.ui.App.ensureController` rebuilds the worker whenever `Audio.Testing` differs from the running controller's, the same way it always compared the old checkbox. **`SampleRate`** is the setting with the longest reach and the reason `config()` exists: it is the rate the ASIO device is opened at, and therefore also the rate every stimulus must already be rendered at (`StimulusSet` refuses any other) and the rate the ring buffer is clocked at. Committing a change to it is consequently not a device edit — `App.applyAudioSettings` rebuilds `app.Config` from it (`applySampleRate`), re-renders the bank at the new rate (`retuneStimuli`), and `ensureController` rebuilds the worker, because the controller captured its Config at construction and every rate it reasons with (the live decimation stride, the filter design rate, `finalize_run`'s resample, the `Session`'s stored rates) comes off that copy. `retuneStimuli` regenerates the bank from its own `Source` — `demoStimuli` rebuilds, a stimgen bank re-synthesizes *from parameters*, which is exactly why `fromStimgen` never takes a cached `Signal` — and where there is no source to regenerate from (a bank built live in the designer and never saved) it leaves the waveforms alone and says so, because silently resampling somebody's calibrated bank is a worse answer than asking for it again; `mabr.stim.Schedule`'s constructor then refuses to plan against the mismatch (`mabr:stim:Schedule:sampleRate`) and the bank label turns red, since `renderSpec` sends the *bank's* rate to the device while the controller decimates by the *Config's* — two clocks, not a rounding error. The analysis rate is **not** a second setting (see `mabr.Config`). Asking for a rate is not getting one, which is what `probeSampleRate` is for: it briefly opens a real device at *this object's* `SampleRate` and reports what the driver granted, a *determination* rather than a setting — and it opens the *same class* the worker would (an `audioDeviceWriter` under `StimulationOnly`), since probing full-duplex would fail on exactly the input-less hardware that mode exists for. `availableDevices` wraps `getAudioDevices(audioPlayerRecorder)` and never throws, since it feeds a settings dialog, not a start-up check.

  **`StimulationOnly`** is the fifth setting and the one that changes what MABR *is* for a run: playback and the timing pulse go out, and **nothing is recorded**. It exists for rigs where another system does the recording, or none does. `worker_loop`'s `prepare_device` opens an output-only **`audioDeviceWriter`** rather than an `audioPlayerRecorder` whose input is discarded — that is what lets the mode also run on hardware with **no input channels at all** — and `stream_block` skips `rb.writeFrame` while the device clock still paces the loop. Both play columns are still emitted: a timing pulse is as much an output as the signal, and something downstream may well be reading it. It is mutually exclusive with `Testing`, which opens no device at all and therefore wins everywhere; `AudioSettingsDialog` greys the `stimCheck` under `Testing` and `readControls` reconciles the pair, and under stimulation only it greys just the *input* half — the recorder channels and the mic — while device, player channels, and Test Device stay live. Unlike `Testing` (baked into the worker at `parfeval` time, so changing it forces an `ensureController` rebuild) this flag rides **per block in the render spec** (`Schedule.StimulationOnly` → `renderSpec`), which costs nothing because `prepare_device` rebuilds the device whenever the mode — like anything else it was built from — changes between runs (and keeps it, clocked, while nothing does). Client-side, `AcqController` drops the whole recording half: `start` skips `verifyTimingLoop` (there is no input to loop back to, so requiring one would make the mode unusable), `on_engine_state` never starts the live timer, and `on_block_completed` skips `finalize_run` entirely — **no `Block`, no `BlockReady`, no `.abr`**.

  What it does *not* drop is the record of what was played. `AcqController.log_stim_run` is the stimulation-only counterpart of `finalize_run`: one **`.stimlog`** per run (`mabr.data.io.writeStimLog`, same MAT-file-with-a-distinctive-extension convention as `.abr`/`.torg`/`.mabrcfg`, holding one `MABR_StimLog` struct), carrying every presentation in play order — stimulus index and ID, polarity, onset sample and time — plus the bank's parameters flattened exactly as a `.abr`'s `SIG` is, and the schedule settings behind them. Nothing is recorded, but *what was presented* is still the experimental record, and on a rig where another system does the recording it is the only thing that can align the two: the onsets are the rendered ones, and the same play matrix puts a timing pulse at each of them. The onsets come from `renderSpec`'s `ExpectedOnsets` (there is no input to recover them from) and are honest about early stops — `worker_loop` now reports how many play-matrix samples actually went out (a `'streamed'` message, sent *before* the `Completed` state so a `BlockCompleted` listener already has it; `Engine.LastStream`), so a run cut short by Advance/Abort writes the whole plan with the unreached presentations flagged `Presented = false` rather than a truncated one or a lie. `BlockSaved` fires for the file (the event means "a file was written"; the extension says which kind), and `Schedule.recordRun` is fed the presented counts so the plan's bookkeeping is as true here as for a recorded run. The schedule-advance tail runs as always, so the plan drives itself to `SchedComplete` exactly as it would with a recording attached. Covered by `tests/verify_stimulation_only.m`.

  **Test Mode** (`Testing`) is the other named mode on this object, and the property keeps its old name only because prefs and every `.mabrcfg` ever saved call it that. It opens no device at all; `worker_loop`'s `stream_block` instead copies each frame of the continuous stimulus **straight into the acquisition ring buffer** — the signal column *and* the timing column, so onset recovery runs over exactly the pulses the plan rendered rather than a substitute for them. That copy is the whole substance of the mode and the reason it is documented rather than left as a developer switch: because the samples at an onset are by construction the samples the plan put there, a Test Mode run checks the correspondence everything else rests on — plan, render, timing channel, ring buffer, onset recovery, and the pairing of the k-th sweep with the k-th presentation. `mabr.metrics.alignment_report` is the pure arithmetic half (expected onsets against recovered ones: a constant `Offset` is a cable, `Jitter` is the fault, `Extra` counts pulses the plan never rendered, and `Truncated` is an early stop rather than a defect; `NumJumps`/`JumpAt`/`JumpSize` say *how* the offset strayed — a step at one presentation is a gap, no steps with a large `Jitter` is a creep — because "drifting by up to 1023" once hid a single late audio frame), and `mabr.ui.AcqController.alignmentCheck` is the verdict — run after **every** recorded run, since a drifting offset is as much a fault on a rig as in loopback, with the sample-exact waveform comparison (`compare_waveforms`, tolerance 1e-3 against a ~1e-6 loopback dither) added only in Test Mode, where there is a right answer to compare against. The onset tolerance is the one thing that differs by mode: **0** samples in Test Mode (nothing is being measured, so one sample of drift is a defect), **50 µs** on a rig — deliberately `verify_timing_loopback`'s own `MaxJitter` line, so MABR and its rig diagnostic cannot disagree about whether a rig is healthy, and because a red warning that fires on every ordinary run is one the operator learns to ignore along with the run that genuinely is misaligned. On a rig the offset may also **step** by up to one USB microframe (125 µs, 24 samples at 192 kHz), give or take that jitter (`alignment_report`'s fifth argument, `stepTolerance`; 0 in Test Mode). The reference rig's Focusrite slips its output by exactly that now and then mid-stream, moving every later onset and its response together, so every sweep is still paired with its own presentation. Such a run was flagged MISALIGNED all the same; it is now aligned, its summary says where the latency stepped (`the latency stepped +24 samples (+0.12 ms) at presentation 42`), and `NumSteps` counts the steps. It still needs no spurious pulse, and the offset holding within the jitter tolerance on either side of each step, so a creep still counts. Any bigger step is still a fault — an underrun's audio frame, or the whole interval a spurious or missing pulse shifts the pairing by — and a misaligned verdict leads with the first such jump, not with a harmless step before it. A misaligned verdict leads with what the offset did and where (`offset jumped +1023 samples (+5.33 ms) at presentation 3258`), says whether the run ended early (so `3602 of 9216` is not read as lost pulses — it was a Stop), and names what the audio device reported: `worker_loop` counts the underruns and overruns `audioPlayerRecorder` returns each frame (samples, with the play-matrix sample each was reported at — approximate to a device buffer) into the `'streamed'` message → `Engine.LastStream` → `AcqController.deviceReport` → `alignment_report`'s optional fourth argument. An underrun plays silence and carries on, so nothing is lost and later presentations come out late by about that much; an overrun drops recorded input. They are *named* in a misaligned verdict and never used to make one — the onsets alone decide. It is announced from `emit_blocks` rather than from `assemble_blocks` where it is computed, so the verdict lands on the status line *after* the `BlockReady`/`BlockSaved` messages that would otherwise overwrite it; the ring is untouched in between, since nothing overwrites it until the next `Run`. The `AlignmentChecked` event carries the report and `LastAlignment` keeps it. A Test Mode run is otherwise a **full** run — blocks, metrics, viewers, `.abr` files — which is exactly the danger, so it is marked at every level: the Run panel banner (`TEST MODE (recording the stimulus, not a subject)`, outranking both PREVIEW and STIMULATION ONLY), `describe()`, `Block.TestMode`, and `ABR_Data.TestMode` written into every `.abr` (always, `false` for an ordinary run — a field that appeared only sometimes would leave offline code guessing, and the guess that a missing field means "real data" is the wrong way round). The dialog carries the explanation and a `mabr.ui.wikiLink` to the wiki's `Test-Mode` page beside the checkbox, and Help ▸ About Test Mode… opens the same page; `mabr.ui.wikiURL` is the one place the wiki address lives. Repo-side prose is `docs/Test-Mode.md`, which is also the source for that wiki page. Covered by `tests/verify_test_mode.m` — the copy, the report, the mark on blocks and files, and that the check can actually **fail** (it is re-run over deliberately corrupted onsets; a check that cannot fail is not a check).

  The stimulation-only mode also **re-labels the worker**. `mabr.acq.Engine.Role` (`'acquisition'` / `'stimulus'`, → `WorkerName`) names it in every startup message and log line, because a worker that records nothing is not an acquisition worker and the log saying otherwise is misleading in exactly the mode where the user most needs to be sure. `AcqController.workerRole(stimOnly)` is the one place the mapping lives; `App.ensureController` passes it at construction and `AcqController.start` calls `Engine.setRole` for each run, since one worker is reused across runs that may switch modes between them (`setRole` logs the change — "the worker" in a log must not silently be two different things). `worker_loop` says which device class it opened and tags a stimulation-only block as it streams.

- `mabr.ViewPolicy` is the fifth top-level value object, and the smallest: **which viewer windows open by themselves at Start** — one logical per window (`LivePlot`, `Analysis`, `TraceOrganizer`, `StimulusViewer`, `ProgressMonitor`, `PresentationOrder`, `Notes`), with `loadPrefs`/`savePrefs` in the same `MABR` pref group and `toStruct`/`fromStruct` for the configuration file. Its defaults are what MABR always did — the live view and the trace organizer, nothing else — because which windows a rig wants up while it acquires is a per-rig habit, and until it was a setting the operator paid two closes and two presses at every single Start. `names()`/`labels()` are the order the Settings submenu is built in (the toolbar's order, so the menu reads like the row of buttons it talks about), and `opens`/`setOpen` take a window by name and tolerate one this MABR does not have, since a configuration file may name a window a later version dropped. Two things are deliberately **not** expressible here, because they are rules about the run rather than preferences about the layout: the trace organizer additionally needs `Send blocks to trace organizer` (nothing would ever arrive in one opened with the transfer off), and a **stimulation-only** schedule opens the progress monitor alone whatever this says — there is no trace to plot and no metric to compute from. Covered by `tests/verify_view_prefs.m`.

## Architecture: parpool-worker acquisition engine (`+mabr/+acq/`)

The load-bearing subsystem. Acquisition runs on a **1-process parallel pool worker** launched once per session with `parfeval`, keeping the pool and `audioPlayerRecorder` warm. Control/state flow over **parallel queues**; recorded samples flow through **one** memory-mapped ring buffer. This replaces the legacy two-`matlab.exe` design (spawned via `system(...)`, Wmic PID checks, `info.mat`, `dac.wav` handoff, `mabr_com.dat` command/state memmap).

- `mabr.acq.Engine` (client, GUI process) — starts/keeps the pool warm, launches the worker, owns the read-only ring buffer, and turns worker messages into **events** (`StateChanged`/`BlockCompleted`/`WorkerError`) via a `DataQueue` `afterEach` callback. **No busy-waits.**
- `mabr.acq.worker_loop` (runs ON the worker) — owns the `audioPlayerRecorder`, **synthesizes the stimulus frame-by-frame** from the `mabr.stim.PlayPlan` the Prep message carries (`PlayPlan.range(i,hi)` per frame — the run's waveforms, onsets, stimulus indices and polarities, never a whole play matrix; see the stimulus-adapter section), writes recorded ch1/ch2 into the ring buffer, and polls a `PollableDataQueue` every frame for `Prep`/`Run`/`Pause`/`Stop`/`Kill`. `PlayPlan.fromSpec` is the one place it decides between a `Plan` and the explicit `PlayMatrix` a hand-built block (the timing self-test, the tests) still carries. A **TESTING loopback** mode (`Engine(cfg,true)`) runs the whole engine with no hardware.
- `mabr.acq.RingBuffer` — thin wrapper over the retained memmap surface: `ring_signal.dat` + `ring_timing.dat` (single, `maxInputBufferLength`) plus a small `ring_header.dat` write-head header. Worker writable, client read-only. **`prefault(lo,hi)`** reads one sample per 4 KiB page of both channels, and `worker_loop` calls it over the whole ring at start-up (~0.13 s warm) and over each run's range at `Prep`, between runs. The ring is *file*-backed and `writeFrame` covers one page per channel per frame, so a page gone cold had to be faulted in, from disk, by the frame loop itself: long rig runs showed one-frame underruns at whole-MiB spacings of ring written (29, 11, 2, 20 MiB), and short runs, which keep rewriting the first few MiB, never did. That is a hypothesis the next piece is there to confirm or refute on the rig.
- **The frame loop times itself.** `stream_block` records each frame's command poll, render, device call, ring write and whole iteration (a few `tic`/`toc`s against a 5.3 ms frame), and `summarize_frames` turns that into per-stage p50/p99/max plus the eight frames with the most *work* (everything but the device call, which is where the loop waits) and the ring sample each started at. It rides the `'streamed'` message as `timing` → `Engine.LastStream.timing`, and `log_block_report` logs it once per block: a detail line normally, and loud (level 1, with the slowest frames) when a frame's work came within half a frame of the budget or the device reported an xrun. Underruns and overruns are *logged after the block* rather than from inside the loop — a logged line costs a stack walk and a file write at exactly the moment the loop has no time to spare — each with its offset into its MiB of ring, so the log alone says whether the MiB pattern holds. Every block writes the ring from its start, so a play-matrix sample is also a ring position. A fresh worker's first block used to underrun on its first frames, which paid first-call setup: ring writes of 4–13 ms apiece against a 5.3 ms frame on the rig, and a first render of real waveforms near 3 ms, which the self-test's explicit-matrix block never reaches. Those costs are now paid where nothing streams. `prime_ring` writes three frames of zeros at worker start and resets the head; `prime_render` renders, and discards, a run's first frame and its first frame holding a presentation at every `Prep`. The block's first `range()` call rewinds the plan's cursor, so the discarded renders leave no trace. On the rig a fresh worker's first block now streams without an underrun: ring writes peak at 1.3 ms where they reached 13 ms, and a first run's first frames render in under 1 ms rather than about 3.
- Enums `mabr.acq.Cmd` (client→worker commands) and `mabr.acq.State` (worker→client state) travel as messages, not shared memory. `Cmd.Release` (+ `Engine.releaseDevice`) closes the audio device while keeping the worker and warm pool alive. It exists because the worker opens its `audioPlayerRecorder` on the first `Prep` and **keeps it**: `prepare_device` reuses the device while nothing it was built from has changed (its signature is the constructor plus every argument — mode, device, rate, channel maps) and rebuilds it only when something has, and between runs the main loop keeps it **clocked**, feeding it one frame of silence per iteration (`idle_frame`, input discarded, xruns tallied apart from any run's) and polling the queue without waiting. The next run therefore starts on the next frame of a stream already running, with the same round-trip latency as the last, instead of paying the driver's start-up on its first frame — measured at a quarter to half a second a run on the reference rig when every `Prep` built a new device — and without re-reading the shared preferences file a device construction does. One extra idle frame after each `Prep` absorbs what the Prep's own work cost the stream, so it is not reported as the run's first frame. After `IdleClockSeconds` (spec field, default 10 s) with nothing to do the stream is stopped (`release`, device kept) and the next run starts it again; a device that errors while idle is dropped and rebuilt at the next `Prep` rather than ending the worker. The `'streamed'` report carries `deviceOpens` and `idleFrames`, and `tests/verify_device_reuse.m` checks all of it by running a real (not Test Mode) worker over `mabrtest.FakeAudioDevice`, chosen through the spec's test-only `DeviceFactory` field. That is also why an ASIO device, which has exactly one owner, is still held while nothing is being acquired: **"controller idle" does not mean "device free"**. Without it, the first calibration after any acquisition could not open the device and the only remedy would be restarting MABR. The next `Prep` reopens it.
- **A failed command fails that command, not the worker.** `worker_loop` catches per command, reports the error, un-prepares the block, releases the audio device (a failed command leaves it in an unknown state, so its reuse signature and the idle clock go with it) and goes back to polling; only an error outside any command (the ring buffer failing to map) ends the loop. `Engine.isAlive()` asks the future whether the loop is still running — `isReady` cannot, since the command queue outlives the loop — and `App.ensureController` never reuses a controller whose worker has exited, which used to leave the next Start sending `Prep` to a queue nothing read. **Pool workers share the user's `matlabprefs.mat` with the GUI process**, and MATLAB's pref functions take no lock: opening the audio device reads it (the DSP toolbox's device lookup asks for `dsp`/`portaudioHostApi`), so a `setpref` in the GUI landing at a run boundary tore that read (`MATLAB:load:notBinaryFile`). `open_device` retries a `MATLAB:load:*` failure a few times, since the write takes milliseconds. Code that runs on a worker should not read prefs itself; pass what it needs in the command.
- Because commands are polled every frame, the engine can honor an **online advance criterion** — stopping a block early when a correlation threshold is met (the capability the legacy code documented it could not provide).

Sweep extraction moved to `+metrics`: `mabr.metrics.find_timing_onsets` (pure function on a timing vector) and `mabr.metrics.extract_sweeps` (explicit cursor state, reads the ring buffer, returns only the sweeps each call windowed; `state.epoch` moves when it starts over on a new block) — direct analogues of the legacy `abr.Runtime` methods. **The detector re-arms only once a pulse is over.** A timing pulse spans its whole *presentation* (5–8 ms), far longer than the 2 ms shadow. On hardware a pulse can drop below threshold for a moment in the middle: the reference rig's Focusrite outputs a 24-sample USB microframe of silence now and then. Once the shadow had passed, the far side of such a dropout was read as a new onset. That meant one sweep too many, and every later sweep paired with the wrong presentation. The MISALIGNED "spurious pulse" verdicts in rig logs were this (8 on 29 Sep alone). So a rising crossing is a new onset only after the channel has been below threshold for `mabr.Config.OnsetRearm` (0.5 ms, four microframes) — a lockout as long as the pulse, however long the pulse is. The flip side is that a gap between two presentations must be at least that long. `OnsetThreshold` (0.1), `OnsetShadow` (2 ms) and `OnsetRearm` are defined once, in `mabr.Config`. The live pipeline, finalization and the self-test all use them, because two readings of one timing channel that differ by a single onset attribute every later sweep differently. Replayed through the new rule, a 300 s rig recording with a real dropout gives exactly its 12,000 onsets, in one pass and in 6,002 live 50 ms slices; `verify_live_pipeline` Part F is the regression test. **The slice boundary between the two functions is load-bearing too.** Read on its own, a slice that begins inside a pulse reports an onset at its sample 1. One that begins just after a dropout reports the recovery as a crossing with nothing before it. Both are the middle of a pulse already counted. So `extract_sweeps` passes the samples before its slice as look-back (`find_timing_onsets`' `context`): at least one, and as far back as the re-arm looks. Nothing inside the look-back is reported, but it settles both questions. Without it a slice boundary landing more than the shadow into a pulse inflated the live sweep count and shifted every later sweep onto the wrong condition (measured at **56 sweeps for 48 presentations** — 17% — in `verify_stimulus_alignment` Part F, the regression test for that). The boundary only ever affected the live path, since `finalize_run` reads the whole block in one call; the dropout reached saved `.abr` files too. `mabr.metrics.error_band` and `mabr.metrics.t_quantile` are the live view's SD/SEM/CI band arithmetic and a toolbox-free Student-t inverse CDF, kept out of the UI because they are claims about data rather than drawing. `error_band` is two lines over **`mabr.metrics.band_from_stats`**, which takes the standard deviation and the sweep count instead of the sweeps — term for term the same arithmetic in the same order, so a view holding only a condition's statistics (the live view, once the DSP has run in another process) draws the same band, to the bit.

`mabr.acq.Engine.set_priority` sets a process's scheduling priority through .NET (`System.Diagnostics.Process.PriorityClass`) rather than the legacy `wmic` call: `wmic` is a deprecated Feature-on-Demand that Windows 11 24H2 and later no longer install by default, and it had been failing silently (caught, logged at level 1). The acquisition worker runs `high priority`; the compute workers below it (see the next section).

## Compute workers (`+mabr/+compute/`)

Every computation MABR makes from recorded samples while a schedule runs lives in **`mabr.compute.Pipeline`** — sweep extraction, the display filter chain, the artifact preview, the onset-contrast correlation, the per-condition running mean/SD/counts, and the finalization DSP (`finalize`: read the block, `resample`, split by stimulus, filter, judge — reading a full ring's onsets straight off the single samples, since `find_timing_onsets` compares a positive threshold against the smallest single at or above it and so needs no 512 MB double copy, and letting each channel go the moment it has been used; the resample itself is untouched, so saved samples are bit-identical) — lifted out of `AcqController`'s live tick and `finalize_run` so that **one object** can be stepped by a worker process or, with no worker, by the controller itself. A controller built without workers — which is what every verification script builds — is the in-process path *by construction*. The pipeline is **incremental and exact**, and a cycle costs the sweeps that arrived since the last one, never the run so far: `extract_sweeps` returns only the sweeps *this call* windowed (one indexed read per half) and keeps no sweeps itself; `Pipeline` filters and judges only those into the next columns of a **column-per-sweep cache preallocated for the planned run** (`Filt`, `[2L × capacity]`, filled in place); and the statistics are **running** — per condition a Welford mean and sum of squared deviations, and over every clean sweep the odd/even split-half sums the onset-contrast correlation is made of (`accumulate`, feeding `mabr.metrics.partition_corr_from_means`, which `partition_corr` shares). Late in a 330 s run that took a step from 33 ms (two thirds of the DSP worker's period — the old step appended rows to a column-major matrix, re-copied and transposed the whole raw cache, and re-averaged every sweep of every condition) to 0.6 ms, flat. `step` returns its last answer when nothing is new. Everything is updated **one sweep at a time, in sweep order**, and a lone new sweep is filtered as a pair with itself (a single column takes `filtfilt`'s vector path, which rounds ~1e-14 differently from any grouping of two or more): so a sweep's filtered samples and the statistics depend on the sweeps and never on where step boundaries fell, which is what keeps the DSP worker and this process bit-identical (`verify_live_pipeline` Part B holds one call, random slices and one sweep at a time equal). `configure` mid-run rewinds extraction (`nWindowed = 0`) on a chain or gain change — the sweeps are read back off the ring, which still holds the block — restarts it on a window change, and on an artifact-policy change re-judges the cache and replays it into the statistics. `columns()` hands out the `[2L × nSweeps]` matrix on request — a copy, in the cache's own orientation, which is also how a condition holds its sweeps (`ConditionStore.fromLive` takes `Columns`, and still takes a hand-built snapshot's row `Sweeps`), so nothing between the cache and a metric transposes the run; handed over as rows it was transposed there and straight back, each a full copy. `sweeps()` is the same with rows as sweeps. **Neither timer calls either**: the analysis snapshot is built when a window pulls it (`AcqController.liveSnapshot`), and the metrics worker asks only while some window has a job on it. `CopyCount` counts the copies handed out, the detector `StepCount` is for steps. `step` returns **sufficient statistics, never sweeps** — the latest sweep, `R`, the counts, and per condition the mean, SD and counts — because every band the live view draws is a function of `(mean, SD, n)`; `columns()` is there for the consumers that need the matrix. `mabr.compute.ConditionStore` and `mabr.compute.evaluateJobs` are the online-analysis table and its evaluation loop, lifted out of `MetricPlot` for the same reason.

Two optional workers run it, launched on the same parallel pool as the acquisition worker by **`mabr.compute.ComputeEngine`** (the client facade, shaped like `mabr.acq.Engine`) and both executing **`mabr.compute.compute_loop(root,queue,role)`** — one function, the `Engine.Role` idiom — with the same handshake / `PollableDataQueue` command / `DataQueue` state-and-error protocol as `worker_loop`:

- **The DSP worker** (`role = 'dsp'`, `below normal` priority) steps its pipeline over the acquisition ring buffer every `LivePeriod` (50 ms) while a run is in progress and publishes the statistics to `mabr.compute.LiveBuffer`; at the end of a run it performs the finalization DSP on `Cmd.Finalize` and replies with a `'finalized'` message carrying plain `parts`.
- **The metrics worker** (`role = 'metrics'`, `idle` priority, launched **lazily** by the first analysis window) steps its *own* pipeline over the same ring every `MetricPeriod` — the online metrics need the sweep matrix, which the live surface deliberately does not carry — keeps the session's condition table (`Cmd.AddCondition` per finalized block), evaluates the requested metrics (`evaluateJobs`, time-boxed between conditions, **live conditions first** so a budget spent on the finished backlog cannot leave the changing ones unreached, and **remembering a finished condition's value** across cycles in a memo keyed by the condition's key and counts, the job's `Sig` — a catalog `Key`, or a custom slot and the generation of its function — and window; a finished condition changes only when a block is merged into it, which changes its counts, and metrics are pure by contract, so a remembered value is the value — re-evaluating every finished condition every cycle made each cycle cost the session so far; and **not evaluating a live condition at all for a job whose `WhileAcquiring` is false**, which `mabr.metrics.online.catalog` sets for the sweep correlation alone: it compares every pair of sweeps, and a live condition is evaluated afresh every cycle, so it cost the square of the run — 0.9 s a cycle at 5,000 sweeps of one condition, 2.8 s at 9,000 — for a number the finished block gives once) and splits the run in progress into live conditions only while some window has a job on it, since that copies every sweep of the run (it outlives the window that launched it) and publishes to `mabr.compute.MetricBuffer`. **This is the process user-supplied metric functions run in**, so a hung one costs its window and nothing else: the client watchdog cancels and relaunches the worker once, drops every custom metric (there is no telling which hung), flags their slots, and a window whose slot is flagged evaluates nothing in-process — a hang in the GUI is the one outcome the third worker exists to prevent.

**A run reaches the workers at its Acquire, not when it is prepared.** `begin_current_run` holds the `RunStart` in `AcqController.PendingRunStart` and `on_engine_state` sends it on the run's first `Acquire` (a Resume reports Acquire again; the one-shot is what keeps that from restarting a run), before the state change so any listener sees the workers already on it. The acquisition worker resets the ring only when a run starts streaming, and a worker windows whatever the ring holds: told earlier, the DSP worker's first cycle windowed the *previous* run's sweeps and published them under the new run's id, the first live tick saw a complete run, and the advance criterion stopped the new run one frame in with nothing recorded — 8 of 143 blocks on one rig day, each a condition silently missing from the session. `verify_compute_worker` Part H checks the order directly, since the race itself seldom fires in loopback.

**Nor does the first run start before the DSP worker has designed its chain.** A fresh worker's first `Configure` runs `designfilt` in a process that never has (3–6 s measured on the reference machine; `FilterPolicy`'s memo is per process), and `hasDSP()` is true from the handshake, so a run started meanwhile had a live view with nothing in it and an advance criterion with nothing to judge — and past 5 s the watchdog would take the busy worker for a wedged one and relaunch it into the same cost. `AcqController.waitUntilReady` therefore ends with `ComputeEngine.waitConfigured` (bounded at 30 s, never fatal), which returns once the worker reports anything but `Idle` — it does only after acting on a Configure. The first Start of a session begins streaming that much later, under the startup dialog, whose milestone says why. On a cold pool the overlap used to leave `verify_compute_worker` Part B's worker the last ~1.6 s of a 4 s run, and one slow first step left it with no publish at all; Part B now asserts the worker is configured before the run starts.

Neither worker talks to the other; both derive from the same ring bytes under the same `Cmd.Configure` (rate, window, both policies as their `toStruct` forms — re-sent from `set.Filters`/`set.Artifacts`), so their verdicts agree by construction. **The rate is not optional**: a compute worker needs it for the decimation stride and the filter design, so it builds `mabr.Config(fs)` from `Configure` and steps nothing before one arrives. `tests/verify_compute_worker.m` asserts the worker's statistics and finalization are **bit-identical** to the in-process pipeline over the same ring, and that a controller served by the DSP worker never steps its own (`Pipeline.StepCount` stays at 0).

The bulk traffic is memory-mapped, as the ring buffer is, through **`mabr.compute.PublishBuffer`** — one base class holding the discipline: every payload field exists in two halves (encoded in the field's shape, `[2m x n]` or `[m x 2]`, never a third dimension); the writer fills the idle half, flips `Half`, bumps `Seq`, in that order; a reader reads `Seq`, the half, `Seq` again, and keeps its previous payload if `Seq` moved. The `Seq` re-check is the correctness guarantee, the halves the fast path; readers slice rows and never read the file (~17 MB live, ~30 KB metrics). `LiveBuffer` (DSP → client), `MetricBuffer` (metrics → client) and `RequestBuffer` (client → both: cadences and the per-slot job table; a custom metric's function handle travels over the queue instead, since it cannot live in a memory map) supply the layouts; `Config` supplies the paths (`compute_*.dat` beside the ring files) and the sizes (`MaxComputeSamples`/`Conditions`/`Jobs` — a window or run over them is refused, never truncated). A worker publishes on **every** cycle, sweeps or none (`Pipeline.emptyStats`), so a `Seq` that has not moved for far longer than the cadence is the one thing a wedged worker and a live one do not share. `LiveBuffer.read()` returns exactly `Pipeline.step()`'s struct, which is what lets the controller's tick be the same code either way.

**Degradation is per role, and stale is not absent.** `ComputeEngine.hasDSP()`/`hasMetrics()` say whether each worker is up — never launched, not yet handshaken, or declared dead by the watchdog — and every consumer checks before it asks: a controller without a DSP worker steps its own pipeline (a worker that dies mid-run is covered on the next tick, since the in-process pipeline follows every run too), an analysis window without a slot evaluates in-process. A consumer that merely finds no new publish keeps its last values with a note, because computing in-process the moment a worker is slow would reproduce the overload the workers exist to remove. The watchdog rides the consumers' own polls (no timers): silence is judged only *after* reading the sequence word — a run's preparation can take seconds between `runStart` and the first tick while the worker heartbeats throughout. A wedged worker is `cancel`-ed and relaunched **once**, with what it missed replayed at its handshake (the last `Configure`, the run in progress, the conditions, the custom metrics); if the fresh handshake never arrives the role is written off for the session and the status line says so. The pool is never deleted or recreated mid-acquisition. The workers are a **preference** (`MABR`/`ComputeWorker`, default on; `Settings ▸ Background compute workers`, a `configControls` entry) because they decide the pool's size, which `App.ensureController` sets through `mabr.pool(3 or 1)` before building a controller; a pool that cannot be resized (busy, or the profile too small) costs the workers for the session, never the acquisition. Killing a worker frees its *slot*, not the pool — MABR's workers never return on their own, so `delete`-ing an `Engine`/`ComputeEngine` sends `Kill`, waits for the future to finish, and leaves one to three idle worker processes resident for as long as the MATLAB session lasts. Closing the GUI is where that stops being wanted, which is what `mabr.shutdownPool` and the `Shut down parallel pool on exit` preference are for.

Finalization on the DSP worker is **asynchronous**: `on_block_completed` sends `Finalize` and returns with `ProgState` in `BlockComplete`; the reply (`on_finalized` → `conclude_run`) or a single-shot timeout (`FinalizeTimeout` plus a per-sample allowance → finalize here from the ring, which nothing overwrites until the next `Run`, and report the worker as stalled) moves the plan on. The GUI stays responsive across the block boundary. **`conclude_run`** is the tail of every recorded run, whichever process did its DSP, and its order is the point: it *computes* the alignment verdict (`alignment_compute` — it reads the ring, `CurOnsets`/`CurSeq`/`CurPol` and the device's report, all of which the next run replaces), *credits* the run from the finalization output alone (`credit_run`: `recordRun`, and `appendMakeup` for what the artifact policy rejected), and then — unless that was the last run of the plan or a halt — **begins the next run before this run's Blocks are built**, so the rig streams the next run while this one is assembled, saved and handed to the viewers (with the organizer, analysis windows and files, the part of the gap that grew over a session). `assemble_blocks` reads a snapshot of the run (`run_context`), never the `Cur*` fields, and the verdict is *announced* (`alignment_announce`) after the run's `BlockReady`/`BlockSaved`, as before. The last run and a halt keep the old order, so `ScheduleComplete` still means every Block is built and every file written. The consequence for listeners: run *k*'s `BlockReady` now arrives after run *k+1*'s `PrepBlock` (`verify_online_advance` Part D). The listeners keep that burst cheap: the trace organizer draws only the new trace, an analysis window merges and draws at its next tick, and `App.onBlockSaved` sets the status line without forcing a repaint (`setStatus(txt,false)` — a full `drawnow` per saved file, ~75 ms each on the rig, flushed every figure and callback queue once per condition). `assemble_blocks` is the half only the GUI process can do — `Recording`/`Block` assembly, polarity, notes, `writeABR`, then `computeMetrics` (after the file and inside its own `try`: a metric must never cost a block its `.abr`, and it used to be able to — `mean_pairwise_corr` built the whole nSweeps × nSweeps `corrcoef` matrix, 435 MB at 7,374 sweeps, and an out-of-memory there lost the rest of the run; it now works a ~32 MB tile at a time, the same number to rounding), `Session.addBlock` — and it adopts each part's filtered trace through **`Recording.withProcessed`**, so no consumer of a `Block` ever filters the trace again.

## Core data model (`+mabr/+data/`)

- `mabr.data.Recording` (value type) — one channel's `SampleRate` + `Data` + `SweepOnsets`/`SweepLength`, with `SweepData`/`SweepMean`/`noisePower`/`SNR` ported from the old `abr.Buffer` but **cycle-free** (no `ABRobj` back-reference; decimation passed explicitly). Filtering is **explicit** and lives in a `mabr.FilterPolicy` held in `Filters` — the same object the GUI edits and the live view applies, so what the operator watches and what a `Block` reports come off one set of corners. `designFilters()` designs it at the Recording's own `SampleRate`, after which it is applied consistently in segmentation (the legacy designed but never applied it); before that call `ProcessedData` returns raw `Data`. `ProcessedData` is **cached**: `designFilters()` runs the chain once into a private `Processed` (or `withProcessed(x,policy)` installs a trace filtered elsewhere — the DSP worker's — after checking the policy asks for the same chain), and `set.Data`/`set.Filters` clear it. Every descriptive accessor (`SweepData`, `CleanSweepData`, `NumSweeps`, `SweepMean`, `noisePower`/`SNR`/`RMS`) starts from `ProcessedData`, and without the cache each of them ran `filtfilt` over the whole trace again — one finalized block cost five or six passes between `finalize_run`, `Block.computeMetrics` and the viewers. `to_struct` and `io` never see it. `Data` is never filtered in place and `io` saves `Data`, so a `.abr` file is always the raw trace. `IsArtifact` flags rejected sweeps (aligned with `SweepOnsets`, **not** with `SweepData` — map through the `ValidSweeps` mask, since a truncated run's last window is dropped from `SweepData`); flagged sweeps are excluded from everything descriptive — `CleanSweepData` is the basis of `SweepMean`, `noisePower`/`SNR`/`RMS` and `Block.computeMetrics`, while `SweepData` still returns every sweep — but never removed from `Data`. With *every* sweep flagged, `SweepMean` is all-NaN (there is no mean to report) and viewers skip it.
- `mabr.data.Block` (value) — one condition's result: stimulus metadata + the recorded `Recording` + computed metrics + start time + `SweepPolarity` (+1/-1 per sweep, aligned with `ADC.SweepOnsets`).
- `mabr.data.Session` (handle) — subject/device/rate config + block queue + array of `Block` results.
- `mabr.data.SessionNotes` (handle) — the **rig notebook**: a store of timestamped free-text notes ("ear plug slipped", "impedance 3.2 k") that the operator writes *while it is happening*, and that is then saved with the data. It is the data half of the notes component; `mabr.ui.Notes` is the view, and any number of views can be open on one store because every change fires `NotesChanged` and each view redraws from the store rather than its own copy. What a note is stamped with is the point: a wall clock alone does not say *where in an experiment* something happened, so a note committed during a run carries the run and the sweep count too — `[R02 S0128 09:17:05] ear plug slipped`, against `[09:03:11] impedance 3.2k` for one taken while nothing is acquiring (there is no run to name, and inventing one would be worse than saying the time). The acquisition context comes from `ContextFcn`, which `mabr.ui.App` points at `mabr.ui.AcqController.noteContext`; that method leaves `Run`/`Sweep` NaN unless a run is actually under way, and `Sweep` is the count within the *current run*, the same number the Run panel shows. `ContextFcn` is called inside a `try` — a stale controller costs a note its run number, not the note. Notes are saved **whole into every file** rather than split across them (`ABR_Data.Notes` via `Block.Notes`, `MABR_StimLog.Notes`, `View.Notes` in a `.torg`), so no file depends on another to be read and a session recovered from one surviving `.abr` still has its notebook. `JournalFile` is the other half of that: every commit rewrites the entire log to it as **plain text**, deliberately *not* a MAT-file like the rest of MABR's outputs, because the whole reason the journal exists is to survive a crash and a format needing MATLAB to read is the wrong one for that (`fromFile` reads one back). `setFromLog` is what the view's editable mode writes back — it re-parses `[stamp] text` line by line and keeps each surviving line's original record (time, run, sweep) intact, claiming each old note at most once so two notes committed in the same second cannot collapse onto one. `Session.Notes` holds the store (never as a property default — a handle default is evaluated once at class load and would be the *same* store in every `Session`) and `Session.noteRecord()` is the safe accessor the writers use.
- `mabr.data.io` — save/load. `writeABR` emits an offline-compatible `ABR_Data` struct and matching filename; `importLegacy` reads old `ABR_Data` structs (incl. sigProp-style SIG) into the new model. `writeStimLog`/`buildStimLog` emit the `.stimlog` a stimulation-only run produces in place of a `.abr` (see `AudioSettings.StimulationOnly`); both filename builders share one `subjectToken`, so a session's files sort together whatever it wrote.

## Stimulus adapter (`+mabr/+stim/`)

MABR **does not** generate signals or calibrate — an external package supplies precomputed, calibrated waveforms as a plain struct array where **each entry is one presentation**: `signal` (required), `ID` (required), optional `SampleRate`/`Repetitions`/`Timing`/`alternatePolarity`/`informativeParams`, and any number of passthrough fields. `mabr.stim.StimulusSet` wraps and validates it; `mabr.stim.demoStimuli` is a built-in tone-pip bank for testing only.

`informativeParams` is the one addition the stimgen work forced. Left absent, MABR infers the list — every numeric scalar extra — which is right for a hand-built bank whose only extras *are* its parameters. A generator emits far more than that (a stimgen `Tone` variant carries `Duration`, `WindowDuration`, `OnsetPhase`), and every name on that list becomes a **grouping dimension** in the offline pipeline, so a source that knows which of its parameters actually vary now says so instead of letting MABR guess from types. `StimulusSet.paramTable(idx)` is the read side of that list: the parameters a set of entries shares, their values as an `[nStim x nP]` matrix, which of them vary across *that* subset, and the units (`kHz`/`dB` for the two the toolbox fixes by name end-to-end, `''` for everything else rather than a guess). Pass a **run's** stimulus indices, not the bank's — a bank varying Frequency and Level holds one condition per blocked run and neither varies within it, and the question a live view asks is about the run. Only numeric scalars are tabulated: it is a table of dimensions to sort, group, and shade by, and a name with no order over its values cannot do any of those; the full metadata of an entry is still `meta()`, which now shares one `informativeNames` rule with it. `StimulusSet` also carries a `Source` struct (`Kind`/`File`/`Calibration`/`Generated`) and an `isCalibrated()` — provenance, not contract: nothing in acquisition reads them, but a calibrated bank and the demo bank are otherwise indistinguishable once they are struct arrays, and that is exactly the confusion worth being unable to have.

**stimgen is the suggested source** (`external/stimgen`, optional — see `mabr.stim.stimgenAvailable`). `mabr.stim.fromStimgen` converts a `.spl` bank file, a live `stimgen.StimPlayer`, a `StimPlay`, or a bare `StimType` into a `StimulusSet`. Three things about it are load-bearing:

- **One stimgen *variant* is one MABR entry.** A vectorized property expands into variant combinations — a `Tone` with `Frequency=[8000 16000]`, `SoundLevel=[30 60]` is four variants — which is already MABR's unit. The conversion flattens `StimPlayer.StimPlayObjs` → `StimPlay.StimObj` → variants and reinterprets nothing.
- **Regenerated, not resampled.** `StimType.Fs` defaults to 97656.25 (a TDT rate); MABR sets `Fs = Config.DACSampleRate` on a `copy()` and calls `update_signal()`, so each variant is synthesized natively at 192 kHz. This is why the importer takes *parameters* and never a bank's cached `Signal`.
- **`VariantReselectOnUpdate` must be forced false first.** With it at its default, every `selected_value()` call *outside* an update cycle silently re-runs the selector and advances the active index — so metadata read back after `set_variant_index` describes a *different* variant than the `Signal` just generated under it, and an 8 kHz waveform gets saved labelled 16 kHz. The signal is always right; it is the description that drifts. `verify_stimgen_import` FFTs each waveform against its own label to catch exactly this.

**Polarity is carried across** where a stimulus asks for it: a stimgen `Tone` with `Polarity = 0` ("+/- Alternate") is generated positive and reports `alternates_polarity()` true, so `fromStimgen` imports it with `alternatePolarity` set and `Schedule` splits its repetitions between the signs — unlike `OnsetPhase = [0 180]`, which is two variants and so twice the presentations. A `ClickTrain` offers both kinds: `Polarity = 2` ("+/- Alternate presentations") imports the same way — the one a single click needs — while `Polarity = 0` alternates click by click inside the train and reports false. The call is guarded on `ismethod` for older submodule pins. Covered by `verify_stimgen_import` part 8.

Deliberately dropped on import: `StimPlay.ISI`, `StimPlayer.ISI`, `SelectionType`, `StimOrder`. MABR owns presentation and `mabr.stim.Schedule` decides it. `Schedule` does now have a `[min max]` jitter range of its own (`ISIMode`/`ISIRange`), so stimgen's ISI *could* be carried across — it still is not, because the timing is the operator's setting for this session and adopting a bank must not silently retime a schedule already configured around it. `Reps` survives as the starting repetition count **unless the host hid the field**: `fromStimgen`'s `repsHidden` reads a live player's `ControlVisibility.Reps`, and a hidden control means the number is `StimPlay`'s default (20) rather than anyone's choice — 20 sweeps is not an ABR — so it imports as *no opinion* and `Schedule.startingRepetitions` supplies 512. A `.spl` read from disk carries no such tell and is taken at its word. Two unit reconciliations happen in one place (`buildEntry`): stimgen's `SoundLevel` → `Level`, and `Frequency` Hz → kHz, because `mabr.data.io.buildFilename` reads both by name and unit to match the offline regex.

**An uncalibrated stimgen bank is the sharp edge.** `apply_calibration` is a no-op with no calibration loaded, so `SoundLevel` never reaches the amplitude and a 30/60/90 dB series would be three *identical* stimuli. Absolute SPL is unknowable without a measurement, but the spacing is not — dB is a ratio — so `fromStimgen`'s `relativeLevels` pass rescales an **entirely** uncalibrated bank relative to its own loudest entry (`10^(ΔdB/20)`, recorded per entry as `LevelScale`, which passes through to the `.abr`). The reference is the top of the bank, never a fixed dB, so the loudest waveform is left exactly as stimgen normalized it and this can only ever *attenuate* — no bank acquires a clipping risk it did not already have. A **partly** calibrated bank is left untouched: half its volts are real and there is no common reference to be relative to. Either way `Calibrated` stays false and `App` warns rather than refuses — an amber bank label, and a `uialert` on adopt naming which of the two cases it is (`warnUncalibratedLevels` branches on the presence of `LevelScale`). Covered by `verify_stimgen_import`, which asserts a 30 and a 60 dB entry come back exactly 30 dB apart.

Also: `stimgen.StimCalibration.loadobj` used to throw (it assigned the read-only `Engine.MicSensitivity`; fixed at the current submodule pin — it restores through `Engine.restore` now), and `StimType.fromStruct` calls it unconditionally — so `fromStimgen`'s `readBank` restores the stimulus *without* its calibration and reattaches separately in a `try`. The split is kept because the isolation, not that one bug, is the point: on any `loadobj` failure (an older submodule checkout included) a bank whose calibration cannot be revived imports and reports itself uncalibrated rather than becoming unloadable. The restore runs with `ApplyCalibration` forced **false**, and the bank's own value is put back *last*: `fromStruct` assigns `Fs` and the user properties onto a live object, every assignment regenerates the signal through `StimType`'s `PostSet` listeners, and until the calibration is reattached that is against the default, empty `StimCalibration` — which made stimgen print its red level-0 `No calibration data available for stim` while importing a **correctly calibrated** bank, word for word the warning a genuinely uncalibrated one earns. The waveforms were never wrong (every variant is regenerated afterwards with the calibration attached); the log was, and an operator could not tell the two cases apart. So the state is now *said* rather than inferred from silence: `fromStimgen`'s summary line ends `calibrated (measured …)` / `PARTLY calibrated (n of m)` / `UNCALIBRATED`, and `StimulusSet.describeSource` reads `(calibrated)` instead of leaving it to the absence of `(uncalibrated)` — its second output adds when the calibration was measured (`StimulusSet.calibrationTime`), which is what the bank label's tooltip shows. `verify_stimgen_import` part 6c hears the warning at stimgen's `LogSink` seam and asserts it is absent for a calibrated bank *and present* for an uncalibrated one, alongside the volts themselves (the lookup table's, and sample-identical to the live stimulus). stimgen's own restore paths (`StimType.fromStruct`, which SpotCheck loads through, and `StimPlayer.load_bank`, the designer's) had the same ordering and are bracketed the same way upstream; `readBank` keeps its own bracket regardless, since the submodule may be checked out at a commit from before that, and part 6c *reports* which it found rather than asserting it. `StimType.fromStruct` also does not restore `SoundLevel`/`Duration`/`WindowDuration`/`WindowFcn` (stimgen's own `load_bank` assigns those itself), so `readBank` does too — without it a bank comes back silently at class defaults, 60 dB and 100 ms. One refusal is new with the current pin: stimgen's `apply_calibration` now asserts a **filter-type** calibration is run at the rate its FIR was designed at, and `fromStimgen` forces `Config.DACSampleRate` — so a bank whose filter calibration was measured at another rate refuses to import. `fromStimgen` translates that (`mabr:stim:fromStimgen:calibrationRate`) into what a MABR user can do: recalibrate through **Settings ▸ Calibration…** (which measures at the DAC rate) or redesign the filter with `design_filter(...,SampleRate=192000)`; the tone/click LUTs are in Hz and volts and need no re-measuring.

**Upcoming conditions can be switched off mid-schedule** (`Schedule.setEnabled`, `isEnabled`, `upcomingCounts`, `Disabled`, `Skipped`; the GUI is `mabr.ui.PresentationOrder`'s table). The mask is applied to a run only when `advance()` makes it current — *before* the controller renders it — by removing the disabled stimuli's presentations and polarities from it, and a run left empty is removed from the plan. Never earlier and never to the current run, because the run rendered and the `runSequence` `finalize_run` pairs its onsets with must be the same thing; so a change applies from the next run (for a one-run intermixed plan, only to make-up/repeat runs appended after it), and a condition can be switched back on until its run is reached. `isComplete()` answers with the mask (`nextRun`), so `conclude_run`'s `goOn` does not begin a run that `advance()` would then drop — `ScheduleComplete` still arrives after the last run's Blocks. A disabled stimulus is not made up (`appendMakeup`), a dropped make-up run's presentations are refunded to the budget, and `repeatRun` re-enables its stimulus. `build()`/`reset()` clear the mask and restore the runs `build()` produced (`BuiltRuns`, since the mask edits `Runs` in place). The progress monitor's totals shrink when a run is reached rather than when the box is cleared.

**MABR owns presentation, the stimulus package does not.** `mabr.stim.Schedule` turns a `StimulusSet` plus three GUI-chosen settings — `ISI` (s, onset-to-onset), `Repetitions` (per entry), and `Strategy` — into ordered *runs*, and renders each into a **`mabr.stim.PlayPlan`** rather than a play matrix: the waveforms of the stimuli the run presents, the onset list, and the stimulus index and polarity at each onset. The plan is what `Engine.prep` sends and what `worker_loop` renders a frame at a time (`PlayPlan.range(i0,i1)`), performing the same summation in the same presentation order a whole-matrix render did — so overlapping presentations are still summed, and `PlayPlan.matrix()` (tests, and `fromMatrix` for hand-built blocks such as `verifyTimingLoop`'s) is bit-identical to what `renderSpec` used to allocate. A run therefore costs the GUI process the size of its bank, not its duration, and the Prep message the same, instead of a 512 MB `[N x 2]` for a run filling the ring. The ring-buffer cap on the *recording* still stands (`mabr:stim:Schedule:tooLong`, checked before anything is built) — the worker records into a true ring that keeps only its newest lap and `finalize_run` reads it whole — so a run longer than the ring is the remaining step, not this one. Covered by `tests/verify_play_plan.m`. Strategies are named for the acquisition designs they implement: `conventional`, `conventional-shuffled` (one run per stimulus) and `interleaved`, `interleaved-random`, `shuffled` (one run, **intermixed**). `interleaved` cycles through the bank, every cycle in the same order; `interleaved-random` shuffles each cycle, and `shuffled` shuffles the whole multiset with no cycles. All five are permutations of a fixed multiset — each entry gets exactly its repetition count (`interleaved-random`'s randomness is the order within a cycle, not what is presented). **`conventional` and `interleaved` take their order from the setting** (`Schedule.OrderedStrategies`, `strategyTakesOrder`) — the order the runs play in for one, the order every cycle walks the bank in for the other: `Schedule.OrderBy` names the stimulus parameter(s) the bank is sorted by, most significant first, and `OrderDirection` the way each goes — `ascending`, `descending`, or `listed` (grouped by value, the groups in the order the bank first lists them, which is what keeps a frequency order that was chosen on purpose, e.g. listed non-adjacently so successive presentations excite different places on the cochlea). Both are cellstr rows that take a char for the one-parameter case, `{}` being the bank's own order, and it is a *list* because it takes two parameters to say the ordinary threshold series — `{'Frequency','Level'}` / `{'listed','descending'}`, one frequency at a time and loudest first within it; one name can only ever make its parameter the outer loop. The two interleaved designs that used to be strategies of their own are now just orders: the **ramp** (one frequency at a time, levels ascending) is `{'Frequency','Level'}` / `{'listed','ascending'}`, the **plateau** (every frequency at each level) is `'Level'` / `'ascending'`. `parameterOrder` is one `sortrows` over a column per parameter with the bank index last, which makes the sort stable in every direction: ties keep bank order, descending included, so reversing a direction reverses that parameter and nothing else. A parameter the bank does not vary is **skipped, never refused** (`orderKeys`), and without handing its direction to the next — the setting outlives the bank it was chosen for, and a configuration naming `Level` must still load against a bank without one — whereas a direction that is not one of the three is refused on assignment (`mabr:stim:Schedule:orderDirection`), since a misspelt one read as ascending would present a session backwards. The shuffled strategies and `custom` do not read the pair. `orderLabel()` is the order *in force* in words, and `strategyLabel()` carries it into a `.stimlog` (`conventional (Frequency as listed, Level descending)`, `interleaved (Level ascending)`). Retired names are translated on assignment by `Schedule.canonicalStrategy` (`set.Strategy`, and `App.applyConfiguration` before it matches the dropdown), because `.mabrcfg` files and the `LastSession` pref carry them: `blocked`, `shuffled-blocks`, `shuffled-cycles` from before the strategies were named for their designs, and `interleaved-ramp` / `interleaved-plateau`, which become `interleaved` **and set the order they stood for** (`LegacyOrders`, read through `legacyOrder` — by the setter, so a script naming one presents what it always did, and by `applyConfiguration`, where it replaces the order saved beside it, since that one was the conventional run order and the old interleaved strategies never read it). `interleaved` itself is the design's original name, whose cycles followed the bank's own order — what it means again with no `OrderBy`. Covered by `tests/verify_strategies.m`. A seventh, **`custom`**, hands the ordering to the user's own function — see the custom-strategy section below. An entry flagged `alternatePolarity` has its successive presentations multiplied by `+1,-1,+1,…` — the repetition count is *split* between polarities, never doubled, and the polarity travels with the presentation through shuffling. `renderSpec` emits `StimulusIndex` — the stimulus behind each onset — plus `Polarity`, the sign applied there — and refuses runs exceeding `maxInputBufferLength` (`mabr:stim:Schedule:tooLong`). The plan's timing channel (one unit pulse over each presentation, or the entry's own `Timing`) is synthesized because sweep extraction depends on it. A run is bracketed in silence: **`SilencePad` (0.1 s) in front**, which only has to clear the first sweep's baseline window, and at the end at least that — or, once `AcqController.begin_current_run` has set `ResponseWindow` from its analysis `Window`, at least `ResponseWindow + LatencyAllowance` (50 ms, twice the reference rig's round trip), so a completed run's last response reaches the recording rather than being dropped as a truncated window (`trailPad`, `padSeconds`). The lead-in was 0.25 s at both ends, played on every run, to keep a device's start-up off the run; that job is now the worker's (`warm_up`: a device not already streaming — just opened, or stopped after an idle spell — is started on 0.25 s of unrecorded silence before `stream_block`), and a device kept clocked between runs needs none of it. Covered by `verify_play_plan` Part F.

The ISI is either of two settings, chosen by `ISIMode`: the scalar `ISI` (`'fixed'`, onsets on a strict grid) or a uniform draw per interval from `ISIRange` = `[min max]` s (`'random'`, so the presentation rate carries no periodicity of its own). Both are always held, and the mode picks between them, so turning randomization off and on cannot lose the range — the GUI's checkbox *is* `ISIMode`. `renderSpec` accumulates one interval per presentation rather than multiplying a period, drawing from the schedule's own `RandStream`, so rendering never perturbs the global `rng` and a `Seed` fixes a plan's timing along with its order. Two dependent properties say which number to reason with: **`MinISI`** (the shortest interval that can occur) is what `overlaps()` and the GUI's overlap warning judge against — one short draw is enough to collide — while **`MeanISI`** is what `summary().duration` estimates from, making a randomized plan's duration an expectation rather than a promise. Nothing downstream knows or cares: the timing channel still marks every onset, so sweep extraction and every metric are indifferent to the spacing, and the realized intervals survive in each file's `ADC.SweepOnsets`. Covered by `tests/verify_isi_jitter.m` (no hardware, no pool).

`mabr.stim.CalibrationAdapter` implements stimgen's `stimgen.calibration.HwAdapter` (`sample_rate()` + `play_and_record(signal)`) against MABR's own audio path, so `Settings ▸ Calibration…` measures **this** rig: `Audio.Device`, out on `PlayerChannels(1)`, in on `MicChannel`, at `Config.DACSampleRate`. The rate is not bookkeeping — `fromStimgen` regenerates every stimulus at the DAC rate and stimgen's `design_filter` produces a rate-specific FIR, so a calibration measured elsewhere would be applied to signals it does not describe. Note stimgen's contract is `(1,:) double` both ways, so `play_and_record` transposes on the way out. **It removes the device round trip from every record**: `audioPlayerRecorder` returns input aligned to the output *stream*, so an ASIO round trip (~25 ms on the reference rig) otherwise lands in everything stimgen reads as a time — a 10 cm speaker-to-mic path measured as a 25 ms conduction delay, i.e. metres of air. Each record therefore also sends a 1 ms unit pulse out `PlayerChannels(2)` starting on the excitation's first sample, records it back on `RecorderChannels(2)` (the same loop-back cable acquisition already requires), and shifts the mic record by that lag (`alignToLoopback`, static and pure); both inputs share the converter, so what is left is air plus speaker/mic electronics. The record runs `MaxLatency` (0.1 s) longer than the excitation so there is something to shift into — which also stops the last round-trip's worth of every response being cut off, as it was. `LastLatency` holds the lag; `CompensateLatency=false` restores the old stream-aligned record. With no pulse back, or a timing input shared with `MicChannel` (`hasLoopback`), it still calibrates — levels do not depend on latency — but uncompensated, with one red warning per adapter. Device I/O is the protected `stream`, so `tests/+mabrtest/LatentAdapter` can stand a simulated latent device in its place; `verify_calibration_latency` runs stimgen's own `measure_conduction_delay` through it. It refuses in `Testing` mode (loopback would measure the excitation fed back to itself) and while the controller is non-`Idle`, and calls `Engine.releaseDevice()` once per adapter to take the device off the idle-but-still-holding worker. MABR does **not** implement `stimgen.HardwareHost` — that is a TDT/RPvds buffer protocol, and MABR owns playback through its own worker.

**A custom presentation strategy** (`+stim/+strategy/`) is the sixth `Strategy`, and the same shape of extension point as an advance criterion — `context` builds the one struct the user's function is called with, `validate` refuses a malformed one at selection time, `custom_template` is the copy-me stereotype, and `sampleContext` is the representative design both the validator and a user at the command line try a strategy against. `Schedule.StrategyFcn` is called **once per `build()`** (never during acquisition, so it may be as expensive as it likes and cannot react to data — that is what an advance criterion is for) and returns the order: a vector for one run, a cell of vectors for several, or a struct carrying explicit polarities. `mabr.stim.strategy.normalize` is the one place those shapes become the canonical `Runs`/`Polarities` cells.

Three decisions in it are load-bearing. **Polarity is assigned, not asked for**: the k-th presentation of an alternating entry is inverted for even k, counted *across the whole plan* rather than restarted per run — which reproduces all three built-in polarity assignments bit-for-bit (`verify_custom_strategy` Part C asserts exactly that by replaying each built-in's own sequence through a custom strategy) and keeps an entry spread over several runs balanced, which is the entire point of alternating. **The repetition invariant is warned about, never enforced**: departing on purpose is a legitimate reason to write a strategy, while structural faults — an index off the end of the bank, a non-integer, a polarity that is not ±1 — are errors, since no design intends them and none can be presented at all. **`isIntermixed` asks the plan, not the name**: whether a custom strategy mixes stimuli inside a run is a property of the runs it produced, so the *method* inspects `Runs` while the *static* (all a caller holding no plan has) answers `true` conservatively — a custom strategy emitting one stimulus per run therefore keeps the correlation early-stop, the Repeat button and the live view's correlation bar, and `mabr.ui.App.PlanIntermixed` caches what the last successfully built plan said so `syncAdvanceEnables` is truthful rather than merely safe (which is why `onStrategyChanged` now calls `refreshPlan` *before* deriving those enables). `Strategy = 'custom'` with no `StrategyFcn` is refused (`mabr:stim:Schedule:noStrategyFcn`) rather than falling back to a built-in — a session presented in an order nobody chose is worse than one that will not start — and a strategy that throws is re-thrown as `mabr:stim:Schedule:strategyFcn` naming it, since the stack alone does not once the handle came from a file the GUI resolved. `Schedule.strategyLabel()` is what a record says (`custom: my_ordering`, not bare `custom`), which is what `AcqController` writes into a `.stimlog`'s `Presentation.Strategy`. The GUI plumbing mirrors the advance criterion's exactly: a `Custom function…` sentinel in the Strategy dropdown, the picked file's folder onto the path, `validate` before acceptance, a `Custom: <name>` item, and the choice saved **by file** in a `.mabrcfg` so it re-resolves next session (a file that has moved leaves the built-in in place and says so, rather than selecting a `custom` with nothing behind it). Documented with worked examples in `docs/Extending.md`.

Advance criteria are proper implementations in `+stim/+advance/`: `num_sweeps` and a real `corr_threshold` (the legacy `abr_adv_corr_thr.m` was an empty stub). They are evaluated **only for blocked strategies** — an intermixed run pools different conditions, so early-stopping it is both meaningless and unbalancing. The GUI greys the control out accordingly.

**Artifact rejection** is *decided* at finalization. `AcqController.finalize_run` judges each sweep with `mabr.metrics.detect_artifacts` (a pure function: `voltage` = any sample outside ±thr, `rms` = sweep RMS over thr) on the **filtered** sweeps, and records the verdict in `Recording.IsArtifact`. The live path *previews* the same policy (`AcqController.live_artifacts`, on the sweeps `filter_sweeps` has already run the same chain over; with the high pass switched off it falls back to removing each sweep's own mean, since nothing else would be taking out a baseline offset) so the live mean shows the average the block will actually hold and a noisy electrode is visible while it is happening — nothing there is recorded, and re-pointing `Artifacts` just changes what the next tick previews. Once flagged, a sweep is excluded from everything **descriptive**: `Recording.CleanSweepData` is what `SweepMean` (hence the trace organizer), `noisePower`/`SNR`/`RMS`, and `Block.computeMetrics` are built on, while `SweepData` still returns every sweep. Rejected sweeps are always **marked and saved, never dropped** — `io` writes `ADC.IsArtifact` alongside `ADC.SweepPolarity` so offline analysis can override the call or use `abr_analysis/rejectArtifacts` (which instead rejects by `isoutlier` over a whole session; a fixed threshold is what the live path needs because it is decidable for one sweep as it arrives). When `ArtifactPolicy.Repeat` is set, the controller calls `Schedule.appendMakeup(counts)` to re-present what was lost. Make-up runs are **appended to the end** of the plan (a run's play matrix is rendered before streaming and cannot grow mid-flight) and hold **one stimulus each**; `Schedule.MakeupLimit` (default 1 = at most double a condition) bounds the total so a permanently noisy electrode cannot make a session run forever, and `reset()` drops them so a re-started schedule begins from what `build()` produced. Clearing `Repeat` mid-schedule is the one policy change that cannot simply wait for the next run — `AcqController.set.Artifacts` calls `Schedule.dropPendingMakeup()`, withdrawing the make-up runs not yet reached (the one in progress is kept) and refunding their budget.

**Loop** (the Run panel's `Loop` toggle → `AcqController.Loop`) holds the plan on the condition in progress until it is switched off — and is for a **blocked** plan only, one condition per run (`AcqController.canLoop` = `~Schedule.isIntermixed()`: `conventional`, `conventional-shuffled`, or a custom strategy whose runs each hold one stimulus), the line Repeat and correlation early-stop already draw. An intermixed run is every condition at once, and repeating it would repeat the session rather than hold a condition, so `Schedule.loopRun` refuses one (`mabr:stim:Schedule:loopIntermixed`), `loop_run` ignores a `Loop` set under one with a log line (only a script can do that), and `App.syncLoopEnable` greys the button **and switches it off** under an intermixed strategy (re-derived on a strategy change, a restored configuration, and in `transport`; mid-schedule from the plan actually being played, `loopAvailable`). It is read when a run **ends**, so it is live at any time: at the end of every run — recorded (`conclude_run`, after `credit_run` and *before* `goOn` asks `isComplete`, so a looped last run still overlaps its next pass with block assembly) or stimulation-only (`on_block_completed`, before `after_finalize`) — `AcqController.loop_run` calls `Schedule.loopRun(r)`, which **inserts** another pass of run *r* directly after it, so the `advance()` that follows lands on the pass and the rest of the plan waits one place further back; cleared, the pass playing finishes and the plan goes on from the run that was next. Inserted, not appended like make-up/repeat runs — those must not jump the queue, a loop is the queue waiting. A pass is run *r* again, presentation for presentation and sign for sign, except a **make-up** run's, which is a full run of its stimulus at the scheduled count and is not charged to `MakeupUsed`; it is flagged `IsLoop` (parallel to `Runs`, like `IsMakeup`/`IsRepeat`), unbounded, untouched by `dropPendingMakeup`, and dropped by `reset()`. A pass is a run not yet started like any other, so the `Disabled` mask (`setEnabled`, the presentation-order window) applies to it when `advance()` reaches it: switching the looped condition off ends the loop on it (the emptied pass is dropped and the plan goes on). Recorded or stimulation-only, every pass is an ordinary run: finalized, credited, one `Block`/`.abr` per condition (or one `.stimlog`), `BlockReady` to the viewers. The advance criterion still ends a pass (and the pass is looped — it decides when a pass has enough, not when to leave the run); **Advance** still means advance — `stopBlock` sets the one-shot `AdvanceRequested` (cleared first thing in `begin_current_run`), `loop_run` skips that run, and the next run is held in its turn; Abort (`HaltAfterBlock`) still halts. The controller never clears `Loop` itself. `App.onStart` hands the button's state to a (possibly rebuilt) controller and `onLoopChanged` to the running one; the button is a `liveControls` entry that `transport` re-derives in both states (`syncLoopEnable`), tinted amber while set (`syncLoopButton`), and deliberately in neither prefs nor `captureConfiguration`, so MABR always opens with the plan free to advance. While it is set the progress window says `looping` and quotes no time left (see `ProgressMonitor`), and the Start status line quotes no duration. Covered by `tests/verify_loop_mode.m`.

A bank is remembered when it is *used*: Open…, a pick from the dropdown, and a loaded configuration. It is **not** remembered while `restoreLastSession` runs (`RestoringSession`) — a bank the app reopens by itself is not one the operator just used, and re-listing it would undo a removal at the next launch — nor on a sample-rate re-render. A file that has vanished is dropped from the list with a status line when it is picked, the self-healing rule Recent Configurations follows; one that is there but will not load stays listed, since removing it is the user's call. The list and the folder are history of this machine, not settings, so like Recent Configurations and the stimgen launcher's recent files they are in neither `captureConfiguration` nor the last-session snapshot. The dropdown and +/− are `configControls` entries (a pick is Open… by another route), and `syncRecentEnables` — re-called from `transport` when idle — greys the dropdown and − while the list is empty. The second row is why the Stimulus panel is 96 px, and with the Presentation panel's two order rows (256 px) why the window is 796: the panels' fixed heights sum to 780, so `WindowPos.restore` is given a minimum height and a window remembered from before those rows reopens tall enough rather than with the Run panel clipped.

A **Settings** menu (beside `HelpMenu`, built alongside it in `createComponents`) holds `Audio Device (ASIO)…`, which opens `mabr.ui.AudioSettingsDialog` over the `Audio` property (`mabr.AudioSettings`), `Calibration…`, which opens stimgen's own `CalibrationGui` over a `mabr.stim.CalibrationAdapter` rather than reimplementing it — stimgen owns calibration, MABR owns the rig — and the checkable `Background compute workers` (pref `MABR`/`ComputeWorker`, default on; `computeEnabled`/`onComputeWorkers`), a `configControls` entry that takes effect at the next Start because it decides the parallel pool's size (`ensureController` calls `mabr.pool` before building a controller, and its reuse test includes `UsingCompute` beside `Testing` and the sample rate). Directly beneath it, the checkable `Shut down parallel pool on exit` (pref `MABR`/`ShutdownPool`, **default on**; `poolShutdownEnabled`/`onPoolShutdown`) is the other half of that preference's lifetime: `App.delete` already kills every worker, but the pool they ran on outlives them, and an idle pool is still one to three worker processes holding a MATLAB's worth of memory each. It runs **last** in `App.delete`, after the windows are gone and after every worker above it has been killed *and waited for* — `mabr.shutdownPool` leaves a busy pool alone, and MABR's own futures have to be off it before that test can mean what it says (which is also what keeps a `parfor` of the user's own from being cancelled by closing MABR). Switch it off on a rig that keeps a pool warm for other work, or across MABR restarts to skip the 30–60 s relaunch. Like `Send blocks to trace organizer` below it, and unlike `Background compute workers` directly above, it is in *neither* control list — it decides nothing until the window closes, so it is safe to click mid-schedule. Beneath it the checkable `Send blocks to trace organizer` (pref `MABR`/`TraceTransfer`, default on; `traceTransferEnabled`/`onTraceTransfer`/`bindTraceOrg`) decides whether finalized blocks reach `mabr.ui.TraceOrganizer` at all — with it on, `openViewers` opens the organizer at Start and `bindTraceOrg` keeps it listening to the current controller; with it off the organizer is left out of Start, opens **empty** when pressed (the `Session` backfill is as much a transfer as the live one, and the reason to open it in that mode is to load a `.torg`), and any organizer already up is detached (`listenTo([])`) while keeping the traces it has. It is in *neither* control list either — nothing about it touches the rig or the pool *while a schedule is running*, so it takes effect the instant it is clicked, mid-schedule included. Below it, **`Windows to open at Start`** is a submenu of six ticks over `mabr.ViewPolicy` (`onStartupWindow`/`syncStartupMenu`, one item per window in `ViewPolicy.names()` order): a submenu rather than a dialog because there is one question per window and the answer is yes or no, so the menu *is* the editor. A tick opens and closes nothing now — it says what the *next* Start should come up with, and a window appearing under the pointer would be a surprise nobody asked for — which is also why it is in neither control list. Beneath that, the checkable **`Restore settings from last session`** (pref `MABR`/`RestoreSession`, default on; `restoreSessionEnabled`/`onRestoreSession`) governs the session-to-session recall below. It is a preference because a shared rig may want every session to start from one known state rather than from whatever the last user left behind — the case where reopening onto somebody else's subject and bank is worse than reopening empty. `Audio Device (ASIO)…`, `Calibration…` and `Background compute workers` are the three that do, and unlike the artifact/filter controls all three are in `configControls`, not `liveControls` — they lock for the duration of a schedule, since `buildSchedule` hands `Schedule.Device`/`PlayerChannels`/`RecorderChannels` to the controller only at `Start` and `AcqController.start` verifies the timing loop-back against whatever it was handed. The **Help** menu adds `Verification Tests…` below the wiki link, opening `mabr.ui.TestRunner`; it is a `configControls` entry too, for a blunter reason — the suite builds its own engine, worker and pool, so it cannot share the rig with a schedule in flight. Owns the presentation settings (bank, per-stimulus repetitions, strategy, ISI); `buildSchedule` is the single place they (and the `Audio` settings) become a `Schedule`, shared by the plan-summary preview and `onStart` so they cannot drift. **Start and Preview are one code path** — `onStart(preview)`; Preview hands the controller a `Session` with an empty `OutputPath`, which is already `finalize_run`'s record-without-saving route, so blocks are still acquired, finalized, counted for artifacts, and pushed to the viewers through `BlockReady` while nothing reaches disk (and the output folder does not join the remembered history). Because a preview is otherwise indistinguishable from a real run, the Run panel's title carries `PREVIEW (nothing is saved)` for as long as one is in flight. A **stimulation-only** schedule (`Audio.StimulationOnly`) gets the same treatment one notch stronger and takes precedence over it — `STIMULATION ONLY (no recording)`, since a preview acquires everything and merely declines to write it while this never records at all. `setRunTitle` decides *which* banner (from the `StimOnlyRun` snapshot, captured at Start for the same reason as `Previewing`) and the caller only says whether one is in flight. In that mode the **entire Acquisition panel is disabled** — `syncAcquisitionEnables` is the one place that decides it, retitling the panel `Acquisition — n/a (STIMULATION ONLY)` (a greyed control says "not now"; only the panel can say why) and routing through the three `sync*` functions that own those enables, since `transport()` calls them and would otherwise put the controls straight back. Those three speak only for their own *fields*, though, which leaves every row label black and the header bold — a panel that reads as live with some dead controls in it, which is the opposite of what is true — so a final sweep disables the panel as a unit, labels and title included (`ForegroundColor` greyed against the `AcqPanelFG` captured at build time, since the theme's own title colour is not the same everywhere). It runs **last** for that reason: it is the one that has to win. Coming back *out* of the mode it re-derives only the labels, which carry no state of their own — every interactive control keeps whatever verdict the `sync*` calls just reached, so an artifact threshold stays dead under `none` and Advance under an intermixed strategy. The panel's own `Enable` is deliberately unused: `uipanel` only gained one after R2021b, which `mabr.Config` still supports. Every one of them judges, stops, or displays a *recording*: an advance criterion has no running average to watch, an artifact threshold no sweep to judge, a filter chain nothing to draw (`FilterLabel` reads `n/a — nothing is recorded`). The live-plot **and analysis** toolbar buttons go with them, since the controller is handed no `LivePlot` and there is nothing for a metric to be computed from; the trace organizer stays, because it can still load a `.torg`. `syncAcquisitionEnables` is called at construction, from `transport()`, on each **Commit** in the audio dialog (`applyAudioSettings`, which is why the panel greys while that dialog is still open), and at the end of `applyConfiguration` (a restored `Audio` can enter the mode after the artifact/filter blocks above it have just re-enabled their controls from the same file). Advance is re-derived only when nothing is running, because it is a `configControls` entry that `transport()` owns. In that mode `onStart` opens **neither acquisition viewer** and hands the controller an empty `LivePlot` — there is nothing coming back to plot, and two windows that never fill are worse than none — so the Run panel's `Sweeps:`/`r =` readouts carry run progress (`Run k/N`, `no recording`) instead, written by `setRunReadout` from `onState`, since no live timer runs to fire `onMetrics`. It opens the one window that *does* fill there, `mabr.ui.ProgressMonitor` (the plan still walks itself run by run, which is exactly what that window shows), and hands focus straight back to the main window. `AudioMenuItem` is already a `configControls` entry, so the mode cannot be toggled mid-schedule. It opens **the viewers the user asked for at Start/Preview** — `openViewers`, called from `onStart`, walks `app.Views` (`mabr.ViewPolicy`, the live view and the organizer by default), builds only the ones whose window is absent and never raises one already up, and skips the organizer entirely when `Send blocks to trace organizer` is off, since nothing would arrive in it; the analysis window opens only when *none* is up, because it is deliberately not a singleton and a new one per Start would stack a session's worth of them, and `liveView()` hands the controller an empty `LivePlot` where the live view is switched off, exactly as stimulation-only already did — and lays them out beside itself on first run; nothing but the main window opens at launch, since there is nothing to watch until a schedule is in flight; a `uitoolbar` of pictogram glyphs (`live` = one trace on axes, `metrics` = three rising points on axes, `traces` = a stack of traces, `stim` = a loudspeaker, `progress` = three part-filled bars, a ruled notepad = the session notes, `front` = three cascaded windows with the front one solid, `arrange` = four tiled windows, `pin` = keep on top, `help` = a question mark, all drawn through `mabr.ui.Icon` like `TraceOrganizer`'s) raises them (`live`, `traces`), opens the stimulus viewer (`stim`), opens the progress monitor (`progress`), opens the notebook, and opens the wiki (`help`). `front` is the one button that acts on *every* window at once — `App.bringToFront` walks `App.windows()` raising each (restoring a minimized one first, since `figure()` alone raises without un-minimizing) and takes the main window **last**, so the press hands focus back to where it came from; the viewers are laid out beside the main window rather than over it, so nothing is buried by that. `windows()` collects from two sources because the App is not the only owner: the viewers it holds handles to, in toolbar order, then a `findall` sweep for anything else MABR put on screen whose owner is private — a `TraceInspector` opened from the organizer, a notebook the organizer popped out, an analysis window's static copy — identified by a `'MABR'` Tag or Name, which is what those windows have in common and a user's own figures do not. Like the notebook it is never disabled: losing a viewer behind another application happens most *during* a run, which is exactly when every other control is locked. `arrange` sits beside it and does the same after **laying the windows out** (`App.arrangeWindows`): the main window stays where it is as the anchor, and every other window from `windows()` is tiled, in that order, over the wider strip of the main window's display beside it (`mabr.ui.WindowPos.arrangeRegion` — the whole display when neither strip is `MinArrangeWidth` wide) cut into a grid of non-overlapping cells (`WindowPos.tile`, the column count whose cells hold the largest 4:3 box). Cells are outer rectangles and each window's chrome is measured off it (`placeOuter`), a non-resizable window keeps its size, and the progress monitor gets its height back from `fitToView`. Nothing is remembered by the press; positions are saved on close as always. The arithmetic is pure and covered by `tests/verify_window_arrange.m`. `metrics` is the one button that is not a raise: it opens **another** `mabr.ui.MetricPlot` every press (see that bullet), which is why `App` keeps an array of them and `closeMetricPlot` only remembers a position when the window closing is the last one open — every other one sits at a cascade offset, and storing that would walk the remembered origin across the screen a little further every session. The **notes** button is deliberately a toolbar button rather than a panel row: the window is already five panels deep and a log needs height the layout does not have, while what the operator actually needs is one press to write a line down at the moment something happens — and like the rest of the toolbar it is never disabled, since writing a note is safe in any state and the states worth writing about are exactly the busy ones. `App` owns the `mabr.data.SessionNotes` store (constructed in the constructor, since notes start before a schedule does — impedances, what changed since yesterday — and the controller does not exist until the first Start) and `bindNotes` hands it to `Controller.Session` from `ensureController`, *before* the `listenTo` re-point below it, so an organizer adopting the session's notebook cannot end up on the fresh one the controller built for itself. `applyNotesJournal` then points the plain-text crash journal at the output folder at Start; a **preview gets none**, because writing no files at all is the whole of what Preview means, and neither does a run with no output folder — the notes are still kept and still reach any file a later real run writes. Deliberately *not* part of `captureConfiguration`: a configuration is settings, a notebook is data. Because an open organizer keeps itself current through `BlockReady`, `traces` is a pure raise once it exists — it backfills from the `Session` only when building the organizer from scratch, so it cannot discard a loaded `.torg` view. `stim` is on-demand (it inspects what is about to be played, not what is coming back); `adoptStimuli` pushes each newly loaded bank into an open viewer, and a plain raise deliberately does *not* re-push, so it keeps the user's selection.

A **File** menu (leftmost, built before `SettingsMenu` in `createComponents`) holds `Save Configuration…` / `Load Configuration…` — the direct analogue of the legacy `+abr` ConfigTab's "Save/Load a Config file", now covering everything the GUI owns: Subject/Output, the stimulus bank plus per-stimulus repetitions, Strategy/Advance/ISI, and the `Artifacts`/`Filters`/`Audio` policies, in one `.mabrcfg` file (a MAT-file under `save(file,'MABRConfig')`, matching the `.abr`/`.torg` convention of a distinctive extension over a plain MAT-file). This is a separate concept from each policy's `loadPrefs`/`savePrefs` "last used" persistence — a configuration is a deliberately named, reloadable point (switching between protocols on one rig) captured by `App.captureConfiguration` as **plain structs**, never classdef objects, so a file saved by one version keeps loading after a class gains or loses a property. `App.applyConfiguration` restores defensively field-by-field (the same rule `loadPrefs` already follows) and returns a warning string rather than calling `setStatus` itself, because `onLoadConfiguration`'s own final status would otherwise overwrite it the instant it returns; `applyConfigStimuli` is where that warning usually comes from, when `StimulusSource.File` — the bank's own provenance, from `StimulusSet.Source` — is empty (a bank built live in the stimgen designer and never saved to a `.spl`/`.mat`) or has moved, in which case the bank already loaded is left alone and the repetitions are not touched either. Where the bank *does* reload, saved per-stimulus repetition counts are matched back onto it **by ID, not position**, so a bank that has gained or dropped an entry since the configuration was saved still lines counts up correctly. Restoring a Strategy that turns out to intermix stimuli always wins over a saved 'Correlation Threshold' `Advance` value (`syncAdvanceEnables` runs first and its disabled state gates whether the saved value is even applied) — early-stop is meaningless for an intermixed run, configuration or not. `LoadConfigMenuItem` is a `configControls` entry, since loading one can replace the bank/ISI/audio mapping out from under a running schedule; `SaveConfigMenuItem` is not, since capturing a snapshot changes nothing and is safe at any time, including mid-run. Beneath them **`Recent Configurations`** is a submenu of the last nine files saved or loaded, most-recent-first (`RecentConfigs`, pref `MABR`/`RecentConfigFiles`; `addRecentConfig`/`syncRecentConfigsMenu`), numbered so recency is visible at a glance and titled with the file name alone — the full path is the tooltip, since a subject-named file is what the operator actually reads. A file that has vanished since is dropped from the list with a status line rather than erroring, the same self-healing rule `applyConfigStimuli` follows for a bank that has moved; it is a `configControls` entry alongside `Load Configuration…`, being the same action by another route.

- `mabr.ui.AcqController` — owns the `Engine`/`Session`/`StimulusSet`/`Schedule`, the `mabr.compute.Pipeline` (and, when asked for by its fifth constructor argument and the pool can hold them, the `mabr.compute.ComputeEngine` — see the compute-workers section), translates UI actions → engine commands and engine events → UI updates, and runs **two timers**, split by priority. `LiveTimer` (~20 Hz) is **poll and dispatch**: it takes the run's statistics from the DSP worker (`Compute.live()`, doing nothing on a tick with nothing new) or from its own `Pipeline.step` when there is none — the same struct either way — then `LivePlot.updateStats`, the `CurMetrics` the advance criterion judges, and the early-stop check. The controller itself does no signal processing. `AuxTimer` (~2 Hz, the public `AuxPeriod`, retunable mid-run) carries the `MetricsUpdated` event the progress tally and the Run panel readouts ride. The live timer is a **poll**, not a frame clock: `fixedSpacing` every `LivePoll` (10 ms), and `on_live_tick` draws a frame only once `LivePeriod` (50 ms; both are `Constant`s) has passed since the last one *began*. A 50 ms `fixedSpacing` period was measured from a tick's *return*, which capped the view at 1/(50 ms + the frame), about 12–14 Hz. Polling holds 20 Hz up to a ~40 ms frame and follows a slower frame by one poll. The thread still gets 10 ms to itself after every tick, and a poll that draws nothing costs ~0.02 ms. A due poll that finds nothing new is not a frame (`live_tick_body` returns `fresh`); the next poll asks again. Two alternatives were measured and rejected. A single-shot timer re-armed from its own `StopFcn` does not work: when the tick processes events, that `StopFcn` is deferred, which dropped the view to a few frames a second. A 50 ms `fixedRate` timer halves the rate the moment a frame outgrows the gap it leaves. The split is still load-bearing rather than tidiness: once a frame costs more than the period, every millisecond of low-priority work in it comes straight off the frame rate. With the progress monitor and an analysis window open, that had taken the realized refresh from ~13 Hz to **~1 Hz**; moving the slow half out restores it. Nothing on the aux timer recomputes anything, and nothing on either timer copies the run: the analysis windows' snapshot is built when one of them pulls it (see `liveSnapshot` below). It used to be built on every aux tick whether or not a window was open to read it — a copy and transpose of every sweep so far, ~10 ms of the GUI thread twice a second at 9,000 sweeps. `LiveLocal` says whether the run's sweeps are in this process at all (the live tick sets it when its own pipeline served the statistics and clears it when the DSP worker did); it is cleared by `stop_timer` and at `begin_current_run`, so a finished run cannot be served to a puller after the fact. Every tick is **timed** (`mabr.ui.LiveTiming`, always on — a few `tic`/`toc`s): the stats fetch, the render split by `LivePlot.RenderTiming` into prep / `drawnow` (which includes any callbacks MATLAB runs inside it) / label gutters, the *gap* between frames (what was left of the period plus whatever else ran on the GUI thread), how long a due frame *waited* for something new to draw (`noData`: a poll that finds nothing is not logged as a tick), and each aux tick with whether it ran nested inside a live tick. `report_live_timing` summarizes a run at `on_block_completed` into `LastLiveTiming` (percentiles in ms, a one-line verdict, and `.Text`), logs the breakdown at level 2, and adds one level-1 line when the view drew at under half its target rate — the first thing to read when the live view feels slow. A single explicit `mabr.ui.ProgState` (Idle/PrepBlock/Acquire/BlockComplete/AdvanceBlock/SchedComplete/Error) drives program flow — event-driven, no global, no busy-wait. `finalize_run` **de-interleaves** the run: it pairs recorded onsets with `Schedule.runSequence` and emits one `mabr.data.Block` + one `.abr` per stimulus present, so the on-disk unit stays one-file-per-condition however the run was ordered. A homogeneous run saves the continuous trace; an intermixed one saves each stimulus's sweep windows concatenated (`compact_sweeps`) rather than N copies of a shared trace. `finalize_run` is `Pipeline.finalize` (the DSP: read the ring, recover the onsets, `resample`, split by stimulus, filter, judge — plain `parts`) followed by `assemble_blocks` (everything only the GUI process can do); with a DSP worker the first half runs there and the tail runs on its reply (see the compute-workers section). The `Artifacts` policy is applied and the `Filters` policy handed to each `Recording` in that split, and make-up runs are appended in `assemble_blocks` (see above). The live path filters the pre- and post-onset windows **together**, since `extract_sweeps` takes the baseline as the samples immediately preceding the onset at the same stride — one unbroken segment — which doubles the length available to `filtfilt` and keeps the edge transient in the baseline rather than on the first milliseconds of the response; that reasoning now lives in `Pipeline.filterRows`. Everything downstream (traces, correlation, artifact preview) therefore sees the same chain finalization will use. `set.Filters`/`set.Artifacts`/`set.Window` call `configure_pipeline`, which re-configures the pipeline (it designs the chain at the ADC rate on a change, never inside a tick) and broadcasts `Cmd.Configure` to the workers. It raises **`BlockReady`** (`.Info.block`, the finalized `Block`) once per stimulus recovered — always, independent of saving — alongside `BlockSaved` (`.Info.file`), which only fires when the `Session` has an `OutputPath`. Viewers listen to `BlockReady`. The other half of that seam is a **pull**: `liveSnapshot()` returns the sweeps of the run currently streaming as of the last live tick (time base starting negative, `Columns` = one sweep per column — `Pipeline.columns`, the orientation a condition holds them in — the artifact preview alongside), or `[]` when no run's sweeps are in this process (none streaming, or the DSP worker doing the signal processing, when the metrics worker serves the analysis windows instead). It is **built on demand** (`build_live_snapshot`) and kept: a pull within `AuxPeriod` of the last one made, or with no sweep since, gets that one, so however many windows ask, the run is copied at most once per `AuxPeriod`, and not at all while none does. It is cleared both at `begin_current_run` and at the top of `on_block_completed`, before finalization, so a puller can never count a run's sweeps twice (`verify_stimulus_alignment` Part H). It is a pull rather than a push because `mabr.ui.MetricPlot` refreshes at 1 Hz or slower and there may be several of them: handing every one a copy twenty times a second to be thrown away is the wrong shape. `start()` also runs a one-time hardware self-test, `verifyTimingLoop`: it streams a synthetic timing-only block (no signal, a few unit pulses) through the real `Engine.prep`/`run` path and confirms at least one pulse comes back on the timing input channel before letting the first real block begin, so a broken or mis-mapped loop-back cable — "the most common rig problem" — fails immediately with `mabr:ui:AcqController:timingNotDetected` instead of after a whole block streams with zero onsets. A private `SelfTestActive` flag makes that synthetic block invisible to `on_engine_state`/`on_block_completed`. The result is cached as `VerifiedAudioConfig` against the current `Device`/`PlayerChannels`/`RecorderChannels` rather than for the controller's whole lifetime, because `App.ensureController` reuses one `AcqController` across `Start` clicks and those three are editable between runs — so the check re-runs whenever they change and is skipped otherwise. It runs unconditionally, including in `Testing` mode, since `worker_loop`'s loopback branch passes the timing column straight through and exercises the identical code path.
- `mabr.ui.LivePlot` — the live view, and the one place an intermixed run is legible while it runs. It has two entry points ending in one render: `update(sweeps,…)` and **`updateStats(stats,info)`**, which takes what `mabr.compute.Pipeline.step` returns (the latest sweep, `R`, the counts, and per condition the mean, SD and counts), so the view runs with no sweep matrix in the foreground at all — the controller feeds it statistics whichever process produced them, and `stimulusMeans` branches once at the top (`error_band` over sweeps, or `band_from_stats` over the published SD; the same arithmetic). The most recent sweep keeps its **own axes at the top** (a single sweep is tens of times a mean; sharing an axis would flatten the averages) spanning the full width of the top row (the former `rho_post - rho_pre` onset-contrast bar beside it was removed from the view; the correlation is still computed for the advance criterion). Below it sits **one running mean per stimulus the run presents**, laid out four ways. Sweeps are attributed by the per-onset stimulus index `AcqController.live_info` passes through — the same pairing `finalize_run` de-interleaves by, so the live panels and the saved blocks agree. The controller hands it `[pre post]` as one contiguous segment so the time base can start **before** the onset; `TimeBase` (default `[-2 10]` ms), `Layout`, `GroupBy`, and `AmpMode` (`each`/`common`/`manual` + `ManualLimit`) are public properties, and the control strip along the bottom of the window writes exactly those. Overlaid means share an axes and therefore a scale, so `each` collapses to `common` there; the latest-sweep axes always scales on its own, including under `manual` — but in **discrete steps**, not to the peak. A single sweep is redrawn at the live tick rate, and a limit tracking its own peak grows with the thing being measured, which flattens the one comparison a raw sweep is watched for (is this one bigger than the last?); so `latestLimit` quantizes it to the 1-2-5 rungs of `LatestLadder` and moves it a whole rung at a time — **up** the instant a sweep would not fit, since clipping the signal is never the better trade, and **down** only after the smaller rung has been enough for `LatestShrinkHold` consecutive refreshes, so one big sweep does not leave the scale walking back down over the quiet ones behind it. The rung already stands clear of its data, so it is the one limit applied unpadded (`setLimits`' `pad`), which also puts the ticks on it; `reset` drops it, because a rung held over from the last run would frame this one's first sweeps against an amplitude nothing in it has shown. **The means stand on the same ladder** under `each` and `common` (`meanLimits` → `holdMeanRungs`, both rulers stepping through the one static `climbLadder`) — one rung per tile under `each`, per stack under `stacked` (where the rung sets the offset between traces), one under `common` — held off longer (`MeanShrinkHold`, ~2 s against the sweep's ~0.75 s) because a mean is watched for a response *emerging* and moves far more slowly than one sweep. A **setting** change is not held off (`afterSettingChange` clears the rungs): the hold is for data arriving, and between runs nothing arrives to count it down, so a band switched off would otherwise leave the axes wide for good. `manual` is applied **unpadded**, so the axes read exactly the number typed, and switching into it seeds from the rung on screen (`dataLimit`) so the view holds still. The display unit is picked from the **limits**, not the data, so an axes whose rung has not moved is never relabelled between µV and mV by a peak crossing 100 µV. **Means and Group are greyed while the run on screen presents one condition** (`MultiCondition`, `syncArrangeControls`) — every run of a blocked strategy — since one mean is one axes under every arrangement (`resolveGrouping`'s `n < 2` rule) and a live control there changed a setting and nothing on screen; the tooltip says why, and the setting is kept for the next intermixed run.

  **Multiple parameters** are what the lower region is really for. A bank almost never varies along one dimension — the ordinary ABR run is a Frequency × Level grid — and a list of means labelled `Tone_8000_30` in presentation order is not a view of one. `live_info` therefore also carries `Params`, the run's stimuli tabulated by `mabr.stim.StimulusSet.paramTable` (names, an `[nStim x nP]` value matrix row-aligned with `Stimuli`, and units), and the view uses it three ways: conditions are **labelled** by the parameters that actually vary across *this run* (`8 kHz, 30 dB`, never a constant one); **ordered** by them rather than by the order the schedule happened to present them in; and **grouped** by one of them. A blocked run's single mean is named the same way, in the overlaid axes' title. Which parameters count as informative is settled at the **bank**, not the run — `AcqController.stimParams` tabulates the whole bank and takes the run's rows out of it, `Varying` included — because a blocked run holds one condition and therefore varies nothing, and a view that dropped every parameter for that reason would leave the operator's own dimensions off the one label saying what is being acquired. `LivePlot` computes `Varying` itself only when a caller supplies none. The group parameter decides the colours — one hue per group, ramping pale-to-full along the within-group parameter, so a level series looks like a series instead of seven unrelated colours — and it decides the two parameter-aware layouts: **`grid`** gives every condition a tile, groups across columns and the within-group parameter up the rows with the largest at the top and short columns bottom-aligned (the live analogue of `abr_analysis/plotABRGrid`), and **`stacked`** gives each group one axes with its conditions offset into it, named on the y axis — the y ticks *are* the labels, so a threshold series needs no legend. `GroupBy` is `''` (auto: `Frequency` where the run varies one, else the coarsest varying parameter — fewest distinct values, so the grid comes out wide and short), `'none'`, or a parameter name; **one** varying parameter is deliberately left ungrouped, since a single dimension is the series itself and grouping by it would put every condition in a group of one. Naming a parameter the run does not vary falls back to auto rather than erroring — the Group menu re-derives itself from the run, so it settles by itself. Without parameters altogether nothing changes: the ID-labelled, presentation-ordered list is exactly what it always was.

  **The y axis labels always have room**, in every layout and at any window size, because the margins are *measured* rather than fixed: `fitLabelGutters` reads each axes' `TightInset` after a refresh and re-tiles around it (`meanPositions` is the single place a tile's rectangle is decided, so the axes that get built and the axes that get moved cannot disagree). It matters most in `stacked`, where the labels are the condition **names** and *every* column of stacks carries them rather than just the leftmost — a margin sized for a three-digit microvolt number does not merely crop `60 dB (136)`, it draws it across the trace in the tile to its left. A gutter therefore grows the instant the labels need it and shrinks only once there is real room to give back (`pickGutter`): the asymmetry is what keeps the fit from oscillating, since a narrower axes can be relabelled by MATLAB with shorter ticks that would ask for the gutter straight back. Measuring costs a graphics query, so it happens only when the answer could have changed — a new arrangement, a limit, unit, band or stack label that could lengthen the labels, or a resized panel (the gutters are fractions of it, which is why `relayout` re-fits and caches its width) — and never on the plain refresh in between. *Whether* it could have changed is decided without a query: `gutterKey` is built entirely from values the view wrote itself (the limits, which are ladder rungs and move in whole steps; the unit and band the y labels name; which tiles show numbers; the stack labels' lengths; the time axis; the arrangement; the panel's size; the gutters in force). It used to read every axes' tick labels back to ask, and a tick label cannot be read until MATLAB has laid its axes out — that readback was most of a blocked run's frame (~28 ms), twenty times a second, for an answer that changes a few times a run.

  **A frame writes only what changed, and knows what changed without asking the graphics.** `updateStats` returns at once when handed the statistics it drew last (a pipeline with nothing new returns its last answer) — ending an artifact flash on its clock (`expireFlash`) and nothing else. The grouping is re-resolved only when something it reads changes (the run's stimuli, labels and parameters, `GroupBy`, `Layout`), and with it the controls it drives. Every line's data, band polygon, axis limit, y label, title, stack tick, tick-label visibility and the artifact counter is compared with a record of what the view last wrote there (`setLine`, `setBand`, `setAxisLims`, `setYLabel`, `setTileTitle`/`setLatestTitle`, `setStackTicks`, `showArtifacts`) — **never with a read**, because reading any property of an axes with changes pending makes MATLAB lay it out on the spot, which pulled the previous frame's drawing into this one. Writing an unchanged value is not free either: it marks the axes for another layout, and a centred title re-laid out under `drawnow limitrate` is redrawn before the last one has been erased, which is what reads on screen as doubled text. The records describe particular graphics objects, so `forgetWritten` drops them whenever those are rebuilt (`buildMeanAxes`) or written behind their back (`reset`); `verify_live_plot` Part 18 holds a view brought up a frame at a time, through every arrangement, scale, band, grouping, time base and a reset, equal to one drawn once from the last frame, and was checked against both of those omissions. Measured in batch MATLAB with a full `drawnow` per frame: 54 conditions ~290 → ~45 ms (grid) and ~325 → ~30 ms (stacked), a blocked run ~22 → ~7 ms, and a frame with nothing new ~280 ms → ~0.1 ms; on `verify_live_refresh`'s run the median tick went from 36 to 5 ms.

  **`render` is not re-entrant** — the same rule `mabr.ui.MetricPlot` follows, and for the same reason one notch sharper. `legend()` and `drawnow` both process the event queue, so a live tick can land *inside* a render started by the control strip (or the other way about), and the inner call rebuilds the mean axes the outer one is still holding handles to: the outer's axes are left orphaned on the panel with a stale run drawn over the new ones, its captions land on somebody else's axes, and a render that resumes against an emptied `axMean` indexes past the end. Where `MetricPlot` simply skips a re-entrant call, `LivePlot` **remembers** it (`RenderPending`, run once when the outer pass returns): a setting changed between runs has no timer tick behind it and would otherwise never appear. `buildMeanAxes` additionally sweeps the panel for any axes the view is not holding (`dropStrayAxes`) — nothing else puts axes there, so an orphan from any cause cannot outlive the next change of arrangement. Both are covered by `tests/verify_live_plot.m`, which plants an orphan by hand and then changes the arrangement under a live timer for three seconds.   **Error bands** are the right-click menu's job (`ErrorBand` = `none`/`std`/`sem`/`ci` + `ConfidenceLevel`, default 95%; the menu offers 90/95/99 as a flat radio list so one click reaches any answer). Each mean gains a `patch` in its own colour behind it, drawn as one closed polygon — mean − hw left to right, mean + hw back — from `mabr.metrics.error_band`, which is the one place the three statistics live. Its `ci` needs a t quantile and `Config.RequiredToolboxes` deliberately excludes Statistics, so `mabr.metrics.t_quantile` computes one exactly from core MATLAB's `betaincinv` via `nu/(nu+T²) ~ Beta(nu/2,1/2)` rather than approximating or requiring `tinv`. A condition with fewer than two clean sweeps gets **no** band rather than one of zero width, and a patch whose edges are not wholly finite is blanked outright (a patch is one face; a NaN vertex in the middle of it is an undefined polygon, not a gap). The load-bearing asymmetry is in the scaling: **`sem`/`ci` widen the axes to fit, `std` does not** — an SD band describes a single *sweep*, which on an ABR is tens of times the average, so folding it into the limit would squash every mean in the window to a flat line; it is drawn and left to run off the axes, which is the statement it was switched on to make. `stimulusMeans` therefore returns one bundle (`.M`, `.E`, `.A` = what the axes must fit, `.counts`, `.rejected`) so the traces, the limits, the stack spacing, and the Manual seed cannot disagree about which sweeps they describe. The band is named in the mean axes' y label (`Mean ± 1 SEM (µV)`) — and in the stack title's parenthetical under `stacked`, where the y axis is already carrying the condition names. It went in a context menu rather than the control strip because the strip is already full at the window's minimum width. `setFilterText` captions the latest-sweep axes with the chain in force (a subtitle — the sweep count owns the title and the artifact readout owns the top-left corner), so a filtered view is never mistaken for the raw signal. The control strip ends with **Analysis…**, which calls `NewAnalysisFcn` — a handle the host supplies (`mabr.ui.App` points it at its own `onMetricPlot`), because this view has no business knowing about controllers or how many analysis windows are open; unset, the button is present but disabled, since a button that opened an empty window would be worse than a dead one. It is here because the moment you want a metric plotted across conditions is the moment you are staring at the traces wondering whether the response is growing with level. The whole set of display settings **persists between sessions** (`displaySettings`/`applySettings`, `loadDefaults`/`savePrefs`/`saveDefaults`, pref `MABR`/`LivePlot`, the same idiom `MetricPlot` follows): a new window opens on the layout, grouping, time base, scaling and error band the last one was left showing. It is written only from the control strip and the right-click menu — a *user* choosing a look — and never from a property setter, since a script driving the view (or a verification script) is not a preference; the constructor applies the stored settings *before* `build()`, so the strip is drawn from them rather than flickering through the class defaults. Covered by `tests/verify_live_plot.m` and `tests/verify_view_prefs.m` (no hardware).
- `mabr.ui.ProgressMonitor` — how far the *schedule* has got, as opposed to what the data looks like. Three views over one tally, and the **default one draws nothing**: `simple` is the lamp, the header beside it, and the control strip — no axes at all, because the header already says how far along the session is, what the rig is doing and how long is left, and a bar under it was a second drawing of the same number. The header is the big number (green when done) plus three lines: the state (`Paused` while the rig is — a paused run is still `Acquire` to `ProgState`, so `listenTo` also listens to the controller's `Engine` for `mabr.acq.State.Paused`), run *k* of *N* with `(make-up)`/`(repeat)`/`(loop)`, `stimulation only`, and `looping` while the followed controller's `Loop` is set (read off it each repaint, `looping()`; the time line then says `until Loop is off` instead of a time left or `done ≈`, since a looping plan has no end to count down to); the current run's condition named by the bank's *varying* parameters (`8 kHz, 30 dB`, or `n conditions intermixed`), its count, and the live artifact count — or, between runs, conditions complete and plan size; and elapsed / time left / `done ≈ HH:MM`, then `took`/`finished` once at rest. The time left is the plan's remaining work (presentations × `MeanISI` plus each remaining run's `padSeconds() + maxDuration`) scaled by measured ÷ planned time for the work done since a baseline, once 10 s have been watched, with pauses excluded from the ratio; a window opened **mid-session** (the common case — it is on demand) shows no elapsed time and takes its baseline only once it knows the current run's count, because measuring from the moment it opened made the old `el*(T-D)/D` estimate wildly short. The window's `Name` carries the percentage, for the taskbar. `headerText()` returns `[pct,state,time,detail]`. The other two are `bars` (one per stimulus, or per value of any one stimulus parameter via `GroupBy`) and `heatmap` (two parameters, `HeatX` across and `HeatY` up, each cell shaded by completeness). The **window sizes itself to the view**: `applyViewLayout` collapses the plot row to one pixel (the axes is collapsed, never destroyed — switching views is a row height and a `Visible`, not a rebuild) and `fitToView` takes the figure down to `CompactHeight`, then back up to `PlotHeight` when a plot is asked for. Only the height moves — the width means the same thing in both forms and is the user's — and the **top edge is held**, so the window grows and shrinks downwards rather than jumping out from under the pointer that just changed the view. `PlotHeight` is whatever the plot views were last left at, remembered per rig in the `MABR` pref group, which is why `mabr.ui.App.onProgress` restores a remembered *position* with no minimum height and then calls `fitToView`: the spot is the user's, the height is the view's, and a remembered heat-map height would otherwise reopen the default plotless view as a tall window with nothing in the middle of it. Plus `Labels` (`counts`/`percent`/`none`) deciding what the numbers on the bars, in the cells, and in the header read as, and `AlwaysOnTop` (uifigure `WindowStyle`, the same mechanism the main window's pin uses, persisted in the `MABR` pref group). The heat map is the one view that shows a **hole** — a condition the bank does not contain, **hatched** (`HoleHatch`, one NaN-separated line) over paper-white rather than left the colour of the ramp's 0% step, which it used to be almost indistinguishable from — and it outlines the cells being presented (`ActiveOutline`) in the bars' amber; cell text is ink or white by WCAG contrast against that cell's actual colormap entry (`whiteInk`), not a fixed threshold that put white on mid-teal at ~2:1. The tally is *computed from the plan every time*, never accumulated across events: planned = every presentation in `Schedule.Runs` summed per stimulus (so `appendMakeup`/`repeatRun` enlarge it, and overall progress correctly steps *back* when a make-up run lands — the work grew), recorded = `Schedule.RunCounts`, in flight = the current run's sweep count paired against `Schedule.runSequence` — the same pairing `finalize_run` de-interleaves by, so the bar moving mid-run and the count left behind after it agree. The in-flight part is kept from `PrepBlock` until the run is **credited** (`sum(RunCounts)` moves off `RunBase`), not dropped at `BlockComplete`: with the DSP worker finalization is asynchronous, and dropping it there made every bar fall back by a whole run until the reply landed. Under **stimulation only** there are no sweeps, so it is *estimated from the clock* (onset *k* at `SilencePad + (k-1)*MeanISI` of streaming; the run clock is held while paused and frozen when streaming stops) and marked `~`, with `Estimated` true — until the recorded count replaces it. It rides `AcqController.MetricsUpdated` (~2 Hz — the **aux** timer, deliberately not the 20 Hz live tick, which belongs to the trace) and repaints at most every `MinInterval` (0.2 s), and then only when the tallies moved or a second has passed for the clock — a throttle the aux tick does not reach; `MinInterval` remains as this window's own guarantee against a faster caller. State changes force a repaint; `BlockReady` does **not** (an intermixed run raises one per stimulus in a burst, and the state change after finalization repaints once). Because nearly every refresh runs inside a controller callback it **never calls `drawnow`** (from a timer callback that flushes every figure, the live view included, and services the queue, so the live tick could nest inside it), writes every uifigure property only when it changes (`put`, judged against what it last wrote rather than read back, since even a read of a uifigure property goes through the component), holds the state as plain flags (`Phase`, set once per change by `setStateNow` — an enum comparison costs tens of microseconds) and the finish time as seconds off a wall-clock reference rather than a `datetime` round trip, diffs the per-bar and per-cell text (`setTexts`/`markDrawn` over the `Drawn` struct), computes the current run's stimulus set and label once per run (`RunCache`), and tallies its in-flight counts incrementally (`prefixCounts`); nothing is created per refresh (two patches whose vertices are rewritten, one image whose `CData` is, two overlay lines, a fixed array of texts whose `String`s are) and layout is rebuilt only when the view, the grouping, or the plan changes. It has **one timer of its own**, a 1 Hz header clock (`clockRunning()`) that runs only while a followed schedule is in flight and repaints only when nothing else has in the last second — the aux tick fires only while sweeps are counted, so without it the clock froze between runs and for the whole of a stimulation-only session, the one mode the App opens this window by itself. Closing its own window deletes the monitor (listeners and clock with it). Grouping dimensions come from `StimulusSet.paramTable`, **varying parameters only** (a constant one is a single bar or a one-column map), so a condition here and a condition in `batchABRAnalysis` are the same thing. `listenTo(controller)` re-points rather than stacking, and reads `controller.Schedule` on every refresh rather than holding it (`setStimuli` *replaces* it); `attach(schedule,set)` follows a bare plan, which is what the verification script drives. `mabr.ui.App` opens it on demand from the toolbar — never at Start like the acquisition pair, with one exception: a **stimulation-only** run opens it, because that mode opens no other viewer and this is the only window that fills. Covered by `tests/verify_progress_monitor.m` (no hardware, no pool), which drives it through `mabrtest.FakeController` and its `mabrtest.FakeEngine` (the pause).
- `mabr.ui.PresentationOrder` — the order the plan presents its conditions in, with the one on now highlighted, and the switches for upcoming conditions. One axes: presentation number across the whole plan (`Schedule.Runs` concatenated; `RunStarts` are the run offsets, drawn as dotted verticals) against one row per condition, sorted and named by the bank's *varying* parameters (`8 kHz, 30 dB`), so a conventional plan is a staircase, an interleaved one a sawtooth, a shuffled one scatter; presentations made are blue, the rest grey. The **active** condition gets an amber band along its row, a bold amber row label (the tick labels use the TeX interpreter for this, so IDs are escaped), an amber marker and cursor at the presentation, and the header (`Now: …`, run *k* of *N*, presentation *i* of *M*). The position is the controller's live sweep count paired against the run's sequence — the pairing `finalize_run` de-interleaves by — so the highlight is the latest presentation the rig has **recorded**; a run being prepared highlights its first; under stimulation only it is estimated from the run clock (`Estimated`, `~` in the header, a 0.5 s timer of its own that runs only then). `Span` (`auto`/`window`/`run`/`plan`, with `WindowLength`) decides the x range; `auto` is the whole plan when every run holds one condition and a window following the active presentation otherwise, and lines join presentations only while ≤ 400 are shown. The side **table** (On / Condition / Upcoming) is the enable/disable control: clearing On calls `Schedule.setEnabled(idx,false)`, the condition's upcoming presentations are drawn as crosses and dropped from the pending line, its label greys, and **Enable all** puts everything back. Covered by `tests/verify_presentation_order.m` (no hardware, no pool).
- `mabr.ui.MetricPlot` — the **online analysis** window: ONE metric, computed per stimulus condition and plotted against the stimulus parameters, refreshed while the schedule runs. The live plot answers "what does the response look like right now"; this answers the question the experiment is actually asking — "how does this number behave across the conditions I am running". **One plot per window, and the window is deliberately not a singleton**: every press of the App's chart toolbar button (or the live plot's Analysis… button) opens another, each with its own metric, window, plot type and aesthetics, because RMS-against-level and correlation-against-frequency are two plots and folding them into one window behind a mode switch means never seeing both. `App` holds them in an array only to re-`attach` them when `ensureController` rebuilds the controller and to delete them with itself. Data comes from two sources merged by stimulus ID: finalized blocks (the `BlockReady` event plus a backfill of `Session.Blocks` at `attach`, authoritative — artifacts already excluded, filter chain already applied; a `BlockReady` is *merged without drawing*, under `Suspend`, and the window's own tick draws it, because an intermixed run raises one per condition in a single burst and a full evaluate-and-rebuild after each was that many redraws at every run's end — the public `addBlock` still draws at once) and the run in progress, pulled from `AcqController.liveSnapshot` on this window's own clock. A live condition is drawn with a **hollow ring** and counted in the subtitle, since a number from 40 sweeps is not the number the block will report — except under the sweep correlation, whose catalog entry is not evaluated while acquiring (`WhileAcquiring`, honoured by `evaluateJobs` on both paths): it compares every pair of sweeps, so a live point stays blank until its block lands, and the subtitle says `n acquiring (shown when finished)`; repeats and make-up runs of one stimulus **accumulate** (`mergeCondition`) rather than replace, because they are more data for that condition. The plot **adapts to how many parameters vary** (`informativeParams`): none → a bar per stimulus ID, one → a line with symbols, two → one line per level of the second with a legend, three or more → the user picks the two axes and the rest average into each point (the subtitle says so). Heat map / contour / surface are on request only — `auto` never picks a surface, because lines are what is readable at a glance during acquisition — and a map asked for without two parameters, or without enough conditions to make a grid, falls back to lines and says why rather than drawing something that looks like a map and is not; the heat map indexes its axes and labels them with the real values, since drawing an octave-spaced series on a linear grid would restate it as an even one. Metrics are `mabr.metrics.online.catalog` plus any user function meeting the contract, validated at selection time. The condition table and the evaluation loop are `mabr.compute.ConditionStore` and `mabr.compute.evaluateJobs`, shared with the metrics worker; with the compute workers on, `attach` takes a **slot** on that worker (`ComputeEngine.acquireSlot`, one per window, eight in all — a window opened with none free evaluates in-process and nothing else changes), `pushJob` sends every setting change to it, and `computeValues` reads the published row back (`workerValues`) or computes locally (`localValues`, public so a test can hold the two against each other). A window whose custom metric hung the worker is flagged (`Stalled`) and evaluates nothing until another metric is picked. `render` is not re-entrant (`legend` processes events, and a tick landing inside one would `cla` the axes out from under it) and skips a redraw whose values are the ones already on screen — a setting change forces one — so idle windows cost nothing between runs. A refresh that changes *only* the values (every refresh of a run in progress) does not rebuild either: `layoutKey` is everything a line drawing depends on besides them (conditions, x positions, live flags, metric, style, notes), and when it matches the last one `updateLines` moves the series and live-ring handles `drawLines` kept (`SeriesLines`/`RingLines`) to the new values instead of `cla` + series + legend + menus once a second per window; bars, maps and value labels still redraw in full. In-process evaluation keeps a `Memo` for `evaluateJobs` (below), with `CustomGen` naming each custom function adopted. Aesthetics are entirely on the axes **right-click menu** (plot type, palette, per-series colour, colormap, marker, line style/width, grid, legend placement, log axes, manual Y limits, point labels, font size, light/dark, and the clipboard/CSV/image/pop-out exports) while the control strip owns what is *measured* (metric, analysis window, which parameter is on which axis, refresh interval) — ink on the menu, numbers on the strip. `Style` plus the analysis choice persist in the `MABR` pref group, so the next window opens looking like the last one tuned. The refresh interval is 1 s by default and clamped to `[0.25 60]`: an average moves slowly, and every open window recomputes every metric for every condition on the GUI thread. Nothing here writes anything. Covered by `tests/verify_metric_plot.m` (no hardware, no engine, no pool).

## Offline analysis classes (`+mabr/+analysis/`)

The object-oriented counterpart of `abr_analysis/`, written to the same `.abr` files and reproducing the same results. It does **not** replace those functions — they are untouched — but it is where the offline work is meant to go. Repo-side prose is `docs/Analysis-Classes.md`; `tests/verify_analysis.m` covers it end to end (no hardware, no pool, no prefs touched, and in the suite).

The organizing rule is that **every static method does one thing to one unit, and batching is the caller's loop**. `mabr.analysis.Session` is the only stateful class and its unit is one *session* — one folder of `.abr` files — so a study is a loop over `Session.find(root)`, never a `for` inside a function. Each of the five steps (`parse` → `segment` → `reject` → `detect` → `estimateThresholds`) delegates the per-condition arithmetic to a class that can be called with no Session in sight: `mabr.analysis.Filter` (one trace), `.Artifacts` and `.PermTest` (one condition), `.Threshold` (one condition to detect, one series to fit), `.Plot` (plain data), `.Progress` (a console counter that replaces `parfor_progress`).

- **Conditions are a table, not an N-D cell array.** One row per condition with a column per stimulus parameter, named from each file's `SIG.informativeParams` — which is what lets a bank vary three things without anybody hard-coding which two they were, the structural limit of the `S{level,freq}` + `U` form. `grid(rowParam,colParam)` reshapes to exactly that older form for the code that wants it, and `verify_analysis` Part H asserts the two describe the same data.
- **Rejection flags, never deletes** — the same rule as `mabr.data.Recording.IsArtifact`, and the reason a rejection setting is something you can change your mind about without reloading. `segment` seeds the flags from the rig's own `ADC.IsArtifact` (`HonorAcquisitionArtifacts`, default true), reads `ADC.SweepPolarity` so a polarity-split analysis is possible offline, and says so loudly when a file carries `TestMode` — those samples are the stimulus, not a subject. Files sharing a condition are **concatenated**, where `extractABRResponses` silently overwrote the cell.
- **Filtering is applied to the whole continuous trace before segmentation** (`mabr.analysis.Filter`, equiripple FIR 300–3000 Hz, `filtfilt`), because a sweep is a few hundred samples and the filter's edge transient would land on the response. Traces are cached (`KeepTraces`, default true), so re-segmenting with another band costs no disk reads. `fromObject`/`fromCoefficients` accept a design made elsewhere, as `extractABRResponses`' `HighpassHd`/`LowpassHd` did. An all-bands-off filter is a legitimate "reprocess unfiltered" setting and passes the trace through rather than refusing.
- **`mabr.analysis.PermTest` is the rewritten `permtest`**, taking `[nSamples x nSweeps]` like everything else in the package (the old one took the transpose, so every call site transposed). The permutations are **vectorized**: a sign flip leaves `sum(x.^2)` untouched, so a whole block of permuted t-maps is one matrix product, and the cluster-mass and TFCE statistics are then computed for the block by run-length arithmetic (a cumulative-sum difference at run boundaries; a difference array for TFCE's per-threshold accumulation) rather than sample by sample. `verify_analysis` Part E holds both against a naive per-row implementation. `Seed` matters more than it looks — a threshold is fitted to these p-values, so an unseeded test makes the threshold jitter between re-analyses of the same data.
- **No Statistics, Curve Fitting, or Parallel Computing toolbox, and no File Exchange dependency** — which is the point, since `mabr.Config.RequiredToolboxes` lists none of the first three and `colorcet`/`use_fig`/`parfor_progress`/`structToCallerVars` live only on the author's own path. The t threshold is `mabr.metrics.t_quantile`, the logistic regression is IRLS (replacing `fitglm`), the sigmoid is `fminsearch` (replacing Curve Fitting's `fit`), confidence intervals are Monte Carlo draws from a covariance taken off the fit's own Jacobian with a local percentile (replacing `quantile`), and `mabr.analysis.Plot.palette` carries perceptually uniform colormaps of its own.
- **`Criterion` means two different things and `FitTarget` decides which**, which is the one thing here most easily misread. On binary detections it is a probability — the level at which a response becomes detectable half the time, the usual meaning of "ABR threshold". On graded strength it is a fraction of the response range, so 0.5 is the **half-maximum of the growth function**, a materially larger number because the response goes on growing after it first appears. `estimate`'s `auto` gives each model the target it is a model of; ask for `FitTarget="binary"` explicitly to get a detection threshold out of a sigmoid or isotonic fit. `verify_analysis` Part G asserts both readings separately, precisely so the two cannot quietly merge.
- The sigmoid's asymptotes are **pinned to the observed range by default** (`Asymptotes="fixed"`, fitting only midpoint and slope). Four free parameters on the six or eight levels a real series holds is over-parametrized whenever the response is still growing at the loudest level — the usual case — and the fit then answers by inventing a ceiling far above anything measured and moving the midpoint out with it (184 dB, on the verification's own data, before this was fixed).
- A threshold that was never reached is **`Inf`**, never a made-up number; what to plot for it is the caller's decision. `Thresholds` carries the fit and the human answer side by side (`Threshold`/`Curated`/`IsCurated`), because the two disagreeing is information and a curated session must still be able to say what the model said.
- `saveResults` writes a **plain struct** of tables and arrays, deliberately not the object: a results file that needs a particular class version to load is one that stops opening the day the class changes. `fromResults` reads it back; `IncludeSweeps=false` writes a much smaller file that still carries every answer.

## Offline analysis pipeline (`abr_analysis/`) — UNCHANGED

A **separate, function-based** batch pipeline (authored `dstolz@umd.edu`, 2025) — not part of the app and untouched by the rewrite. It reprocesses saved `.abr` files. Flow (`batchABRAnalysis`):

`getABRSessions` → `parseABRFiles` (regex over filenames, e.g. `SUBJ_ID_<n>_Frequency_<f>kHz_Level_<L>dB_<yyMMdd'T'HHmmss>.abr`) → `extractABRResponses` (loads `-mat`, filters full trace, segments into sweeps grouped by stimulus) → `rejectArtifacts` → `filterABRData` → `plotABRGrid` → `abrPermutationThreshold` (permutation-test threshold via `permtest`, with `abrPermutationThresholdCuration`).

It reads exactly: `ABR_Data.ADC.SampleRate`/`Data`/`SweepOnsets`, `ABR_Data.StartTime`, `ABR_Data.SIG.informativeParams` + numeric named params + `Label`. `mabr.data.io.writeABR` emits precisely these, plus `ADC.SweepPolarity` (+1/-1 per sweep) and `SIG.alternatePolarity` (0/1) for polarity-aware analysis, and `ADC.IsArtifact` (logical per sweep) recording which sweeps acquisition rejected — all three always written, and kept out of `informativeParams` so they don't become grouping dimensions; `verify_data_roundtrip` confirms it. A fourth, `ABR_Data.TestMode`, sits at the **top level** rather than under `SIG` for the same reason: it says the samples are the stimulus rather than a recording (see Test Mode above), which is a fact about the session and must never be read as a stimulus parameter. Note `batchABRAnalysis` has a **known stale-signature bug** (it calls `parseABRFiles`/`extractABRResponses` with positional args that no longer match) — **do not fix** it; call those functions with name-value syntax directly instead. `parfor_progress` is an external File Exchange dependency of this pipeline.

## Data file format

`.abr` files are **MATLAB v5 MAT-files** (despite the extension) containing a single `ABR_Data` struct. Load with `load(file,'-mat')`. **No `.abr` or `.stimlog` is ever overwritten** (`io.uniqueFile`): the name's timestamp resolves whole seconds, so two runs of one condition started within the same second (short Loop passes, a Repeat straight after a run) would share one and `save` would silently replace the first; the later file gets `_2`, `_3`, … after the timestamp instead, and the log says so. Such a name still starts with the subject token and ends `.abr`, but does not match the strict `…(\d{6}T\d{6})\.abr` pattern `batchABRAnalysis`/`docs/Data-Files.md` quote. `.mabrcfg` files are the same convention applied to `mabr.ui.App`'s save/load configuration feature (see GUI section): a MAT-file holding one variable, `MABRConfig`, a plain struct. `.notes` files are the one deliberate exception to that convention: **plain UTF-8 text**, one `[stamp] note` per line under a `%`-commented header, rewritten in full on every commit by `mabr.data.SessionNotes.writeJournal` (`mabr.data.io.buildNotesFilename` names them alongside the session's other files). A crash journal that needs MATLAB to read it is not a crash journal; the structured copy lives in every `.abr`/`.stimlog`/`.torg` the session wrote, and `SessionNotes.fromFile` reads the text back. `.stimlog` files are the same again, holding one `MABR_StimLog` struct — the stimulation sequence of one run, and the *only* output a stimulation-only session produces (see `mabr.data.io.buildStimLog` for the fields; `Sequence` is parallel arrays, one element per presentation, so `struct2table(S.Sequence)` reads as a log on the spot). Note `*.abr`, `*.stimlog`, `.runtime_data/`, and `*.asv` are gitignored.
