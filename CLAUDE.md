# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

MABR (Matlab Auditory Brainstem Response) is a **proprietary, Windows-only** MATLAB toolbox for presenting acoustic stimuli and acquiring/analyzing ABR electrophysiology data. Copyright Daniel Stolzberg, PhD — see `Copyright.txt`. There is no build system or package manager; it runs inside MATLAB.

One **git submodule**: [`stimgen`](https://github.com/dstolz/stimgen) at `external/stimgen`, the suggested source of calibrated stimuli and the calibration front end. Clone with `--recurse-submodules`, or run `git submodule update --init` after the fact. It is **optional at runtime** — MABR launches and acquires without it, and everything that needs it is gated on `mabr.stim.stimgenAvailable`. Note stimgen is GPL-3.0 while MABR is proprietary; the submodule stores only a commit pointer, so no GPL source enters this tree, but distribution is a decision worth making deliberately (both repos are the same author's).

The acquisition app was **rewritten ground-up** into a single `+mabr` namespace (see `MABR Complete Refactor — Ground-Up Rewrite.md`). The legacy `+abr` package was retired at cutover and is recoverable from git history / the `master` branch.

## Running & developing

- **Launch the app:** run `MABR` from the MATLAB command window. `MABR.m` genpath-adds every subfolder (except `.git`) and opens `mabr.ui.App`.
- **Requires** (see `mabr.Config.RequiredToolboxes`): MATLAB ≥ 9.11 (R2021b — `uitoolbar` on a `uifigure`), Signal Processing ≥ 8.1, Audio Toolbox ≥ 1.5, DSP System Toolbox ≥ 9.1, **Parallel Computing Toolbox** (new — the acquisition engine runs on a parpool worker). Audio I/O expects an **ASIO** device via `audioPlayerRecorder`.
- **Verification (no hardware):** `tests/run_all_verifications.m` runs the suite — engine loopback, `.abr` round-trip through the offline pipeline, legacy import, and the online-advance early-stop. Individual scripts: `verify_play_plan`, `verify_engine_loopback`, `verify_data_roundtrip`, `verify_legacy_import`, `verify_online_advance`, `verify_artifact_rejection`, `verify_filters`, `verify_compute_worker` (the publish buffers, a worker-served run, bit-identical parity, priorities, the metrics worker, and a DSP worker lost mid-run — the worker parts **skip and pass** where the pool cannot hold three workers), `verify_stimulus_alignment`, `verify_progress_monitor`, `verify_metric_plot`, `verify_trace_organizer`, `verify_trace_inspector`, `verify_notes`, `verify_audio_settings`, `verify_stimgen_import`, `verify_stimulation_only`, `verify_timing_selftest`, `verify_timing_loopback`, `verify_test_runner`. All run in TESTING loopback mode with no audio device. `verify_stimgen_import` **skips and passes** when the `external/stimgen` submodule is absent — a suite must not fail over an optional dependency nobody fetched. The same suite runs from the GUI — **Help ▸ Verification Tests…** (`mabr.ui.TestRunner`), which discovers the scripts rather than listing them. `verify_stimulus_alignment` is the one that tests the correspondence every other number rests on — that the samples recorded at the onset a timing pulse marks **are** the stimulus the schedule placed there. Its bank is built so each condition is identifiable from its own samples (one frequency per column of the design, one amplitude per row, both frequencies chosen to survive the decimation *and* the display low pass), which turns "is this attributed correctly?" into arithmetic: a mean sweep must peak at its own `Frequency`, and a 30 dB step must come back as a 31.62× amplitude ratio. In loopback the DAC frame *is* the ADC frame, so it asserts the strongest form available — recovered onsets sample-exact against `ExpectedOnsets`, and the recorded samples at each onset bit-identical to that stimulus's waveform times its polarity. It covers the plan, the recording, de-interleaving into `Block`s, the online metrics (through `evaluateJobs` *and* a real `MetricPlot`), the live per-condition statistics, alternating polarity, and the same run again through the compute workers. It is **also a rig diagnostic**: `verify_stimulus_alignment('Testing',false)` streams through the real device, where it asserts a *constant* onset offset (reporting the loop-back latency) rather than zero and skips the bit-exact waveform comparison, since what returns through a converter is not what went out.

`verify_timing_loopback` is also the rig **diagnostic**: run it with `'Testing',false` to characterise the real loop-back (pulse recovery, latency, jitter, clock drift, amplitude margin against the hard-coded 0.1 detection threshold), sweep `'PulseRate'` to find where a device starts dropping pulses, and use its `'Corrupt'` option to confirm those measurements actually respond to a known defect.
- **Verbosity/logging:** code logs through `mabr.log.vprintf(level, [red], fmt, ...)` gated on global `GVerbosity` (-1…3). `mabr.log.vprintf(0,1,...)` prints a critical message in red. Logs also go to `.error_logs/`. stimgen's messages land in the same place: `mabr.ui.App` installs a `mabr.log.StimgenLogSink` (stimgen's `LogSink` host seam, via `stimgen.util.logSink`) at startup when the submodule is present, so stimgen forwards through `mabr.log.vprintf` instead of writing its own daily file under tempdir — one log per session, one verbosity setting (both packages already gate on the same `GVerbosity` global).
- **The wiki is not in this repo.** The user/developer wiki lives *only* in the separate GitHub wiki repository (`git clone https://github.com/dstolz/MABR.wiki.git`), which is what the app's Help ▸ MABR Wiki opens. A `wiki/` source folder used to be mirrored here; it drifted out of step with the published pages and was removed — edit the wiki clone and push it, and do not recreate a copy in this tree. Repo-side prose stays in `docs/`. Note wiki links inside a Markdown table need the pipe escaped (`[[Title\|Page]]`) or the cell splits and the link never forms.

## MATLAB conventions used here

- `+mabr/` is the **package namespace** — everything is `mabr.Thing` / `mabr.subpkg.Thing`. Subpackages: `+acq` (acquisition engine), `+compute` (the signal processing between the ring buffer and everything that looks at it, and the two optional workers that run it — see the compute-workers section), `+data` (data model + IO), `+stim` (stimulus adapter + advance criteria), `+metrics` (small tested functions, plus `+metrics/+online` — the per-condition metrics the online analysis window plots, and the one struct they are all called with), `+ui` (GUI), `+log` (logger). `mabr.pool` is a top-level package function: the parallel pool MABR's workers run on, made the right size *before* the first worker launches (a pool cannot be resized once the acquisition loop is on it), from the compute-worker preference.
- `mabr.Config` is a plain **value** object (NOT a superclass) holding the streaming constants (`frameLength=1024`, `maxInputBufferLength=2^26`) and the runtime/error-log paths. Nothing inherits from it. `DACSampleRate` is the one thing on it that is not a constant: `mabr.Config(fs)` builds one at a rate other than the 192 kHz `DefaultDACSampleRate`, and the property is **immutable** — a Config is a value object half the toolbox keeps a copy of, so changing a rig's rate means building a new one and handing it out (`mabr.ui.App.applySampleRate`), never mutating one copy while the rest go on believing another clock. The rate itself is a *setting* and lives in `mabr.AudioSettings.SampleRate`; `AudioSettings.config()` is the single place it becomes a Config. **`ADCSampleRate` is derived, not chosen**: `mabr.metrics.extract_sweeps` windows the ring buffer with a colon *stride* and `finalize_run` resamples `1:df`, so the analysis rate can only ever be the DAC rate over a whole number. `decimationFor` picks the integer landing closest to `ADCTargetRate` (12 kHz) — so 192/96/48 kHz all give exactly 12 kHz while the 44.1 kHz family gives 11.025 kHz, an honest rate a stride can reach rather than a round one it cannot. `SupportedSampleRates` is what the dialog's picker offers, deliberately not a restriction (`validateSampleRate` accepts any positive rate at or above the analysis rate, since a box may run at one nobody listed).
- `mabr.ArtifactPolicy` is the other top-level value object: the artifact criterion (`none`/`voltage`/`rms`), its thresholds **in volts** (defaults ±100 mV peak, 30 mV RMS), and `Repeat`. `loadPrefs`/`savePrefs` persist the user's choice in MATLAB prefs (group `MABR`), so a rig keeps whatever suits its electrode chain; `toStruct`/`fromStruct` are the same fields as a plain struct, forgiving of a missing/invalid field the same way `loadPrefs` is, and back `mabr.ui.App`'s save/load **configuration** file (see GUI section) rather than the "last used" pref. `mabr.ui.App` edits one and hands it to the controller at Start **and on every later change** — the artifact controls are deliberately left live while a schedule runs (see `App.applyArtifacts`), since the criterion is only decided at finalization.
- `mabr.FilterPolicy` is the third top-level value object: the **display** filter chain, as three independent switches — high pass (10 Hz), low pass (3000 Hz), notch (60 Hz, 4 Hz wide) — plus a shared Butterworth order clamped to `[2 8]`. `design(Fs)` caches the `digitalFilter` chain in the object and `apply(x)` runs it zero-phase (`filtfilt`, column-wise) — so the realized response is |H|², corners at −6 dB, which is what `response(Fs)` reports and the dialog draws. `apply` on an undesigned policy returns its input, the same opt-in rule `Recording` follows, and a signal too short to `filtfilt` passes through rather than throwing (a truncated sweep must not kill the live view). `loadPrefs`/`savePrefs` persist it in the same `MABR` pref group; `toStruct`/`fromStruct` (deliberately excluding the cached `Designs`, same as `sameSettings`) are the configuration-file counterpart. It is called *display* filtering advisedly: it decides what a plot or a metric is computed from and never touches `Recording.Data`, which is what `io` writes — so no setting here can reach a `.abr` file, and there is no wrong moment to change one.
- `mabr.AudioSettings` is the fourth top-level value object: the ASIO `Device` name, the `PlayerChannels`/`RecorderChannels` mapping that `mabr.stim.Schedule.renderSpec` and `mabr.acq.worker_loop`'s `prepare_device` have always accepted but the GUI never exposed a way to set, `MicChannel` — the input the calibration microphone is patched to, deliberately **separate** from `RecorderChannels(1)` because acquisition records an electrode where calibration records a mic, two patchings of one device and therefore two settings (only `mabr.stim.CalibrationAdapter` reads it; nothing about it can reach a `.abr`) — `Testing` — the loopback (no hardware) switch, moved here from the main window because it is meaningless without an opinion about which device it is overriding — and `StimulationOnly` (see below). `loadPrefs`/`savePrefs` persist all five in the same `MABR` pref group, so a rig keeps whatever mode, device, and wiring suit it across restarts; `toStruct`/`fromStruct` do the same for the configuration file. Unlike `ArtifactPolicy`/`FilterPolicy` it is a **config** control, not a live one — `mabr.ui.App` locks its Settings menu item for the duration of a schedule (see `configControls`), because the worker's `audioPlayerRecorder` is already open on whatever device (or lack of one) `Start` handed it, and `AcqController.start` re-verifies the timing loop-back (`verifyTimingLoop`) whenever `Schedule.Device`/`PlayerChannels`/`RecorderChannels` change between runs; `mabr.ui.App.ensureController` rebuilds the worker whenever `Audio.Testing` differs from the running controller's, the same way it always compared the old checkbox. **`SampleRate`** is the setting with the longest reach and the reason `config()` exists: it is the rate the ASIO device is opened at, and therefore also the rate every stimulus must already be rendered at (`StimulusSet` refuses any other) and the rate the ring buffer is clocked at. Committing a change to it is consequently not a device edit — `App.applyAudioSettings` rebuilds `app.Config` from it (`applySampleRate`), re-renders the bank at the new rate (`retuneStimuli`), and `ensureController` rebuilds the worker, because the controller captured its Config at construction and every rate it reasons with (the live decimation stride, the filter design rate, `finalize_run`'s resample, the `Session`'s stored rates) comes off that copy. `retuneStimuli` regenerates the bank from its own `Source` — `demoStimuli` rebuilds, a stimgen bank re-synthesizes *from parameters*, which is exactly why `fromStimgen` never takes a cached `Signal` — and where there is no source to regenerate from (a bank built live in the designer and never saved) it leaves the waveforms alone and says so, because silently resampling somebody's calibrated bank is a worse answer than asking for it again; `mabr.stim.Schedule`'s constructor then refuses to plan against the mismatch (`mabr:stim:Schedule:sampleRate`) and the bank label turns red, since `renderSpec` sends the *bank's* rate to the device while the controller decimates by the *Config's* — two clocks, not a rounding error. The analysis rate is **not** a second setting (see `mabr.Config`). Asking for a rate is not getting one, which is what `probeSampleRate` is for: it briefly opens a real device at *this object's* `SampleRate` and reports what the driver granted, a *determination* rather than a setting — and it opens the *same class* the worker would (an `audioDeviceWriter` under `StimulationOnly`), since probing full-duplex would fail on exactly the input-less hardware that mode exists for. `availableDevices` wraps `getAudioDevices(audioPlayerRecorder)` and never throws, since it feeds a settings dialog, not a start-up check.

  **`StimulationOnly`** is the fifth setting and the one that changes what MABR *is* for a run: playback and the timing pulse go out, and **nothing is recorded**. It exists for rigs where another system does the recording, or none does. `worker_loop`'s `prepare_device` opens an output-only **`audioDeviceWriter`** rather than an `audioPlayerRecorder` whose input is discarded — that is what lets the mode also run on hardware with **no input channels at all** — and `stream_block` skips `rb.writeFrame` while the device clock still paces the loop. Both play columns are still emitted: a timing pulse is as much an output as the signal, and something downstream may well be reading it. It is mutually exclusive with `Testing`, which opens no device at all and therefore wins everywhere; `AudioSettingsDialog` greys the `stimCheck` under `Testing` and `readControls` reconciles the pair, and under stimulation only it greys just the *input* half — the recorder channels and the mic — while device, player channels, and Test Device stay live. Unlike `Testing` (baked into the worker at `parfeval` time, so changing it forces an `ensureController` rebuild) this flag rides **per block in the render spec** (`Schedule.StimulationOnly` → `renderSpec`), which costs nothing because `prepare_device` rebuilds the device on every `Prep`. Client-side, `AcqController` drops the whole recording half: `start` skips `verifyTimingLoop` (there is no input to loop back to, so requiring one would make the mode unusable), `on_engine_state` never starts the live timer, and `on_block_completed` skips `finalize_run` entirely — **no `Block`, no `BlockReady`, no `.abr`**.

  What it does *not* drop is the record of what was played. `AcqController.log_stim_run` is the stimulation-only counterpart of `finalize_run`: one **`.stimlog`** per run (`mabr.data.io.writeStimLog`, same MAT-file-with-a-distinctive-extension convention as `.abr`/`.torg`/`.mabrcfg`, holding one `MABR_StimLog` struct), carrying every presentation in play order — stimulus index and ID, polarity, onset sample and time — plus the bank's parameters flattened exactly as a `.abr`'s `SIG` is, and the schedule settings behind them. Nothing is recorded, but *what was presented* is still the experimental record, and on a rig where another system does the recording it is the only thing that can align the two: the onsets are the rendered ones, and the same play matrix puts a timing pulse at each of them. The onsets come from `renderSpec`'s `ExpectedOnsets` (there is no input to recover them from) and are honest about early stops — `worker_loop` now reports how many play-matrix samples actually went out (a `'streamed'` message, sent *before* the `Completed` state so a `BlockCompleted` listener already has it; `Engine.LastStream`), so a run cut short by Advance/Abort writes the whole plan with the unreached presentations flagged `Presented = false` rather than a truncated one or a lie. `BlockSaved` fires for the file (the event means "a file was written"; the extension says which kind), and `Schedule.recordRun` is fed the presented counts so the plan's bookkeeping is as true here as for a recorded run. The schedule-advance tail runs as always, so the plan drives itself to `SchedComplete` exactly as it would with a recording attached. Covered by `tests/verify_stimulation_only.m`.

  The mode also **re-labels the worker**. `mabr.acq.Engine.Role` (`'acquisition'` / `'stimulus'`, → `WorkerName`) names it in every startup message and log line, because a worker that records nothing is not an acquisition worker and the log saying otherwise is misleading in exactly the mode where the user most needs to be sure. `AcqController.workerRole(stimOnly)` is the one place the mapping lives; `App.ensureController` passes it at construction and `AcqController.start` calls `Engine.setRole` for each run, since one worker is reused across runs that may switch modes between them (`setRole` logs the change — "the worker" in a log must not silently be two different things). `worker_loop` says which device class it opened and tags a stimulation-only block as it streams.

## Architecture: parpool-worker acquisition engine (`+mabr/+acq/`)

The load-bearing subsystem. Acquisition runs on a **1-process parallel pool worker** launched once per session with `parfeval`, keeping the pool and `audioPlayerRecorder` warm. Control/state flow over **parallel queues**; recorded samples flow through **one** memory-mapped ring buffer. This replaces the legacy two-`matlab.exe` design (spawned via `system(...)`, Wmic PID checks, `info.mat`, `dac.wav` handoff, `mabr_com.dat` command/state memmap).

- `mabr.acq.Engine` (client, GUI process) — starts/keeps the pool warm, launches the worker, owns the read-only ring buffer, and turns worker messages into **events** (`StateChanged`/`BlockCompleted`/`WorkerError`) via a `DataQueue` `afterEach` callback. **No busy-waits.**
- `mabr.acq.worker_loop` (runs ON the worker) — owns the `audioPlayerRecorder`, **synthesizes the stimulus frame-by-frame** from the `mabr.stim.PlayPlan` the Prep message carries (`PlayPlan.range(i,hi)` per frame — the run's waveforms, onsets, stimulus indices and polarities, never a whole play matrix; see the stimulus-adapter section), writes recorded ch1/ch2 into the ring buffer, and polls a `PollableDataQueue` every frame for `Prep`/`Run`/`Pause`/`Stop`/`Kill`. `PlayPlan.fromSpec` is the one place it decides between a `Plan` and the explicit `PlayMatrix` a hand-built block (the timing self-test, the tests) still carries. A **TESTING loopback** mode (`Engine(cfg,true)`) runs the whole engine with no hardware.
- `mabr.acq.RingBuffer` — thin wrapper over the retained memmap surface: `ring_signal.dat` + `ring_timing.dat` (single, `maxInputBufferLength`) plus a small `ring_header.dat` write-head header. Worker writable, client read-only.
- Enums `mabr.acq.Cmd` (client→worker commands) and `mabr.acq.State` (worker→client state) travel as messages, not shared memory. `Cmd.Release` (+ `Engine.releaseDevice`) closes the audio device while keeping the worker and warm pool alive. It exists because the worker opens its `audioPlayerRecorder` on the first `Prep` and holds it until `Kill` — that is what keeps block-to-block latency down, but an ASIO device has exactly one owner, so **"controller idle" does not mean "device free"**. Without it, the first calibration after any acquisition could not open the device and the only remedy would be restarting MABR. The next `Prep` reopens it.
- Because commands are polled every frame, the engine can honor an **online advance criterion** — stopping a block early when a correlation threshold is met (the capability the legacy code documented it could not provide).

Sweep extraction moved to `+metrics`: `mabr.metrics.find_timing_onsets` (pure function on a timing vector) and `mabr.metrics.extract_sweeps` (explicit cursor state, reads the ring buffer) — direct analogues of the legacy `abr.Runtime` methods. **The slice boundary between them is load-bearing.** `find_timing_onsets` reports an onset at sample 1 of a vector that starts above threshold, which is correct for a vector read on its own and wrong at `extract_sweeps`' incremental boundaries, where it is the middle of a pulse already counted. The shadow interval cannot be relied on to remove that duplicate — a timing pulse spans its whole *presentation* (5–8 ms), routinely longer than the 2 ms shadow — so `extract_sweeps` reads the single sample *before* the slice and drops the onset when it was already above threshold. Without that check a slice boundary landing more than the shadow into a pulse inflates the live sweep count and, because the k-th onset is paired with the k-th planned presentation, shifts every later sweep onto the wrong condition (measured at **56 sweeps for 48 presentations** — 17% — in `verify_stimulus_alignment` Part F, which is the regression test). It only ever affected the live path: `finalize_run` reads the whole block in one call, so saved `.abr` files were never wrong. `mabr.metrics.error_band` and `mabr.metrics.t_quantile` are the live view's SD/SEM/CI band arithmetic and a toolbox-free Student-t inverse CDF, kept out of the UI because they are claims about data rather than drawing. `error_band` is two lines over **`mabr.metrics.band_from_stats`**, which takes the standard deviation and the sweep count instead of the sweeps — term for term the same arithmetic in the same order, so a view holding only a condition's statistics (the live view, once the DSP has run in another process) draws the same band, to the bit.

`mabr.acq.Engine.set_priority` sets a process's scheduling priority through .NET (`System.Diagnostics.Process.PriorityClass`) rather than the legacy `wmic` call: `wmic` is a deprecated Feature-on-Demand that Windows 11 24H2 and later no longer install by default, and it had been failing silently (caught, logged at level 1). The acquisition worker runs `high priority`; the compute workers below it (see the next section).

## Compute workers (`+mabr/+compute/`)

Every computation MABR makes from recorded samples while a schedule runs lives in **`mabr.compute.Pipeline`** — sweep extraction, the display filter chain, the artifact preview, the onset-contrast correlation, the per-condition running mean/SD/counts, and the finalization DSP (`finalize`: read the block, `resample`, split by stimulus, filter, judge) — lifted out of `AcqController`'s live tick and `finalize_run` so that **one object** can be stepped by a worker process or, with no worker, by the controller itself. A controller built without workers — which is what every verification script builds — is the in-process path *by construction*. The pipeline is **incremental and exact**: `extract_sweeps` already caches the raw windowed sweeps, so `Pipeline` keeps a parallel *filtered* cache and passes only newly windowed sweeps through `filtfilt`, which is bit-identical to filtering the whole matrix (`FilterPolicy.apply` is column-wise; both artifact criteria judge a sweep on its own samples) and turns a cycle's cost from O(all sweeps) to O(new sweeps). `configure` mid-run refilters the cache on a chain change and re-judges it on an artifact-policy change. `step` returns **sufficient statistics, never sweeps** — the latest sweep, `R`, the counts, and per condition the mean, SD and counts — because every band the live view draws is a function of `(mean, SD, n)`; `sweeps()` is there for the consumers that need the matrix. `mabr.compute.ConditionStore` and `mabr.compute.evaluateJobs` are the online-analysis table and its evaluation loop, lifted out of `MetricPlot` for the same reason.

Two optional workers run it, launched on the same parallel pool as the acquisition worker by **`mabr.compute.ComputeEngine`** (the client facade, shaped like `mabr.acq.Engine`) and both executing **`mabr.compute.compute_loop(root,queue,role)`** — one function, the `Engine.Role` idiom — with the same handshake / `PollableDataQueue` command / `DataQueue` state-and-error protocol as `worker_loop`:

- **The DSP worker** (`role = 'dsp'`, `below normal` priority) steps its pipeline over the acquisition ring buffer every `LivePeriod` (50 ms) while a run is in progress and publishes the statistics to `mabr.compute.LiveBuffer`; at the end of a run it performs the finalization DSP on `Cmd.Finalize` and replies with a `'finalized'` message carrying plain `parts`.
- **The metrics worker** (`role = 'metrics'`, `idle` priority, launched **lazily** by the first analysis window) steps its *own* pipeline over the same ring every `MetricPeriod` — the online metrics need the sweep matrix, which the live surface deliberately does not carry — keeps the session's condition table (`Cmd.AddCondition` per finalized block), evaluates the requested metrics (`evaluateJobs`, time-boxed between conditions) and publishes to `mabr.compute.MetricBuffer`. **This is the process user-supplied metric functions run in**, so a hung one costs its window and nothing else: the client watchdog cancels and relaunches the worker once, drops every custom metric (there is no telling which hung), flags their slots, and a window whose slot is flagged evaluates nothing in-process — a hang in the GUI is the one outcome the third worker exists to prevent.

Neither worker talks to the other; both derive from the same ring bytes under the same `Cmd.Configure` (rate, window, both policies as their `toStruct` forms — re-sent from `set.Filters`/`set.Artifacts`), so their verdicts agree by construction. **The rate is not optional**: a compute worker needs it for the decimation stride and the filter design, so it builds `mabr.Config(fs)` from `Configure` and steps nothing before one arrives. `tests/verify_compute_worker.m` asserts the worker's statistics and finalization are **bit-identical** to the in-process pipeline over the same ring, and that a controller served by the DSP worker never steps its own (`Pipeline.StepCount` stays at 0).

The bulk traffic is memory-mapped, as the ring buffer is, through **`mabr.compute.PublishBuffer`** — one base class holding the discipline: every payload field exists in two halves (encoded in the field's shape, `[2m x n]` or `[m x 2]`, never a third dimension); the writer fills the idle half, flips `Half`, bumps `Seq`, in that order; a reader reads `Seq`, the half, `Seq` again, and keeps its previous payload if `Seq` moved. The `Seq` re-check is the correctness guarantee, the halves the fast path; readers slice rows and never read the file (~17 MB live, ~30 KB metrics). `LiveBuffer` (DSP → client), `MetricBuffer` (metrics → client) and `RequestBuffer` (client → both: cadences and the per-slot job table; a custom metric's function handle travels over the queue instead, since it cannot live in a memory map) supply the layouts; `Config` supplies the paths (`compute_*.dat` beside the ring files) and the sizes (`MaxComputeSamples`/`Conditions`/`Jobs` — a window or run over them is refused, never truncated). A worker publishes on **every** cycle, sweeps or none (`Pipeline.emptyStats`), so a `Seq` that has not moved for far longer than the cadence is the one thing a wedged worker and a live one do not share. `LiveBuffer.read()` returns exactly `Pipeline.step()`'s struct, which is what lets the controller's tick be the same code either way.

**Degradation is per role, and stale is not absent.** `ComputeEngine.hasDSP()`/`hasMetrics()` say whether each worker is up — never launched, not yet handshaken, or declared dead by the watchdog — and every consumer checks before it asks: a controller without a DSP worker steps its own pipeline (a worker that dies mid-run is covered on the next tick, since the in-process pipeline follows every run too), an analysis window without a slot evaluates in-process. A consumer that merely finds no new publish keeps its last values with a note, because computing in-process the moment a worker is slow would reproduce the overload the workers exist to remove. The watchdog rides the consumers' own polls (no timers): silence is judged only *after* reading the sequence word — a run's preparation can take seconds between `runStart` and the first tick while the worker heartbeats throughout. A wedged worker is `cancel`-ed and relaunched **once**, with what it missed replayed at its handshake (the last `Configure`, the run in progress, the conditions, the custom metrics); if the fresh handshake never arrives the role is written off for the session and the status line says so. The pool is never deleted or recreated mid-acquisition. The workers are a **preference** (`MABR`/`ComputeWorker`, default on; `Settings ▸ Background compute workers`, a `configControls` entry) because they decide the pool's size, which `App.ensureController` sets through `mabr.pool(3 or 1)` before building a controller; a pool that cannot be resized (busy, or the profile too small) costs the workers for the session, never the acquisition.

Finalization on the DSP worker is **asynchronous**: `on_block_completed` sends `Finalize` and returns with `ProgState` in `BlockComplete`; the reply (`on_finalized` → `assemble_blocks` → the `after_finalize` tail) or a single-shot timeout (`FinalizeTimeout` plus a per-sample allowance → finalize here from the ring, which nothing overwrites until the next `Run`, and report the worker as stalled) moves the plan on. The GUI stays responsive across the block boundary. `assemble_blocks` is the half only the GUI process can do — `Recording`/`Block` assembly, polarity, notes, `computeMetrics`, `Session.addBlock`, `writeABR`, the events, `recordRun`/`appendMakeup` — and it adopts each part's filtered trace through **`Recording.withProcessed`**, so no consumer of a `Block` ever filters the trace again.

## Core data model (`+mabr/+data/`)

- `mabr.data.Recording` (value type) — one channel's `SampleRate` + `Data` + `SweepOnsets`/`SweepLength`, with `SweepData`/`SweepMean`/`noisePower`/`SNR` ported from the old `abr.Buffer` but **cycle-free** (no `ABRobj` back-reference; decimation passed explicitly). Filtering is **explicit** and lives in a `mabr.FilterPolicy` held in `Filters` — the same object the GUI edits and the live view applies, so what the operator watches and what a `Block` reports come off one set of corners. `designFilters()` designs it at the Recording's own `SampleRate`, after which it is applied consistently in segmentation (the legacy designed but never applied it); before that call `ProcessedData` returns raw `Data`. `ProcessedData` is **cached**: `designFilters()` runs the chain once into a private `Processed` (or `withProcessed(x,policy)` installs a trace filtered elsewhere — the DSP worker's — after checking the policy asks for the same chain), and `set.Data`/`set.Filters` clear it. Every descriptive accessor (`SweepData`, `CleanSweepData`, `NumSweeps`, `SweepMean`, `noisePower`/`SNR`/`RMS`) starts from `ProcessedData`, and without the cache each of them ran `filtfilt` over the whole trace again — one finalized block cost five or six passes between `finalize_run`, `Block.computeMetrics` and the viewers. `to_struct` and `io` never see it. `Data` is never filtered in place and `io` saves `Data`, so a `.abr` file is always the raw trace. `IsArtifact` flags rejected sweeps (aligned with `SweepOnsets`, **not** with `SweepData` — map through the `ValidSweeps` mask, since a truncated run's last window is dropped from `SweepData`); flagged sweeps are excluded from everything descriptive — `CleanSweepData` is the basis of `SweepMean`, `noisePower`/`SNR`/`RMS` and `Block.computeMetrics`, while `SweepData` still returns every sweep — but never removed from `Data`. With *every* sweep flagged, `SweepMean` is all-NaN (there is no mean to report) and viewers skip it.
- `mabr.data.Block` (value) — one condition's result: stimulus metadata + the recorded `Recording` + computed metrics + start time + `SweepPolarity` (+1/-1 per sweep, aligned with `ADC.SweepOnsets`).
- `mabr.data.Session` (handle) — subject/device/rate config + block queue + array of `Block` results.
- `mabr.data.SessionNotes` (handle) — the **rig notebook**: a store of timestamped free-text notes ("ear plug slipped", "impedance 3.2 k") that the operator writes *while it is happening*, and that is then saved with the data. It is the data half of the notes component; `mabr.ui.Notes` is the view, and any number of views can be open on one store because every change fires `NotesChanged` and each view redraws from the store rather than its own copy. What a note is stamped with is the point: a wall clock alone does not say *where in an experiment* something happened, so a note committed during a run carries the run and the sweep count too — `[R02 S0128 09:17:05] ear plug slipped`, against `[09:03:11] impedance 3.2k` for one taken while nothing is acquiring (there is no run to name, and inventing one would be worse than saying the time). The acquisition context comes from `ContextFcn`, which `mabr.ui.App` points at `mabr.ui.AcqController.noteContext`; that method leaves `Run`/`Sweep` NaN unless a run is actually under way, and `Sweep` is the count within the *current run*, the same number the Run panel shows. `ContextFcn` is called inside a `try` — a stale controller costs a note its run number, not the note. Notes are saved **whole into every file** rather than split across them (`ABR_Data.Notes` via `Block.Notes`, `MABR_StimLog.Notes`, `View.Notes` in a `.torg`), so no file depends on another to be read and a session recovered from one surviving `.abr` still has its notebook. `JournalFile` is the other half of that: every commit rewrites the entire log to it as **plain text**, deliberately *not* a MAT-file like the rest of MABR's outputs, because the whole reason the journal exists is to survive a crash and a format needing MATLAB to read is the wrong one for that (`fromFile` reads one back). `setFromLog` is what the view's editable mode writes back — it re-parses `[stamp] text` line by line and keeps each surviving line's original record (time, run, sweep) intact, claiming each old note at most once so two notes committed in the same second cannot collapse onto one. `Session.Notes` holds the store (never as a property default — a handle default is evaluated once at class load and would be the *same* store in every `Session`) and `Session.noteRecord()` is the safe accessor the writers use.
- `mabr.data.io` — save/load. `writeABR` emits an offline-compatible `ABR_Data` struct and matching filename; `importLegacy` reads old `ABR_Data` structs (incl. sigProp-style SIG) into the new model. `writeStimLog`/`buildStimLog` emit the `.stimlog` a stimulation-only run produces in place of a `.abr` (see `AudioSettings.StimulationOnly`); both filename builders share one `subjectToken`, so a session's files sort together whatever it wrote.

## Stimulus adapter (`+mabr/+stim/`)

MABR **does not** generate signals or calibrate — an external package supplies precomputed, calibrated waveforms as a plain struct array where **each entry is one presentation**: `signal` (required), `ID` (required), optional `SampleRate`/`Repetitions`/`Timing`/`alternatePolarity`/`informativeParams`, and any number of passthrough fields. `mabr.stim.StimulusSet` wraps and validates it; `mabr.stim.demoStimuli` is a built-in tone-pip bank for testing only.

`informativeParams` is the one addition the stimgen work forced. Left absent, MABR infers the list — every numeric scalar extra — which is right for a hand-built bank whose only extras *are* its parameters. A generator emits far more than that (a stimgen `Tone` variant carries `Duration`, `WindowDuration`, `OnsetPhase`), and every name on that list becomes a **grouping dimension** in the offline pipeline, so a source that knows which of its parameters actually vary now says so instead of letting MABR guess from types. `StimulusSet.paramTable(idx)` is the read side of that list: the parameters a set of entries shares, their values as an `[nStim x nP]` matrix, which of them vary across *that* subset, and the units (`kHz`/`dB` for the two the toolbox fixes by name end-to-end, `''` for everything else rather than a guess). Pass a **run's** stimulus indices, not the bank's — a bank varying Frequency and Level holds one condition per blocked run and neither varies within it, and the question a live view asks is about the run. Only numeric scalars are tabulated: it is a table of dimensions to sort, group, and shade by, and a name with no order over its values cannot do any of those; the full metadata of an entry is still `meta()`, which now shares one `informativeNames` rule with it. `StimulusSet` also carries a `Source` struct (`Kind`/`File`/`Calibration`/`Generated`) and an `isCalibrated()` — provenance, not contract: nothing in acquisition reads them, but a calibrated bank and the demo bank are otherwise indistinguishable once they are struct arrays, and that is exactly the confusion worth being unable to have.

**stimgen is the suggested source** (`external/stimgen`, optional — see `mabr.stim.stimgenAvailable`). `mabr.stim.fromStimgen` converts a `.spl` bank file, a live `stimgen.StimPlayer`, a `StimPlay`, or a bare `StimType` into a `StimulusSet`. Three things about it are load-bearing:

- **One stimgen *variant* is one MABR entry.** A vectorized property expands into variant combinations — a `Tone` with `Frequency=[8000 16000]`, `SoundLevel=[30 60]` is four variants — which is already MABR's unit. The conversion flattens `StimPlayer.StimPlayObjs` → `StimPlay.StimObj` → variants and reinterprets nothing.
- **Regenerated, not resampled.** `StimType.Fs` defaults to 97656.25 (a TDT rate); MABR sets `Fs = Config.DACSampleRate` on a `copy()` and calls `update_signal()`, so each variant is synthesized natively at 192 kHz. This is why the importer takes *parameters* and never a bank's cached `Signal`.
- **`VariantReselectOnUpdate` must be forced false first.** With it at its default, every `selected_value()` call *outside* an update cycle silently re-runs the selector and advances the active index — so metadata read back after `set_variant_index` describes a *different* variant than the `Signal` just generated under it, and an 8 kHz waveform gets saved labelled 16 kHz. The signal is always right; it is the description that drifts. `verify_stimgen_import` FFTs each waveform against its own label to catch exactly this.

Deliberately dropped on import: `StimPlay.ISI`, `StimPlayer.ISI`, `SelectionType`, `StimOrder`. MABR owns presentation and `mabr.stim.Schedule` decides it. `Schedule` does now have a `[min max]` jitter range of its own (`ISIMode`/`ISIRange`), so stimgen's ISI *could* be carried across — it still is not, because the timing is the operator's setting for this session and adopting a bank must not silently retime a schedule already configured around it. `Reps` survives as the starting repetition count **unless the host hid the field**: `fromStimgen`'s `repsHidden` reads a live player's `ControlVisibility.Reps`, and a hidden control means the number is `StimPlay`'s default (20) rather than anyone's choice — 20 sweeps is not an ABR — so it imports as *no opinion* and `Schedule.startingRepetitions` supplies 512. A `.spl` read from disk carries no such tell and is taken at its word. Two unit reconciliations happen in one place (`buildEntry`): stimgen's `SoundLevel` → `Level`, and `Frequency` Hz → kHz, because `mabr.data.io.buildFilename` reads both by name and unit to match the offline regex.

**An uncalibrated stimgen bank is the sharp edge.** `apply_calibration` is a no-op with no calibration loaded, so `SoundLevel` never reaches the amplitude and a 30/60/90 dB series would be three *identical* stimuli. Absolute SPL is unknowable without a measurement, but the spacing is not — dB is a ratio — so `fromStimgen`'s `relativeLevels` pass rescales an **entirely** uncalibrated bank relative to its own loudest entry (`10^(ΔdB/20)`, recorded per entry as `LevelScale`, which passes through to the `.abr`). The reference is the top of the bank, never a fixed dB, so the loudest waveform is left exactly as stimgen normalized it and this can only ever *attenuate* — no bank acquires a clipping risk it did not already have. A **partly** calibrated bank is left untouched: half its volts are real and there is no common reference to be relative to. Either way `Calibrated` stays false and `App` warns rather than refuses — an amber bank label, and a `uialert` on adopt naming which of the two cases it is (`warnUncalibratedLevels` branches on the presence of `LevelScale`). Covered by `verify_stimgen_import`, which asserts a 30 and a 60 dB entry come back exactly 30 dB apart.

Also: `stimgen.StimCalibration.loadobj` used to throw (it assigned the read-only `Engine.MicSensitivity`; fixed at the current submodule pin — it restores through `Engine.restore` now), and `StimType.fromStruct` calls it unconditionally — so `fromStimgen`'s `readBank` restores the stimulus *without* its calibration and reattaches separately in a `try`. The split is kept because the isolation, not that one bug, is the point: on any `loadobj` failure (an older submodule checkout included) a bank whose calibration cannot be revived imports and reports itself uncalibrated rather than becoming unloadable. `StimType.fromStruct` also does not restore `SoundLevel`/`Duration`/`WindowDuration`/`WindowFcn` (stimgen's own `load_bank` assigns those itself), so `readBank` does too — without it a bank comes back silently at class defaults, 60 dB and 100 ms. One refusal is new with the current pin: stimgen's `apply_calibration` now asserts a **filter-type** calibration is run at the rate its FIR was designed at, and `fromStimgen` forces `Config.DACSampleRate` — so a bank whose filter calibration was measured at another rate refuses to import. `fromStimgen` translates that (`mabr:stim:fromStimgen:calibrationRate`) into what a MABR user can do: recalibrate through **Settings ▸ Calibration…** (which measures at the DAC rate) or redesign the filter with `design_filter(...,SampleRate=192000)`; the tone/click LUTs are in Hz and volts and need no re-measuring.

**MABR owns presentation, the stimulus package does not.** `mabr.stim.Schedule` turns a `StimulusSet` plus three GUI-chosen settings — `ISI` (s, onset-to-onset), `Repetitions` (per entry), and `Strategy` — into ordered *runs*, and renders each into a **`mabr.stim.PlayPlan`** rather than a play matrix: the waveforms of the stimuli the run presents, the onset list, and the stimulus index and polarity at each onset. The plan is what `Engine.prep` sends and what `worker_loop` renders a frame at a time (`PlayPlan.range(i0,i1)`), performing the same summation in the same presentation order a whole-matrix render did — so overlapping presentations are still summed, and `PlayPlan.matrix()` (tests, and `fromMatrix` for hand-built blocks such as `verifyTimingLoop`'s) is bit-identical to what `renderSpec` used to allocate. A run therefore costs the GUI process the size of its bank, not its duration, and the Prep message the same, instead of a 512 MB `[N x 2]` for a run filling the ring. The ring-buffer cap on the *recording* still stands (`mabr:stim:Schedule:tooLong`, checked before anything is built) — the worker records into a true ring that keeps only its newest lap and `finalize_run` reads it whole — so a run longer than the ring is the remaining step, not this one. Covered by `tests/verify_play_plan.m`. Strategies: `blocked`, `shuffled-blocks` (one run per stimulus) and `interleaved`, `shuffled-cycles`, `shuffled` (one run, **intermixed**). All five are permutations of a fixed multiset — each entry gets exactly its repetition count — hence "shuffled", not "random". An entry flagged `alternatePolarity` has its successive presentations multiplied by `+1,-1,+1,…` — the repetition count is *split* between polarities, never doubled, and the polarity travels with the presentation through shuffling. `renderSpec` emits `StimulusIndex` — the stimulus behind each onset — plus `Polarity`, the sign applied there — and refuses runs exceeding `maxInputBufferLength` (`mabr:stim:Schedule:tooLong`). The plan's timing channel (one unit pulse over each presentation, or the entry's own `Timing`) is synthesized because sweep extraction depends on it.

The ISI is either of two settings, chosen by `ISIMode`: the scalar `ISI` (`'fixed'`, onsets on a strict grid) or a uniform draw per interval from `ISIRange` = `[min max]` s (`'random'`, so the presentation rate carries no periodicity of its own). Both are always held, and the mode picks between them, so turning randomization off and on cannot lose the range — the GUI's checkbox *is* `ISIMode`. `renderSpec` accumulates one interval per presentation rather than multiplying a period, drawing from the schedule's own `RandStream`, so rendering never perturbs the global `rng` and a `Seed` fixes a plan's timing along with its order. Two dependent properties say which number to reason with: **`MinISI`** (the shortest interval that can occur) is what `overlaps()` and the GUI's overlap warning judge against — one short draw is enough to collide — while **`MeanISI`** is what `summary().duration` estimates from, making a randomized plan's duration an expectation rather than a promise. Nothing downstream knows or cares: the timing channel still marks every onset, so sweep extraction and every metric are indifferent to the spacing, and the realized intervals survive in each file's `ADC.SweepOnsets`. Covered by `tests/verify_isi_jitter.m` (no hardware, no pool).

`mabr.stim.CalibrationAdapter` implements stimgen's `stimgen.calibration.HwAdapter` (`sample_rate()` + `play_and_record(signal)`) against MABR's own audio path, so `Settings ▸ Calibration…` measures **this** rig: `Audio.Device`, out on `PlayerChannels(1)`, in on `MicChannel`, at `Config.DACSampleRate`. The rate is not bookkeeping — `fromStimgen` regenerates every stimulus at the DAC rate and stimgen's `design_filter` produces a rate-specific FIR, so a calibration measured elsewhere would be applied to signals it does not describe. Note stimgen's contract is `(1,:) double` both ways, so `play_and_record` transposes on the way out. It refuses in `Testing` mode (loopback would measure the excitation fed back to itself) and while the controller is non-`Idle`, and calls `Engine.releaseDevice()` once per adapter to take the device off the idle-but-still-holding worker. MABR does **not** implement `stimgen.HardwareHost` — that is a TDT/RPvds buffer protocol, and MABR owns playback through its own worker.

Advance criteria are proper implementations in `+stim/+advance/`: `num_sweeps` and a real `corr_threshold` (the legacy `abr_adv_corr_thr.m` was an empty stub). They are evaluated **only for blocked strategies** — an intermixed run pools different conditions, so early-stopping it is both meaningless and unbalancing. The GUI greys the control out accordingly.

**Artifact rejection** is *decided* at finalization. `AcqController.finalize_run` judges each sweep with `mabr.metrics.detect_artifacts` (a pure function: `voltage` = any sample outside ±thr, `rms` = sweep RMS over thr) on the **filtered** sweeps, and records the verdict in `Recording.IsArtifact`. The live path *previews* the same policy (`AcqController.live_artifacts`, on the sweeps `filter_sweeps` has already run the same chain over; with the high pass switched off it falls back to removing each sweep's own mean, since nothing else would be taking out a baseline offset) so the live mean shows the average the block will actually hold and a noisy electrode is visible while it is happening — nothing there is recorded, and re-pointing `Artifacts` just changes what the next tick previews. Once flagged, a sweep is excluded from everything **descriptive**: `Recording.CleanSweepData` is what `SweepMean` (hence the trace organizer), `noisePower`/`SNR`/`RMS`, and `Block.computeMetrics` are built on, while `SweepData` still returns every sweep. Rejected sweeps are always **marked and saved, never dropped** — `io` writes `ADC.IsArtifact` alongside `ADC.SweepPolarity` so offline analysis can override the call or use `abr_analysis/rejectArtifacts` (which instead rejects by `isoutlier` over a whole session; a fixed threshold is what the live path needs because it is decidable for one sweep as it arrives). When `ArtifactPolicy.Repeat` is set, the controller calls `Schedule.appendMakeup(counts)` to re-present what was lost. Make-up runs are **appended to the end** of the plan (a run's play matrix is rendered before streaming and cannot grow mid-flight) and hold **one stimulus each**; `Schedule.MakeupLimit` (default 1 = at most double a condition) bounds the total so a permanently noisy electrode cannot make a session run forever, and `reset()` drops them so a re-started schedule begins from what `build()` produced. Clearing `Repeat` mid-schedule is the one policy change that cannot simply wait for the next run — `AcqController.set.Artifacts` calls `Schedule.dropPendingMakeup()`, withdrawing the make-up runs not yet reached (the one in progress is kept) and refunding their budget.

## GUI (`+mabr/+ui/`)

- `mabr.ui.App` — the programmatic uifigure view (replaces `abr.ControlPanel`); `createComponents` builds five titled panels (Session / Stimulus / Presentation / Acquisition / Run) from one `panelGrid` helper and a shared `LabelWidth`, so the fields align across panel borders; panels carry explicit pixel heights because `'fit'` does not see through a `uipanel` to its nested grid (so adding a row to a panel means bumping its height in `Grid.RowHeight`). The Acquisition panel's artifact controls share **one** threshold field between the voltage and RMS criteria — they are alternatives, and `syncArtifactFields` swaps the value and its display-format caption on a mode change so each criterion keeps its own number. Below them the **Filters** row is a one-line summary plus a button: three independent filters need eight controls and a response plot to state properly, which is a window (`mabr.ui.FilterDialog`) rather than a panel row, so the row carries the whole setting in text and the button is only pressed to change it. Both groups are in `liveControls` — they stay enabled while a schedule runs and are re-derived by `transport()` in both directions, since `setBusy` kills them on the way in. The Presentation panel's ISI row is followed by a **Random** checkbox and the `[min max]` ms bounds it governs (`Schedule.ISIMode`/`ISIRange`), sharing one row in the field columns the way the artifact-repeat checkbox does; the two settings are alternatives, so `syncISIFields` greys whichever is not in force and `transport()` re-derives it for the same reason it re-derives the advance enables — `configControls` switches all five ISI controls back on wholesale. `isiSeconds` is the single place the GUI answers "which interval", returning the minimum (for the overlap warning) and the mean (for duration estimates) so those two questions cannot be confused. The Stimulus panel's Bank row is three buttons — **Design…** / **Load bank…** / **Demo** — with stimgen leftmost because it is the suggested route. `Design…` opens `stimgen.StimPlayer` **non-modally** and the same button becomes **Adopt bank**: `StimPlayer` keeps its figure handle private so there is nothing to `uiwait` on, but non-modal is the better shape anyway — it lets the user tune, adopt, inspect in the stimulus viewer, and adjust again without reopening, matching how the viewers already behave. `hideDesignerSessionControls` then calls stimgen's own `set_control_visibility(All=false)`, collapsing the designer's Reps / ISI / sample-rate / Shuffle-Serial / preview-output / Run / Pause widgets out of its layout — every one of them duplicates a setting MABR owns (the rate is `Config.DACSampleRate`; `fromStimgen` regenerates at it regardless of what the designer shows), and the duplicates are inert (`fromStimgen` drops ISI and `SelectionType`, and the designer's Run streams through stimgen's speaker preview, not the rig the worker holds open). It is guarded on `ismethod` rather than assumed, since a rig may have the optional submodule checked out at an older commit; the per-stimulus **Play**/**Play All** preview buttons are not hideable and stay, which is right — auditioning a stimulus is the designer's job. `syncDesignButton` derives its label/tooltip/enable (and is re-called from `transport()`, since `configControls` switches it on wholesale but it must stay off without the submodule). `Load bank…` takes `.spl` or `.mat` — `StimulusSet.fromFile` dispatches on extension. The bank label now reads `12 stimuli · stimgen`, amber rather than green when uncalibrated.

A **Settings** menu (beside `HelpMenu`, built alongside it in `createComponents`) holds `Audio Device (ASIO)…`, which opens `mabr.ui.AudioSettingsDialog` over the `Audio` property (`mabr.AudioSettings`), `Calibration…`, which opens stimgen's own `CalibrationGui` over a `mabr.stim.CalibrationAdapter` rather than reimplementing it — stimgen owns calibration, MABR owns the rig — and the checkable `Background compute workers` (pref `MABR`/`ComputeWorker`, default on; `computeEnabled`/`onComputeWorkers`), a `configControls` entry that takes effect at the next Start because it decides the parallel pool's size (`ensureController` calls `mabr.pool` before building a controller, and its reuse test includes `UsingCompute` beside `Testing` and the sample rate). Unlike the artifact/filter controls both are in `configControls`, not `liveControls` — they lock for the duration of a schedule, since `buildSchedule` hands `Schedule.Device`/`PlayerChannels`/`RecorderChannels` to the controller only at `Start` and `AcqController.start` verifies the timing loop-back against whatever it was handed. The **Help** menu adds `Verification Tests…` below the wiki link, opening `mabr.ui.TestRunner`; it is a `configControls` entry too, for a blunter reason — the suite builds its own engine, worker and pool, so it cannot share the rig with a schedule in flight. Owns the presentation settings (bank, per-stimulus repetitions, strategy, ISI); `buildSchedule` is the single place they (and the `Audio` settings) become a `Schedule`, shared by the plan-summary preview and `onStart` so they cannot drift. **Start and Preview are one code path** — `onStart(preview)`; Preview hands the controller a `Session` with an empty `OutputPath`, which is already `finalize_run`'s record-without-saving route, so blocks are still acquired, finalized, counted for artifacts, and pushed to the viewers through `BlockReady` while nothing reaches disk (and the output folder does not join the remembered history). Because a preview is otherwise indistinguishable from a real run, the Run panel's title carries `PREVIEW (nothing is saved)` for as long as one is in flight. A **stimulation-only** schedule (`Audio.StimulationOnly`) gets the same treatment one notch stronger and takes precedence over it — `STIMULATION ONLY (no recording)`, since a preview acquires everything and merely declines to write it while this never records at all. `setRunTitle` decides *which* banner (from the `StimOnlyRun` snapshot, captured at Start for the same reason as `Previewing`) and the caller only says whether one is in flight. In that mode the **entire Acquisition panel is disabled** — `syncAcquisitionEnables` is the one place that decides it, retitling the panel `Acquisition — n/a (STIMULATION ONLY)` (a greyed control says "not now"; only the panel can say why) and routing through the three `sync*` functions that own those enables, since `transport()` calls them and would otherwise put the controls straight back. Those three speak only for their own *fields*, though, which leaves every row label black and the header bold — a panel that reads as live with some dead controls in it, which is the opposite of what is true — so a final sweep disables the panel as a unit, labels and title included (`ForegroundColor` greyed against the `AcqPanelFG` captured at build time, since the theme's own title colour is not the same everywhere). It runs **last** for that reason: it is the one that has to win. Coming back *out* of the mode it re-derives only the labels, which carry no state of their own — every interactive control keeps whatever verdict the `sync*` calls just reached, so an artifact threshold stays dead under `none` and Advance under an intermixed strategy. The panel's own `Enable` is deliberately unused: `uipanel` only gained one after R2021b, which `mabr.Config` still supports. Every one of them judges, stops, or displays a *recording*: an advance criterion has no running average to watch, an artifact threshold no sweep to judge, a filter chain nothing to draw (`FilterLabel` reads `n/a — nothing is recorded`). The live-plot **and analysis** toolbar buttons go with them, since the controller is handed no `LivePlot` and there is nothing for a metric to be computed from; the trace organizer stays, because it can still load a `.torg`. `syncAcquisitionEnables` is called at construction, from `transport()`, on each **Commit** in the audio dialog (`applyAudioSettings`, which is why the panel greys while that dialog is still open), and at the end of `applyConfiguration` (a restored `Audio` can enter the mode after the artifact/filter blocks above it have just re-enabled their controls from the same file). Advance is re-derived only when nothing is running, because it is a `configControls` entry that `transport()` owns. In that mode `onStart` opens **neither acquisition viewer** and hands the controller an empty `LivePlot` — there is nothing coming back to plot, and two windows that never fill are worse than none — so the Run panel's `Sweeps:`/`r =` readouts carry run progress (`Run k/N`, `no recording`) instead, written by `setRunReadout` from `onState`, since no live timer runs to fire `onMetrics`. It opens the one window that *does* fill there, `mabr.ui.ProgressMonitor` (the plan still walks itself run by run, which is exactly what that window shows), and hands focus straight back to the main window. `AudioMenuItem` is already a `configControls` entry, so the mode cannot be toggled mid-schedule. It opens **both acquisition viewers at Start/Preview** — `openViewers`, called from `onStart`, builds only the ones whose window is absent and never raises one already up — and lays them out beside itself on first run; nothing but the main window opens at launch, since there is nothing to watch until a schedule is in flight; a `uitoolbar` of pictogram glyphs (`live` = one trace on axes, `metrics` = three rising points on axes, `traces` = a stack of traces, `stim` = a loudspeaker, `progress` = three part-filled bars, a ruled notepad = the session notes, `pin` = keep on top, `help` = a question mark, all drawn through `mabr.ui.Icon` like `TraceOrganizer`'s) raises them (`live`, `traces`), opens the stimulus viewer (`stim`), opens the progress monitor (`progress`), opens the notebook, and opens the wiki (`help`). `metrics` is the one button that is not a raise: it opens **another** `mabr.ui.MetricPlot` every press (see that bullet), which is why `App` keeps an array of them and `closeMetricPlot` only remembers a position when the window closing is the last one open — every other one sits at a cascade offset, and storing that would walk the remembered origin across the screen a little further every session. The **notes** button is deliberately a toolbar button rather than a panel row: the window is already five panels deep and a log needs height the layout does not have, while what the operator actually needs is one press to write a line down at the moment something happens — and like the rest of the toolbar it is never disabled, since writing a note is safe in any state and the states worth writing about are exactly the busy ones. `App` owns the `mabr.data.SessionNotes` store (constructed in the constructor, since notes start before a schedule does — impedances, what changed since yesterday — and the controller does not exist until the first Start) and `bindNotes` hands it to `Controller.Session` from `ensureController`, *before* the `listenTo` re-point below it, so an organizer adopting the session's notebook cannot end up on the fresh one the controller built for itself. `applyNotesJournal` then points the plain-text crash journal at the output folder at Start; a **preview gets none**, because writing no files at all is the whole of what Preview means, and neither does a run with no output folder — the notes are still kept and still reach any file a later real run writes. Deliberately *not* part of `captureConfiguration`: a configuration is settings, a notebook is data. Because an open organizer keeps itself current through `BlockReady`, `traces` is a pure raise once it exists — it backfills from the `Session` only when building the organizer from scratch, so it cannot discard a loaded `.torg` view. `stim` is on-demand (it inspects what is about to be played, not what is coming back); `adoptStimuli` pushes each newly loaded bank into an open viewer, and a plain raise deliberately does *not* re-push, so it keeps the user's selection.

A **File** menu (leftmost, built before `SettingsMenu` in `createComponents`) holds `Save Configuration…` / `Load Configuration…` — the direct analogue of the legacy `+abr` ConfigTab's "Save/Load a Config file", now covering everything the GUI owns: Subject/Output, the stimulus bank plus per-stimulus repetitions, Strategy/Advance/ISI, and the `Artifacts`/`Filters`/`Audio` policies, in one `.mabrcfg` file (a MAT-file under `save(file,'MABRConfig')`, matching the `.abr`/`.torg` convention of a distinctive extension over a plain MAT-file). This is a separate concept from each policy's `loadPrefs`/`savePrefs` "last used" persistence — a configuration is a deliberately named, reloadable point (switching between protocols on one rig) captured by `App.captureConfiguration` as **plain structs**, never classdef objects, so a file saved by one version keeps loading after a class gains or loses a property. `App.applyConfiguration` restores defensively field-by-field (the same rule `loadPrefs` already follows) and returns a warning string rather than calling `setStatus` itself, because `onLoadConfiguration`'s own final status would otherwise overwrite it the instant it returns; `applyConfigStimuli` is where that warning usually comes from, when `StimulusSource.File` — the bank's own provenance, from `StimulusSet.Source` — is empty (a bank built live in the stimgen designer and never saved to a `.spl`/`.mat`) or has moved, in which case the bank already loaded is left alone and the repetitions are not touched either. Where the bank *does* reload, saved per-stimulus repetition counts are matched back onto it **by ID, not position**, so a bank that has gained or dropped an entry since the configuration was saved still lines counts up correctly. Restoring a Strategy that turns out to intermix stimuli always wins over a saved 'Correlation Threshold' `Advance` value (`syncAdvanceEnables` runs first and its disabled state gates whether the saved value is even applied) — early-stop is meaningless for an intermixed run, configuration or not. `LoadConfigMenuItem` is a `configControls` entry, since loading one can replace the bank/ISI/audio mapping out from under a running schedule; `SaveConfigMenuItem` is not, since capturing a snapshot changes nothing and is safe at any time, including mid-run.

- `mabr.ui.Notes` — the notebook as a **reusable component**, a view over a `mabr.data.SessionNotes` store: a log, an entry field, and a commit button. - `mabr.ui.AudioSettingsDialog` — modal editor over a `mabr.AudioSettings`. A **Testing (loopback, no hardware)** checkbox sits at the top — moved here from the main window's Acquisition panel, since it decides whether anything below it matters: checking it greys out the device dropdown, the player/recorder `[signal timing]` channel fields, the **Microphone** input channel (calibration needs a real device as much as acquisition does), and the **Test Device** button (`probeSampleRate`, which reports the sample rate the selected device actually grants), because `worker_loop`'s `prepare_device` opens no device at all in that mode. Directly beneath it, **Stimulation only (no recording / no loop-back)** is the same kind of switch one step less drastic — a real output device *is* opened, so device, player channels, and Test Device stay live, and only the recorder channels and the mic grey out. `syncTestingEnable` derives both sets of enables in one place and `readControls` forces `StimulationOnly` false under `Testing`, so the two can never both be in force. The **Sample rate** row is an *editable* dropdown (`Config.SupportedSampleRates` are the rates worth offering, not the only ones a device may run at) with the derived storage rate and stride read out beside it — `→ 12 kHz stored (÷16)` — and it is the one control here **never greyed**, `Testing` included: every other setting describes a device, while the rate also decides what `Schedule` renders and what the ring buffer is clocked at, which a loopback run does exactly as a real one does. `readRate` never throws (an editable dropdown is mid-typing for most of the edits `syncCommitEnable` reads it on), falling back to the last value that validated. Test Device probes at whatever rate is *currently selected*, which is the whole point of it sitting under the picker — and probing is the only way to know, since Audio Toolbox offers no supported-rate enumeration (`info()` returns driver, device name, and channel counts, nothing more). Beside the picker, **ASIO panel…** calls `asiosettings(Device)`: on most ASIO hardware the *driver* owns the rate and MATLAB is only asking, so the panel that actually decides it is one button away rather than elsewhere on the machine. Its transport is **Commit / Cancel** rather than OK / Cancel because the two are no longer the same act: `onCommit` applies the settings through an optional `applyFcn` the owner passes as a third argument (`App.onAudioSettings` → `App.applyAudioSettings`, which adopts them, `savePrefs`, re-runs `syncAcquisitionEnables`, and sets the status line) and **leaves the dialog open**, so the consequence of a setting is visible while it can still be changed — above all `StimulationOnly`, which takes the entire Acquisition panel out of play, and which the user would otherwise only see after closing the window they would have to reopen to undo it. `applyAudioSettings` ends in a `drawnow` because the dialog is modal and nothing would flush the queue until it closed, and a failing `applyFcn` leaves the edit *uncommitted* rather than reporting a success the app never had. `syncCommitEnable` greys Commit whenever the controls match what was last committed — nothing pending — and re-labels Cancel to **Close** by the same test, since committed settings have already been applied and are not about to be undone; the dirty comparison is against a `readControls()` snapshot taken at open, so a `settings0` holding both mode flags is normalized before it can read as a pending change. The return value is the last *committed* settings (`[]` if none), which is what a caller passing no `applyFcn` uses. Like the acquisition viewers its position is remembered across sessions (`mabr.ui.WindowPos`).
- `mabr.ui.TestRunner` — the verification suite as a window (Help ▸ Verification Tests…, or standalone). The list is **discovered**, not declared: every `verify_*.m` in `tests/` becomes a row, ordered by parsing the `@verify_…` calls out of `run_all_verifications.m` so the two cannot disagree, with anything that file does not mention falling in after — a test that exists is a test the window offers, wired into the suite or not. A test passes by returning without throwing, the same contract `run_all_verifications` relies on. Output is captured per test with `evalc`, and the `try`/`catch` sits *inside* the captured region (`runOne` → `guarded`) so a failure keeps what the test printed before it threw. Everything runs hardware-free except one deliberate opt-in: **Use the rig for the timing loop-back** re-runs `verify_timing_loopback` with `'Testing',false` and the device/channels from `mabr.AudioSettings.loadPrefs`, which is the rig diagnostic that file documents. Stop is cooperative (MATLAB is inside the test; it takes effect between them), and closing mid-run defers the teardown rather than pulling the window out from under a running test. Covered by `tests/verify_test_runner.m`, which drives it the way a user does and is itself discovered by it — the nesting is bounded because the run it drives is `verify_filters`.
- `mabr.ui.RepetitionsDialog` — modal editor returning a repetition vector (or `[]` on cancel): one value for the whole bank, or one per stimulus, with a live total and duration estimate.
- `mabr.ui.AcqController` — owns the `Engine`/`Session`/`StimulusSet`/`Schedule`, the `mabr.compute.Pipeline` (and, when asked for by its fifth constructor argument and the pool can hold them, the `mabr.compute.ComputeEngine` — see the compute-workers section), translates UI actions → engine commands and engine events → UI updates, and runs **two timers**, split by priority. `LiveTimer` (~20 Hz) is **poll and dispatch**: it takes the run's statistics from the DSP worker (`Compute.live()`, doing nothing on a tick with nothing new) or from its own `Pipeline.step` when there is none — the same struct either way — then `LivePlot.updateStats`, the `CurMetrics` the advance criterion judges, and the early-stop check. The controller itself does no signal processing. `AuxTimer` (~2 Hz, the public `AuxPeriod`, retunable mid-run) carries everything else drawn from a running block: the `LiveSnap` cache the analysis windows pull from, and the `MetricsUpdated` event the progress tally and the Run panel readouts ride. The split is load-bearing rather than tidiness, because both timers are `fixedSpacing` — a tick's period is measured from when the previous one *returns*, so every millisecond of low-priority work in the fast tick came straight off the live view's frame rate. With the progress monitor and an analysis window open, that had taken the realized refresh from ~13 Hz to **~1 Hz**; moving the slow half out restores it. Nothing on the aux timer recomputes anything — the fast tick leaves its already-built sweeps in `PendingLive` (a copy-on-write reference, not a copy) and the aux tick reads them, which also removed the second `[pre post]` concatenation the tick used to build every time (one for the snapshot, one for the view). `PendingLive` is dropped by `stop_timer` and at `begin_current_run`, so a finished run cannot be served to a puller after the fact. A single explicit `mabr.ui.ProgState` (Idle/PrepBlock/Acquire/BlockComplete/AdvanceBlock/SchedComplete/Error) drives program flow — event-driven, no global, no busy-wait. `finalize_run` **de-interleaves** the run: it pairs recorded onsets with `Schedule.runSequence` and emits one `mabr.data.Block` + one `.abr` per stimulus present, so the on-disk unit stays one-file-per-condition however the run was ordered. A homogeneous run saves the continuous trace; an intermixed one saves each stimulus's sweep windows concatenated (`compact_sweeps`) rather than N copies of a shared trace. `finalize_run` is `Pipeline.finalize` (the DSP: read the ring, recover the onsets, `resample`, split by stimulus, filter, judge — plain `parts`) followed by `assemble_blocks` (everything only the GUI process can do); with a DSP worker the first half runs there and the tail runs on its reply (see the compute-workers section). The `Artifacts` policy is applied and the `Filters` policy handed to each `Recording` in that split, and make-up runs are appended in `assemble_blocks` (see above). The live path filters the pre- and post-onset windows **together**, since `extract_sweeps` takes the baseline as the samples immediately preceding the onset at the same stride — one unbroken segment — which doubles the length available to `filtfilt` and keeps the edge transient in the baseline rather than on the first milliseconds of the response; that reasoning now lives in `Pipeline.filterRows`. Everything downstream (traces, correlation, artifact preview) therefore sees the same chain finalization will use. `set.Filters`/`set.Artifacts`/`set.Window` call `configure_pipeline`, which re-configures the pipeline (it designs the chain at the ADC rate on a change, never inside a tick) and broadcasts `Cmd.Configure` to the workers. It raises **`BlockReady`** (`.Info.block`, the finalized `Block`) once per stimulus recovered — always, independent of saving — alongside `BlockSaved` (`.Info.file`), which only fires when the `Session` has an `OutputPath`. Viewers listen to `BlockReady`. The other half of that seam is a **pull**: `liveSnapshot()` returns the sweeps of the run currently streaming as of the last live tick (time base starting negative, rows = sweeps, the artifact preview alongside), or `[]` when no run is — cached by `live_tick_body` from arrays it has already built, and cleared both at `begin_current_run` and at the top of `on_block_completed`, before finalization, so a puller can never count a run's sweeps twice. It is a pull rather than a push because `mabr.ui.MetricPlot` refreshes at 1 Hz or slower and there may be several of them: handing every one a copy twenty times a second to be thrown away is the wrong shape. `start()` also runs a one-time hardware self-test, `verifyTimingLoop`: it streams a synthetic timing-only block (no signal, a few unit pulses) through the real `Engine.prep`/`run` path and confirms at least one pulse comes back on the timing input channel before letting the first real block begin, so a broken or mis-mapped loop-back cable — "the most common rig problem" — fails immediately with `mabr:ui:AcqController:timingNotDetected` instead of after a whole block streams with zero onsets. A private `SelfTestActive` flag makes that synthetic block invisible to `on_engine_state`/`on_block_completed`. The result is cached as `VerifiedAudioConfig` against the current `Device`/`PlayerChannels`/`RecorderChannels` rather than for the controller's whole lifetime, because `App.ensureController` reuses one `AcqController` across `Start` clicks and those three are editable between runs — so the check re-runs whenever they change and is skipped otherwise. It runs unconditionally, including in `Testing` mode, since `worker_loop`'s loopback branch passes the timing column straight through and exercises the identical code path.
- `mabr.ui.LivePlot` — the live view, and the one place an intermixed run is legible while it runs. It has two entry points ending in one render: `update(sweeps,…)` and **`updateStats(stats,info)`**, which takes what `mabr.compute.Pipeline.step` returns (the latest sweep, `R`, the counts, and per condition the mean, SD and counts), so the view runs with no sweep matrix in the foreground at all — the controller feeds it statistics whichever process produced them, and `stimulusMeans` branches once at the top (`error_band` over sweeps, or `band_from_stats` over the published SD; the same arithmetic). The most recent sweep keeps its **own axes at the top** (a single sweep is tens of times a mean; sharing an axis would flatten the averages) with the correlation bar beside it; below it sits **one running mean per stimulus the run presents**, laid out four ways. Sweeps are attributed by the per-onset stimulus index `AcqController.live_info` passes through — the same pairing `finalize_run` de-interleaves by, so the live panels and the saved blocks agree. The controller hands it `[pre post]` as one contiguous segment so the time base can start **before** the onset; `TimeBase` (default `[-2 10]` ms), `Layout`, `GroupBy`, and `AmpMode` (`each`/`common`/`manual` + `ManualLimit`) are public properties, and the control strip along the bottom of the window writes exactly those. Overlaid means share an axes and therefore a scale, so `each` collapses to `common` there; the latest-sweep axes always autoscales, including under `manual`.

  **Multiple parameters** are what the lower region is really for. A bank almost never varies along one dimension — the ordinary ABR run is a Frequency × Level grid — and a list of means labelled `Tone_8000_30` in presentation order is not a view of one. `live_info` therefore also carries `Params`, the run's stimuli tabulated by `mabr.stim.StimulusSet.paramTable` (names, an `[nStim x nP]` value matrix row-aligned with `Stimuli`, and units), and the view uses it three ways: conditions are **labelled** by the parameters that actually vary across *this run* (`8 kHz, 30 dB`, never a constant one); **ordered** by them rather than by the order the schedule happened to present them in; and **grouped** by one of them. A blocked run's single mean is named the same way, in the overlaid axes' title. Which parameters count as informative is settled at the **bank**, not the run — `AcqController.stimParams` tabulates the whole bank and takes the run's rows out of it, `Varying` included — because a blocked run holds one condition and therefore varies nothing, and a view that dropped every parameter for that reason would leave the operator's own dimensions off the one label saying what is being acquired. `LivePlot` computes `Varying` itself only when a caller supplies none. The group parameter decides the colours — one hue per group, ramping pale-to-full along the within-group parameter, so a level series looks like a series instead of seven unrelated colours — and it decides the two parameter-aware layouts: **`grid`** gives every condition a tile, groups across columns and the within-group parameter up the rows with the largest at the top and short columns bottom-aligned (the live analogue of `abr_analysis/plotABRGrid`), and **`stacked`** gives each group one axes with its conditions offset into it, named on the y axis — the y ticks *are* the labels, so a threshold series needs no legend. `GroupBy` is `''` (auto: `Frequency` where the run varies one, else the coarsest varying parameter — fewest distinct values, so the grid comes out wide and short), `'none'`, or a parameter name; **one** varying parameter is deliberately left ungrouped, since a single dimension is the series itself and grouping by it would put every condition in a group of one. Naming a parameter the run does not vary falls back to auto rather than erroring — the Group menu re-derives itself from the run, so it settles by itself. Without parameters altogether nothing changes: the ID-labelled, presentation-ordered list is exactly what it always was.   **Error bands** are the right-click menu's job (`ErrorBand` = `none`/`std`/`sem`/`ci` + `ConfidenceLevel`, default 95%; the menu offers 90/95/99 as a flat radio list so one click reaches any answer). Each mean gains a `patch` in its own colour behind it, drawn as one closed polygon — mean − hw left to right, mean + hw back — from `mabr.metrics.error_band`, which is the one place the three statistics live. Its `ci` needs a t quantile and `Config.RequiredToolboxes` deliberately excludes Statistics, so `mabr.metrics.t_quantile` computes one exactly from core MATLAB's `betaincinv` via `nu/(nu+T²) ~ Beta(nu/2,1/2)` rather than approximating or requiring `tinv`. A condition with fewer than two clean sweeps gets **no** band rather than one of zero width, and a patch whose edges are not wholly finite is blanked outright (a patch is one face; a NaN vertex in the middle of it is an undefined polygon, not a gap). The load-bearing asymmetry is in the scaling: **`sem`/`ci` widen the axes to fit, `std` does not** — an SD band describes a single *sweep*, which on an ABR is tens of times the average, so folding it into the limit would squash every mean in the window to a flat line; it is drawn and left to run off the axes, which is the statement it was switched on to make. `stimulusMeans` therefore returns one bundle (`.M`, `.E`, `.A` = what the axes must fit, `.counts`, `.rejected`) so the traces, the limits, the stack spacing, and the Manual seed cannot disagree about which sweeps they describe. The band is named in the mean axes' y label (`Mean ± 1 SEM (µV)`) — and in the stack title's parenthetical under `stacked`, where the y axis is already carrying the condition names. It went in a context menu rather than the control strip because the strip is already full at the window's minimum width. `setFilterText` captions the latest-sweep axes with the chain in force (a subtitle — the sweep count owns the title and the artifact readout owns the top-left corner), so a filtered view is never mistaken for the raw signal. The control strip ends with **Analysis…**, which calls `NewAnalysisFcn` — a handle the host supplies (`mabr.ui.App` points it at its own `onMetricPlot`), because this view has no business knowing about controllers or how many analysis windows are open; unset, the button is present but disabled, since a button that opened an empty window would be worse than a dead one. It is here because the moment you want a metric plotted across conditions is the moment you are staring at the traces wondering whether the response is growing with level. Covered by `tests/verify_live_plot.m` (no hardware).
- `mabr.ui.ProgressMonitor` — how far the *schedule* has got, as opposed to what the data looks like. Three views over one tally, and the **default one draws nothing**: `simple` is the lamp, the three header labels beside it, and the control strip — no axes at all, because the header already says how far along the session is, what the rig is doing and how long is left, and a bar under it was a second drawing of the same number. The other two are `bars` (one per stimulus, or per value of any one stimulus parameter via `GroupBy`) and `heatmap` (two parameters, `HeatX` across and `HeatY` up, each cell shaded by completeness). The **window sizes itself to the view**: `applyViewLayout` collapses the plot row to one pixel (the axes is collapsed, never destroyed — switching views is a row height and a `Visible`, not a rebuild) and `fitToView` takes the figure down to `CompactHeight`, then back up to `PlotHeight` when a plot is asked for. Only the height moves — the width means the same thing in both forms and is the user's — and the **top edge is held**, so the window grows and shrinks downwards rather than jumping out from under the pointer that just changed the view. `PlotHeight` is whatever the plot views were last left at, remembered per rig in the `MABR` pref group, which is why `mabr.ui.App.onProgress` restores a remembered *position* with no minimum height and then calls `fitToView`: the spot is the user's, the height is the view's, and a remembered heat-map height would otherwise reopen the default plotless view as a tall window with nothing in the middle of it. Plus `Labels` (`counts`/`percent`/`none`) deciding what the numbers on the bars, in the cells, and in the header read as, and `AlwaysOnTop` (uifigure `WindowStyle`, the same mechanism the main window's pin uses, persisted in the `MABR` pref group). The heat map is the one view that shows a **hole** — a condition the bank does not contain, drawn empty rather than as a small number. The tally is *computed from the plan every time*, never accumulated across events: planned = every presentation in `Schedule.Runs` summed per stimulus (so `appendMakeup`/`repeatRun` enlarge it, and overall progress correctly steps *back* when a make-up run lands — the work grew), recorded = `Schedule.RunCounts`, in flight = the current run's sweep count paired against `Schedule.runSequence` — the same pairing `finalize_run` de-interleaves by, so the bar moving mid-run and the count left behind after it agree. `onBlockReady` drops the live count the instant `RunCounts` is credited, since the two would otherwise both hold the same run. It runs **no timer of its own**: it rides `AcqController.MetricsUpdated` (~2 Hz — the **aux** timer, deliberately not the 20 Hz live tick, which belongs to the trace), repaints at most every `MinInterval` (0.2 s) and then only when the tallies moved — a throttle that no longer binds, since the aux tick is now slower than it is; the rate limiting has moved upstream to `AuxPeriod` and `MinInterval` remains as this window's own guarantee against a faster caller, and forces a repaint on state changes and finished blocks; nothing is created per refresh (two patches whose vertices are rewritten, one image whose `CData` is, a fixed array of texts whose `String`s are) and layout is rebuilt only when the view, the grouping, or the plan changes. Grouping dimensions come from `StimulusSet.meta`, so a condition here and a condition in `batchABRAnalysis` are the same thing. `listenTo(controller)` re-points rather than stacking, and reads `controller.Schedule` on every refresh rather than holding it (`setStimuli` *replaces* it); `attach(schedule,set)` follows a bare plan, which is what the verification script drives. `mabr.ui.App` opens it on demand from the toolbar — never at Start like the acquisition pair, with one exception: a **stimulation-only** run opens it, because that mode opens no other viewer and this is the only window that fills. Covered by `tests/verify_progress_monitor.m` (no hardware, no pool), which drives it through `mabrtest.FakeController`.
- `mabr.ui.MetricPlot` — the **online analysis** window: ONE metric, computed per stimulus condition and plotted against the stimulus parameters, refreshed while the schedule runs. The live plot answers "what does the response look like right now"; this answers the question the experiment is actually asking — "how does this number behave across the conditions I am running". **One plot per window, and the window is deliberately not a singleton**: every press of the App's chart toolbar button (or the live plot's Analysis… button) opens another, each with its own metric, window, plot type and aesthetics, because RMS-against-level and correlation-against-frequency are two plots and folding them into one window behind a mode switch means never seeing both. `App` holds them in an array only to re-`attach` them when `ensureController` rebuilds the controller and to delete them with itself. Data comes from two sources merged by stimulus ID: finalized blocks (the `BlockReady` event plus a backfill of `Session.Blocks` at `attach`, authoritative — artifacts already excluded, filter chain already applied) and the run in progress, pulled from `AcqController.liveSnapshot` on this window's own clock. A live condition is drawn with a **hollow ring** and counted in the subtitle, since a number from 40 sweeps is not the number the block will report; repeats and make-up runs of one stimulus **accumulate** (`mergeCondition`) rather than replace, because they are more data for that condition. The plot **adapts to how many parameters vary** (`informativeParams`): none → a bar per stimulus ID, one → a line with symbols, two → one line per level of the second with a legend, three or more → the user picks the two axes and the rest average into each point (the subtitle says so). Heat map / contour / surface are on request only — `auto` never picks a surface, because lines are what is readable at a glance during acquisition — and a map asked for without two parameters, or without enough conditions to make a grid, falls back to lines and says why rather than drawing something that looks like a map and is not; the heat map indexes its axes and labels them with the real values, since drawing an octave-spaced series on a linear grid would restate it as an even one. Metrics are `mabr.metrics.online.catalog` plus any user function meeting the contract, validated at selection time. The condition table and the evaluation loop are `mabr.compute.ConditionStore` and `mabr.compute.evaluateJobs`, shared with the metrics worker; with the compute workers on, `attach` takes a **slot** on that worker (`ComputeEngine.acquireSlot`, one per window, eight in all — a window opened with none free evaluates in-process and nothing else changes), `pushJob` sends every setting change to it, and `computeValues` reads the published row back (`workerValues`) or computes locally (`localValues`, public so a test can hold the two against each other). A window whose custom metric hung the worker is flagged (`Stalled`) and evaluates nothing until another metric is picked. `render` is not re-entrant (`legend` processes events, and a tick landing inside one would `cla` the axes out from under it) and skips a redraw whose values are the ones already on screen — a setting change forces one — so idle windows cost nothing between runs. Aesthetics are entirely on the axes **right-click menu** (plot type, palette, per-series colour, colormap, marker, line style/width, grid, legend placement, log axes, manual Y limits, point labels, font size, light/dark, and the clipboard/CSV/image/pop-out exports) while the control strip owns what is *measured* (metric, analysis window, which parameter is on which axis, refresh interval) — ink on the menu, numbers on the strip. `Style` plus the analysis choice persist in the `MABR` pref group, so the next window opens looking like the last one tuned. The refresh interval is 1 s by default and clamped to `[0.25 60]`: an average moves slowly, and every open window recomputes every metric for every condition on the GUI thread. Nothing here writes anything. Covered by `tests/verify_metric_plot.m` (no hardware, no engine, no pool).
- `mabr.ui.StimulusViewer` — read-only inspector for the loaded `StimulusSet`: a multi-select list of entries beside time-domain and magnitude-spectrum axes, plus a details pane (duration, rate, peak/rms, `alternatePolarity`, passthrough params). An overlay's spectra share one 0 dB reference — the loudest entry selected — so level differences stay visible.
- `mabr.ui.TraceOrganizer` (+ `Trace`/`Marker`) — interactive stacked-waveform viewer with the broken legacy Group/Marker fixed and the user32.dll mouse hook replaced by standard figure callbacks. Each trace is labelled with its stimulus ID and carries a per-trace amplitude `Gain` on top of the shared normalization; amplitude, spacing, selection, ordering, and marking are driven from a menu bar, a right-click menu, and the keyboard, all built from one `menuSpec` so they cannot drift. `saveView`/`loadView` round-trip a `.torg` file holding the waveforms plus the complete display state, so a view reloads exactly as saved; markers are stored as sample indices so they survive rescaling. `listenTo(controller)` subscribes it to `AcqController.BlockReady` so an open view gains a trace as each block completes; it tracks one controller at a time, so re-opening the organizer (or rebuilding the controller) re-points the listener instead of duplicating traces. `listenTo` also **adopts the session's notebook** (`useNotes`), so the organizer's notepad toolbar button, its File ▸ Session notes… item, and Ctrl+N open the *same* log the main window's does rather than a second one nobody would think to check; a standalone organizer keeps its own (`NotesOwned`), and that flag is what decides whether `loadView` may install a `.torg`'s notes — over a **live** session's log it declines and says so in the status line, since a view is loaded to look at old data and the operator is still writing in the current notebook. `.torg` version 3 adds `View.Notes`; older files simply lack the field. **Double-clicking a trace** (or `i`, or Peaks ▸ Inspect trace…) opens it in `mabr.ui.TraceInspector` — the stack normalizes every trace to one shared scale, which is what a level series needs and what a measurement cannot use, so latencies are picked over there and come back through `Trace.setMarkers`. `onTraceClick` branches on `SelectionType == 'open'` and **disarms the drag** the first click of the pair armed, or the trace follows the mouse while the inspector opens. One inspector at a time: re-opening on the same trace raises the window rather than discarding the peaks placed in it, and `pruneInspector` closes it when the trace it was editing is removed. Covered by `tests/verify_trace_organizer.m` (no hardware).
- `mabr.ui.TraceInspector` — the measurement window behind that double-click: one trace, full size, in volts scaled to µV (`DisplayScale`/`DisplayUnit`), with the organizer's normalization, gain, and offset all out of the way. Waves are rows in a table — a name, a search window in ms **re stimulus onset** (a `Recording`'s `TimeVector` starts at the onset, so the trace's own time base is already the right one), and Peak or Trough — and `autoDetect` fills each enabled row with the **most prominent** extremum inside its window, ranking `mabr.metrics.find_peaks` by prominence rather than taking the first. A window holding no turning point at all (a monotonic flank, a peak on the window edge) falls back to the segment extremum: the latency it then reports is what tells the user the window is wrong, which is more use than a silent blank. **Opening the inspector runs this automatically** on whatever the constructor's `seedFromTrace` leaves unplaced — `find([obj.Waves.Enabled] & isnan([obj.Waves.Loc]))` — so a trace with nothing marked yet shows peaks with no button press, but a pick already there (seeded from the trace, or left from an earlier pass) is never recomputed out from under the user; the manual Auto-detect button/`a` has no such restriction and recomputes every enabled wave, placed or not, which is how a wave gets re-found after its window is widened. A placed marker is then dragged freely, clicked into place (snapping to the nearest local extremum within `SnapWindow` ms), or nudged a sample at a time — and it may leave its window, because the window is a search hint, not a cage. `SmoothSpan` smooths the **view and the detection together** (picking off one signal while showing another is a disagreement nobody catches until the numbers are wrong) with the raw trace still drawn underneath; markers are stored as indices into the trace's own samples, so nothing smoothed is ever transferred. **Nothing reaches the trace until Apply & Close**, which calls `Trace.setMarkers` with the placed waves in temporal order plus their names and then fires the apply callback so the organizer redraws; Cancel writes nothing. Reopening on a marked trace **seeds the table from those markers**, matching by name, so a second pass edits the first. Search windows (never the picks) persist in the same `MABR` pref group on Apply, and `results()` returns them as a table (`copyTable` puts the same thing on the clipboard). Covered by `tests/verify_trace_inspector.m` (no hardware).

## Offline analysis pipeline (`abr_analysis/`) — UNCHANGED

A **separate, function-based** batch pipeline (authored `dstolz@umd.edu`, 2025) — not part of the app and untouched by the rewrite. It reprocesses saved `.abr` files. Flow (`batchABRAnalysis`):

`getABRSessions` → `parseABRFiles` (regex over filenames, e.g. `SUBJ_ID_<n>_Frequency_<f>kHz_Level_<L>dB_<yyMMdd'T'HHmmss>.abr`) → `extractABRResponses` (loads `-mat`, filters full trace, segments into sweeps grouped by stimulus) → `rejectArtifacts` → `filterABRData` → `plotABRGrid` → `abrPermutationThreshold` (permutation-test threshold via `permtest`, with `abrPermutationThresholdCuration`).

It reads exactly: `ABR_Data.ADC.SampleRate`/`Data`/`SweepOnsets`, `ABR_Data.StartTime`, `ABR_Data.SIG.informativeParams` + numeric named params + `Label`. `mabr.data.io.writeABR` emits precisely these, plus `ADC.SweepPolarity` (+1/-1 per sweep) and `SIG.alternatePolarity` (0/1) for polarity-aware analysis, and `ADC.IsArtifact` (logical per sweep) recording which sweeps acquisition rejected — all three always written, and kept out of `informativeParams` so they don't become grouping dimensions; `verify_data_roundtrip` confirms it. Note `batchABRAnalysis` has a **known stale-signature bug** (it calls `parseABRFiles`/`extractABRResponses` with positional args that no longer match) — **do not fix** it; call those functions with name-value syntax directly instead. `parfor_progress` is an external File Exchange dependency of this pipeline.

## Data file format

`.abr` files are **MATLAB v5 MAT-files** (despite the extension) containing a single `ABR_Data` struct. Load with `load(file,'-mat')`. `.mabrcfg` files are the same convention applied to `mabr.ui.App`'s save/load configuration feature (see GUI section): a MAT-file holding one variable, `MABRConfig`, a plain struct. `.notes` files are the one deliberate exception to that convention: **plain UTF-8 text**, one `[stamp] note` per line under a `%`-commented header, rewritten in full on every commit by `mabr.data.SessionNotes.writeJournal` (`mabr.data.io.buildNotesFilename` names them alongside the session's other files). A crash journal that needs MATLAB to read it is not a crash journal; the structured copy lives in every `.abr`/`.stimlog`/`.torg` the session wrote, and `SessionNotes.fromFile` reads the text back. `.stimlog` files are the same again, holding one `MABR_StimLog` struct — the stimulation sequence of one run, and the *only* output a stimulation-only session produces (see `mabr.data.io.buildStimLog` for the fields; `Sequence` is parallel arrays, one element per presentation, so `struct2table(S.Sequence)` reads as a log on the spot). Note `*.abr`, `*.stimlog`, `.runtime_data/`, and `*.asv` are gitignored.
